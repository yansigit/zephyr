# Zephyr: an always-on agent on upstream pi-rust

Status: approved 2026-10-28. Research inputs: `/home/user/Projects/.always-on/research/{openclaw,hermes-and-peers,practices-and-channels,pi-rust-integration}.md`.

Decisions made: iMessage through a Mac running BlueBubbles; one `main` session shared by all channels; Zephyr runs in one Docker container (§4.4); repo `yansigit/zephyr`, private. Wherever this file says `rpi-gateway`, `gateway` or `gw-*`, read `zephyr`.

## 1. Goals and constraints

- One personal agent that runs 24/7 on this Linux machine. You can reach it from a terminal UI, Discord and iMessage.
- It runs tools on its own, with no per-call human approval, except for the gated classes: messages, posts and payments, the actions that reach other people or spend money. Those follow the owner's approval modes, from asking every time to full automation (§4.16). Everything else is kept safe by hard limits: a sandbox, a blocklist, budgets and a kill switch.
- **Upstream stays untouched.** The gateway lives in its own repo. It uses pi-rust only through the released `rpi` binary and published crates. Syncing upstream means bumping one version pin, with no merge.
- It survives crashes, reboots, provider errors and token expiry without losing a message or running a job twice silently.

Out of scope for v1: other chat channels, multiple users, vector memory, provider pools.

## 2. What the research says (short)

| Lesson | Source | What we take |
|---|---|---|
| One gateway process owns all state, under a lock, bound to loopback | OpenClaw, Hermes, nanobot | Same. A single daemon with a lock on its state dir, local socket only. |
| The gateway was the attack surface: one-click takeover (CVE-2026-25253), malicious skills, sandbox off by default | OpenClaw | No web UI or HTTP listener in v1. Sandbox **on** by default. No third-party skills installed automatically. |
| Deny-by-default access with sender allowlists and pairing codes | Hermes, OpenClaw | Owner-only allowlist per channel. Unknown senders are dropped and logged. |
| A hardline command blocklist that even full autonomy can't override | Hermes | A blocklist in a tool-call policy plugin, checked inside the sandbox too. |
| Scheduled jobs run in a fresh session, with a run ledger. Interrupted runs become `unknown` and are never retried automatically | Hermes, nanobot | Same. |
| Memory as plain files, kept in git, loaded as a frozen snapshot per session | Hermes, nanobot | Same. Files under `~/agent/memory`, committed after each change. |
| iMessage needs a Mac. No supported pure-Linux route exists | all three reports | A BlueBubbles server on a Mac, reached over Tailscale. This is the only part that needs extra hardware. |
| Durable messaging uses an inbox deduplicated by platform message id, an outbox with client ids, and at-least-once delivery | practices | An SQLite inbox and outbox (WAL mode, `synchronous=FULL`). |
| systemd user service with `Type=notify`, a watchdog, `Restart=on-failure`, and linger | practices | Replaced by the container (§4.4, §4.8): `--restart unless-stopped`, `supervise` restarting a crashed or hung daemon from its heartbeat, and a Docker `HEALTHCHECK`. |

## 3. Integration choice: the daemon spawns `rpi --mode rpc` children

Upstream analysis (`research/pi-rust-integration.md` §7) compared three options:

1. **Spawn `rpi --mode rpc`, one child process per session. Chosen.** The contract is the versioned JSONL protocol: 29 commands, a `ready` frame listing supported commands, `agent_settled`, `session_entry_committed`, and `resume_pending`.
   - rpi keeps owning session files, compaction and crash repair.
   - A crashed child takes down only its own session.
   - An upgrade only replaces the binary.
2. Embed the crates as a library. This gives the most control, but every 0.x bump means migrating to a changed Rust API, and matching the CLI's behaviour needs the unstable `rpi_cli::session::build`. It stays a fallback.
3. An rpi plugin as the daemon. A plugin lives inside one rpi process, so this isn't viable. It is used only as a **sidecar** (§5.4).

**How syncing works:** `gateway.toml` pins `rpi = "0.18.x"`. To upgrade, run `cargo install rpi-cli@<new>` into a versioned path. Then run `rpi-gateway doctor`, which spawns one test child and checks `ready.supportedCommands` against the commands we use. Then switch the symlink. A failed doctor run leaves the old binary in place.

**Not the fork.** The gateway runs on upstream `rpi`, never on `yansigit/pi-rust`.

### 4.1 Sessions

- **`main`** is one long-lived session shared by all three channels. The owner's `/new` (or `/clear`) starts a fresh one, `main-<unix secs>`, kept in `state.db` so restarts reopen it; the old file stays. `/switch` lists the saved `main`/`main-<secs>` sessions (newest first) and `/switch <id>` points `main` back at one, restarting the child when idle as `/new` does; only ids found in `sessions/` are accepted. Attack success rises with session length (ClawSafety Table 3: 50% at 10 turns, 77.5% at 64). It is your assistant, so the context continues whichever channel you use. Each inbound message is prefixed with its channel, e.g. `[discord] …`. The reply goes back to the channel the message came from.
- **`job-<id>-<run>`** is a fresh session for each scheduled run, as Hermes and nanobot do. It is deleted after 30 days.
- **Retention** (`retention.rs`, from the scheduler's tick at start and then hourly): as the agent, regular files only, matched by exact name, never through a symlink, it deletes what is older than 30 days: `job-*` and `task-*` session files (and their `.lock`), the logs and exit files of ended processes (`.procs/<id>.log|.exit`), and ended tasks' overflow reports (`tasks/<id>.md`). Never a `main*` session (`/switch` lists those), nor a running process's or open task's files. The same sweep prunes the projects' checkpoints to the newest 50 per project (§4.14), and, as root: takes the day's backup (§4.8), prunes `state.db` (§4.2), marks replies pending over 7 days `expired` (an unconfigured channel's never go), and deletes the copies in `<state>/files` that no pending reply names (older than an hour, since `send_file` writes the copy just before its row). The sweep runs on a blocking thread with its own store connection, never two at once.
  - Also the files the owner sent (`inbox/<channel>-<id>-<n>.<ext>` and a crash's `.<stem>.part`, §4.3).
- **`btw`**: the owner's `/btw <question>` (outside the queue, one at a time) reads `main` with `get_messages` (rpi answers it mid-run too) into a compact transcript (user and assistant text, `[tool: name]` notes, 2000 chars a message, 24000 in all, oldest dropped first) and asks it, with the question, of a throwaway child on main's account: `--no-session --no-tools` (rpi 0.15 then sends the provider no tools, the plugin's included, and writes no session file), policy plugin still loaded, 120 s cap, on a task of its own. The answer goes to the asker as `[btw] …`, and its usage is booked like a job's; `main`'s session, queue and run are untouched.
- **Ordering:** one prompt at a time per child (`maxConcurrentPrompts: 1`).
  - A message that arrives while the agent is busy is **steered** into the running turn: RPC `queue_message` with `"deliverAs": "steer"`. rpi 0.15 delivers it after the tool call in progress finishes, as a user message (`message_start`/`message_end` with role `user`), and the model reads it before its next step. With the `claude-code` provider every tool call is its own rpi turn, so this happens between tool calls. OpenClaw made steering its default after messages piled up behind long runs (openclaw#15540, #77023).
  - A steered row goes in with a note after its tagged text (`router::steered`): it arrived while the agent was working on the request above, so answer it in a line or two and carry on. Without it, Haiku 5.5 took a mid-run question for the new task: it answered "what is 3+5?" and ended the run with the research unfinished.
  - The router marks a steered row delivered on that user `message_end`, and sends the next assistant text with something in it to that row at once, not at the settle. The run's own row still gets the run's last text.
  - If the run's own row is left with no text of its own (its last text already went to a steered row, or there is none), it is never closed silently: it goes once more as a continuation (`router::continued`), asking the model to carry on, or to answer exactly `NO_REPLY` if it had finished. A `NO_REPLY` is not sent (OpenClaw's silent token). From the transcript alone, "one text answered both" and "answered the steer and stopped" look the same, so this costs at most one short turn instead of losing the work.
  - Steering only happens while busy. A steer sent while idle is accepted and silently waits for the next run, so a steer that races the end of a run is taken back by `reconcile` (`clear_queue` empties the steering and follow-up queues) and dispatched again.
  - How each row went is kept on it (`inbox.sent_as`: `prompt`, `steer` or `continue`; schema v9), and a row waiting to go as a continuation is a `new` row with `continue`. After a gateway crash, `reconcile` rebuilds the run's steer state from the store (`restore_steers`): the run's origin is the newest `dispatched` row sent as `prompt` or `continue`, the later `steer` rows are its steered messages, and their sent replies come from the outbox. rpi keeps queued steers across a restart itself (its harness README), so nothing steered is lost and no reply goes to the wrong row or twice.
  - A steered message still waits for the tool call in progress. A long command would hold it, which is why main runs commands through `exec` (§4.13), and why long work goes to background tasks (§4.12).
  - A `/stop` from any channel sends `abort`, and stops every background task. rpi 0.18 takes back what is still queued (the `abort` answer lists it), so a steered row the run never reached is missing at the settle and goes again through the missing-rows path.
  - A **follow-up** is a row that waits for the settle instead of steering in: an attached client's `send` prompt with `"followUp": true` (the TUI's Alt+Enter). It is stored with `inbox.deliver = 'after'` (schema v10; every other row is `steer`), `dispatch_new` skips it while a run goes, and each one then starts a run of its own, oldest first. While idle it goes at once, like any message. The router holds it itself rather than using rpi's follow-up queue, so it stays a `new` row the owner can still take back.
  - **Taking back** (`zephyr.dequeue`, the TUI's Alt+Up): the `tui` rows still `new` and never sent (`tries = 0`: held by a run, a follow-up, `/pause` or a child that is down) become `withdrawn` and their texts go back to the client, oldest first. A message already steered is rpi's and stays; so are other channels' rows.
- **`/thinking [level|next]`** sets rpi's thinking level (`set_thinking_level`), checked against `get_available_thinking_levels`; `next` takes the one after the current, wrapping. With no argument it lists them. rpi keeps the level neither in the session nor in its settings, so the router sets every new child to the owner's choice again (`shortcut:` until the daemon restarts). The level and the model's context window (`get_state`'s `context.window`, 0 when rpi does not know it) are read when the child starts and after a `set_model`, into `Snapshot.thinking` and `Snapshot.context_window`.
- **`task-<id>`** is a fresh session for each background task (§4.12).
- **`/undo`, `/retry`, `/compact`, `/fork`** are the owner's, outside the queue, and need the agent idle: while a run is going they answer to wait for the reply or `/stop` it first.
  - `/undo [n]` (n from 1 to 20) takes the last n exchanges out of `main`'s context. The exchanges are counted in the conversation itself, `get_messages` (`router::turns`): each tagged user message starts one, unless it follows a tool result (a message steered into the run, so part of its exchange) or repeats a row already seen (a continuation, which goes under the same row after its first form); untagged notes (the resume note) start none. `get_messages` gives each entry's `entryId` (its `parentId` is always null, so the order of the list is what counts), and `navigate {targetId}` moves the session leaf. rpi puts the leaf *on* the target, which stays in context, so the target is the entry just before the n-th exchange's first message, normally the previous assistant reply; when there is none, `navigate` with no target goes to the root, an empty context. The next `prompt` carries on from there; the old branch stays in the session file, so `recall` (§4.11) can still find it: the live check had Haiku recover an undone codeword that way. `shortcut:` recall reads every entry; making it follow only the active branch would need the session file's `parentId` chain. Every row tagged in what was cut becomes `undone` (no schema change: `inbox.status` has no CHECK), so recovery never sends them again although their text is no longer in `get_messages`. Files the agent changed stay changed. Another `/undo` takes the exchange before; fewer exchanges than n is refused, as is one in a fresh `/new` conversation.
  - The TUI's rewind picker (Esc Esc on an empty, idle composer) lists the same exchanges, newest first, from the attach method `zephyr.turns` (the router's own `get_messages` through `router::turns`), so its k-th entry is what `/undo k` takes back; the pick sends `/undo k` and puts the message in the composer.
  - `/fork` copies `main`'s session to a new `main-<secs>` (the next free second) and switches to it as `/switch` does; the reply names the session it came from, which stays as it was. rpi 0.18 has no `fork` RPC command (its `ready.supportedCommands` lists none; a `fork` frame answers `unknown command type: fork`), so zephyr copies the files as the agent (`rpc::copy_session`): rpi's `<stamp>_<id>.jsonl` names its id in its header line and refuses to open a session without its `.progress.jsonl` companion (`required progress companion is missing`), which names it too (`session_id`); both are rewritten, the companion first, and the lane's leaf comes with the copy, so the fork starts where `main` stood. Neither file is ever overwritten.
  - `/rename <name>` names the current session (`session_names`, schema v11; control characters dropped, 60 characters at most). `/switch` lists each session with its name and its first user message's first six words (`rpc::opening`, which reads only the top of a `.jsonl`), the snapshot's `session` is the current session's name (else its id) for the TUI's header, and the attach method `zephyr.sessions` lists `{id, name, at}` for the TUI, which asks again after each `/rename`, `/fork`, `/switch` and `/new` reply.
  - `/export` writes the conversation (`get_messages`; user and assistant text under who said it, each tool call one line of its name and arguments) to `$ZEPHYR_PROJECTS/zephyr-exports/<session>-<YYYYmmdd-HHMM>.md` in the configured timezone, and replies with the path. The daemon has no CAP_CHOWN, so it writes under `agent::fs` (setfsuid/setfsgid to the agent): the folder and file are created with the agent's ids, the owner's on the host, and a symlink the agent planted leads nowhere it could not write itself. Without `ZEPHYR_PROJECTS` it says so.
  - `/retry` is `/undo`, then the same text as a new inbox row on the same channel and sender, platform id `retry-<row>-<n>`, dispatched like any message.
  - `/compact [instructions]` sends `compact` (with `customInstructions`). rpi runs it as a run of its own: it answers `accepted`, commits a `compaction` entry and settles with `outcome: "compacted"` and a `summary` ("Conversation compacted · 44 tokens before, 5 messages kept."), which goes to the owner as `[zephyr] <summary>`. A message that arrives meanwhile is steered and, never delivered, sent again after the settle, as a steer racing the end of a run is.
  - `/usage [days]` (default 7, at most 366) lists spend per UTC day, newest first, with each pooled account's share, from the `spend` and `account_spend` tables. `/status` keeps today's one line.

### 4.2 Message flow and durability

1. **Inbound.** The adapter writes `inbox(platform, platform_msg_id UNIQUE, sender, text, status='new')` and commits before acknowledging the platform. A duplicate platform id is ignored.
2. **Policy check.** The router rejects any sender not on the owner allowlist; the message is logged and gets no reply. Before it, a Telegram or Signal message whose whole text is `/pair CODE` is a pairing claim (§4.3, "Owners on Telegram and Signal"), stored `dropped` with its text cut to `/pair`. The owner check comes before the write, so a stranger's row is inserted `dropped` in the same statement: a crash cannot leave it `new` for the next start to dispatch. Otherwise it marks the row `dispatched` and sends `prompt` (or `queue_message`) with a client tag stored in the row.
3. **Reply.** On `agent_settled`, the router takes the final assistant text of that turn. It writes `outbox(inbox_id, channel, text, client_id, status='pending')` first, then sends.
   - The client id is Discord's `nonce` with `enforce_nonce`, or the BlueBubbles `tempGuid`, so the platform drops a retried duplicate.
   - Sends are retried only while the platform still dedupes the client id: 5 min on Discord, 1 h elsewhere. Then the row becomes `failed` and the failure is surfaced on the TUI. Client ids are at most 20 chars (Discord's nonce limit is 25).
   - A send that takes over 10 s counts as failed, and that channel is skipped for 30 s, so one stuck channel (a chat client that stopped reading, a hung HTTP call) cannot hold up the router or the other channels. The chat channel also drops a connection that does not take a line within 2 s.
4. **After a crash:**
   - **Gateway crash.** On start, `dispatched` rows whose text is already in the session (checked with `get_messages`) are not sent again. Rows whose text is missing are re-sent once.
   - **Child crash.** Respawn it with `--session-id`. If `get_messages` reports `pendingResume` (rpi 0.15 does not put it in `get_state`), call `resume_pending`; rpi allows at most 3 attempts. After that, the gateway tells you in the originating channel.
   - **What rpi recovers.** rpi 0.15's harness records each frame as it streams, so a run cut off resumes from the last committed frame. A tool call cut off mid-flight is replayed only when it is declared safe; otherwise its outcome is recorded as unknown, so the model is told it does not know whether that step happened. After `resume_pending`, the router steers in `scheduler::RESUME_NOTE` (OpenClaw's restart wording): Zephyr restarted while you were working; check the current state of anything that was in progress (files, processes, tasks, external actions) before repeating it, then continue. `reconcile` never takes that note for a message of the owner's. A resumed run that settles before reaching the note would leave it in rpi's queue to open the next run, so the router tracks it (delivered when rpi shows it as a user message) and, if it is still queued at the settle, clears the queue first; any owner message held with it is then sent again through the missing-rows path, answered once. A task's note is left alone: its child stops after the run, and rpi keeps the note in that session, so it is delivered only if that same session is resumed again.
   - **A wedged child.** A run stopped for a limit or a stall (§4.4) that has not settled 60 s later (or `stall_limit`, if shorter) means rpi stopped answering: the router drops the child, which kills its process group, and goes through the child-exit path, so the run resumes as after a crash. An `abort` waits at most 5 s, and a write to rpi's stdin shares the call's 60 s deadline; a write that times out kills the child, since a half-written line breaks the stream.
   - **A rate-limited message** is put back to `new` at most 5 times (`tries`); after that it is answered `[zephyr] the run ended without a reply`, so a provider error that only looks like a rate limit cannot loop.
   - **Shutdown.** While draining (SIGTERM or a re-exec) nothing new is dispatched; messages that arrive meanwhile are written as rows (commands answered) and run at the next start, and the intake is closed only after the outbox flush.
   - **A budget pause that ends** at UTC midnight is noticed by the router's tick, which dispatches what waited, as `/resume` does.
   - **Power loss.** rpi doesn't fsync its session log, so the last few entries can be lost. The inbox survives, because SQLite does fsync, and step 4's check re-sends anything missing. Optional upstream PR: fsync on session appends.
5. **Where notices go.** A run's sent files, outbound list, memory and draft notices and budget notice go to the sender of the newest message the agent took up as a prompt (`Store::last_owner`: rows with `sent_as`), read before reconcile dispatches the next row. A command-only row (`zephyr reload`, `zephyr config set` on the host, `/status`) never becomes that sender.
6. **Growth.** Schema v14 indexes the status columns (`inbox`, `outbox`, `tasks`, `procs`) and `runs(job_id, due_at)`. The hourly sweep (`retention.rs`) ends the web app's expired sessions (§4.3.3), and deletes sent and failed outbox rows and audit rows older than 90 days, and empties the text of settled inbox rows that old without deleting them: dedupe by platform id needs the row (an iMessage backfill reaches back `lookback_hours`), and inbox ids must never be reused. It also deletes one-time passes that old and empties the payload and the agent's reason of settled held actions that old (§4.16, D8): a message's text and what a fact hold was about would otherwise stay in `state.db` and its backups; the row stays, so its id is never used again. Each chat line carries `re`, the `platform_msg_id` it answers (null for a notice), so `zephyr reload` and `pause` print their own reply, not an older notice.

### 4.3 Channels

- **TUI.** The goal is that stock `rpi --connect 127.0.0.1:<port>` attaches with no upstream change.
  - The gateway implements rpi's small remote JSON-RPC: `authenticate`, `start_session`, `subscribe`, `send`, `stop_session`.
  - `start_session` returns `main`.
  - `subscribe` replays history from `get_messages`, then streams live events.
  - The client's `stop_session` only detaches.
  - `get_state` reports the model the agent is on now (the active account's, or `model`), so the client's footer follows `/model` and failover.
  - What the router writes itself for `tui` (command replies, notices such as the outbound list and memory diffs, job output) has no agent event, so it is sent to attached clients as an assistant message. With no client attached, notices and job output wait in the outbox for the next attach.
  - Unverified: these details come from reading the code, not from a test run. Fallback: a ~150-line `rpi-gateway chat` line client over the same socket.
  - A follow-up upstream PR could add `--connect --session <id>`.
  - The attach port and the iMessage webhook each take at most 32 connections at once; an attach connection that has not authenticated within 10 s is closed, and the webhook reads a request head within 10 s. Under the network floor (§4.20) the agent can reach neither: both bind the container's own address, which its uid is refused, and clients inside the container (`zephyr tui`, stock `rpi --connect`) connect there. The caps stay for other users on the host, who reach the ports Docker publishes on its loopback, and for `network = "host"`, where the agent can reach both and must not exhaust the daemon's file descriptors with idle sockets.
  - The host's root clients (`zephyr attach`, `zephyr tui`) keep their files in `/var/lib/zephyr/tui` (the daemon dir, 0700), never in `/tmp`, where the agent could create the folder first.
  - For stock clients, a user turn is drawn as an assistant block `**<channel>** · <text>` (the `[channel #id]` tag removed), and `get_state` reports the live account's model (`Snapshot.model`) and `thinkingLevel` (`Snapshot.thinking`).
- **Web.** A phone-first web app the daemon serves itself, behind `tailscale serve` (§4.3.3). It speaks the attach protocol over a WebSocket as channel `web`; an approval signed with a passkey acts as channel `passkey`.
- **Owners on Telegram and Signal: the pairing code** (`pairing.rs`, pure; the router does the rest). The owner rarely knows their Telegram user id or Signal ACI, and a lookup bot run by someone else is the wrong thing to trust, so the id comes from a message, on the strength of a code only a strong channel saw. Identity is that platform's stable id (`from.id`, `sourceUuid`), never a display name or `@username`.
  1. `/pair telegram|signal` is taken only from a channel in `strong_channels` other than `passkey` (`tui` or `chat` by default), as `/web enrol` is, and only while that channel's table is set. It answers `[zephyr] send /pair ABCDE-FGHJK to the bot within 10 min; it works once` (`to zephyr's Signal number` for Signal). The code is 6 random bytes in base32; only its SHA-256 and expiry are kept, in `meta` (`pair_telegram`, `pair_signal`), and a new code replaces the old one. `gateway` refuses `/pair` and `/unpair`, and a command's reply goes only to its own channel, so the agent never sees the code.
  2. **The claim.** At the top of `Router::inbound`, on every intake path (a shutdown's or re-exec's drain too), before the owner check would drop a stranger's row, a message on `telegram` or `signal` whose whole text is `/pair CODE`, CODE in a code's shape (ten base32 characters; case, the hyphen and spaces do not matter; `/pair telegram` from a channel listed in `strong_channels` is the command, not a claim), is checked against the hash in constant time. Its row is stored `dropped` with its text cut to `/pair`, so the code is never in `state.db`, and a re-delivered message is a duplicate that claims nothing. On a match the `meta` row is taken in one statement (`Store::take_meta`) and the sender id is appended to `owners.<channel>` through `toml_edit`; the owner list is read live, so no restart is needed, and the change is a `settings_log` row (actor `pairing`). The new owner is answered `[zephyr] paired: you are an owner of this zephyr`, and every owner channel (`router::notify_owners`: each owner on `chat` and on every channel whose table is set, and attached clients) is told `[zephyr] Telegram user 123456789 ("Aiden", @aiden) is now an owner; /unpair telegram 123456789 removes them`, which is how the owner learns if someone else used the code. The name comes from the adapter (`Channel::known_as`, the last name that sender used), never from the row.
  3. **Wrong codes** get no reply, so there is no oracle. They count only while a code is out (a claim with none out is logged and nothing more, so a stranger cannot keep pairing closed or have the owner told). Five in 10 minutes close pairing for 15 minutes (`web::signin::Limits`, as the web app's sign-in, on limits of their own); the owner is told once, `[zephyr] 5 wrong pairing codes; pairing is closed until HH:MM`, and `/pair` says so meanwhile.
  4. `/unpair CHANNEL ID` is taken from any owner channel, since it only takes away.
  A stranger's other messages are dropped silently, as on Discord (§4.2 step 2).
- **Telegram** (`telegram.rs`): a bot in private chats, over Bot API long polling with `reqwest`. `[telegram]` takes Discord's keys (`token_env`, `progress`, `progress_after_secs`); `owners.telegram` holds user ids.
  - `run` calls `deleteWebhook` once, then loops `getUpdates {offset, timeout: 50, allowed_updates: ["message", "my_chat_member"]}` on a 60 s client. The offset moves past a batch only after every row of it went to the router, and Telegram counts the batch taken only when the next call carries it: a crash before then re-delivers it (Telegram keeps updates 24 h), and the inbox's platform-id dedupe drops what was stored. A 409 (another client polls the bot: a second zephyr, a side container on the same token) is logged once and retried every 30 s; other errors back off from 5 s, doubling to 5 min. `run` never ends for them, since a channel's error ends the router.
  - **Taken:** only a `message` whose `chat.type` is `private`, whose `from.id` is the chat's id, from a user who is not a bot. The row is `platform_msg_id = "<chat.id>-<message_id>"`, `sender = from.id`, text the message's `text` or `caption`. A display name or `@username` is never an identity: the adapter remembers the last one each sender used (`Channel::known_as`, `"Aiden", @aiden`, quoted with escapes, at most 1000 kept) for the pairing notice only. A bare `/start`, which Telegram sends when a chat opens, is dropped. `edited_message` is not subscribed and the Bot API sends no deletions, so a message already taken stays taken.
  - **Groups are refused twice:** README has the owner set `/setjoingroups` to Disable in @BotFather, and a `my_chat_member` for a group, supergroup or channel whose new status is not `left` or `kicked`, or any message from one (a group joined while zephyr was down), gets `leaveChat` and never a row.
  - **Files:** `photo` (the largest size), `document`, `audio`, `voice`, `video` and `video_note` go through `inbox::append`. `getFile` is called only when `inbox::owner` holds, so a stranger's file costs no call; the bytes come from `GET {api}/file/bot<token>/<file_path>`. The Bot API serves at most 20 MB, so a larger file is listed `too large, not downloaded`.
  - **Sending:** `sendMessage {chat_id, text}` with no `parse_mode` (Markdown shows as typed), in pieces of 4096 UTF-16 units (`channel::chunks`), then the attachment as multipart `sendDocument` (`voice.ogg` as `sendVoice`). Telegram has no client nonce, so the adapter remembers in memory how many pieces of each `client_id` got a 200, for 5 minutes (the router's retry window), and a retry starts after them; a timeout after a request went out may still send a piece twice, and a restart resends the whole reply. A 429 waits its `retry_after` and tries again. While a run goes, `sendChatAction typing` every 4 s, and the progress note as Discord's (`Progress`, `progress_text`): posted after `progress_after_secs`, edited with `editMessageText` at most every 5 s, deleted with `deleteMessage` on `Stop` or before the reply.
  - **The token** is in every URL (`/bot<token>/…`): no URL is logged, every `reqwest` error goes through `without_url()`, and the token is redacted from Telegram's own descriptions and anything else the adapter returns or logs. The struct that holds it has no `Debug`. A hidden `Config::telegram_api` (default `https://api.telegram.org`) points tests at a stub. `doctor` checks the variable is set and that `getMe` answers, naming the bot.
- **Signal** (`signal.rs`, `[signal] account`, owners `owners.signal` by ACI). The daemon runs `/opt/zephyr/signal/bin/signal-cli --data-dir /var/lib/zephyr/signal -a ACCOUNT jsonRpc --ignore-stories --ignore-avatars --ignore-stickers` as a child of its own (`Config::signal_cli`), in its process group with `kill_on_drop`, so it dies with the daemon. It speaks JSON-RPC on stdin and stdout, one object per line with ids `z<n>`, so nothing listens. Its environment is cleared to `PATH` (root's system folders), `JAVA_HOME` (the image's `/opt/zephyr/signal/jre`) and `JAVA_TOOL_OPTIONS=-Xmx256m -XX:+UseSerialGC`. A child that exits is started again after 5 s, doubling to 5 min, and logged; `run` never fails for it.
  - **Why root:** the account's keys must be out of the agent's reach, and root's `<state>` already is (§4.4): the agent can neither run signal-cli with them nor read the conversation's keys or the account's password. The cost is a JVM that parses traffic from anyone who messages the number, running as root with the daemon's SETUID, SETGID and KILL and able to read `state.db`, `secrets.env` and `vault.toml`; a uid of its own is a follow-up.
  - **Keys.** `<state>/signal` (root, 0700, made so at every start) holds the identity keys, password and sessions. It is never under `<home>` and not in the daily backup: old session keys restored beside a live account desynchronize it, and the cure for a lost folder is to register or link again. `zephyr signal-setup remove` runs `unregister` (best effort, 60 s), then deletes the folder.
  - **A number of zephyr's own, never the owner's account.** `zephyr signal-setup register NUMBER [--voice]` (root, in the container; `zephyr channel add signal` runs it with `docker exec -it`) says so in those words, takes the `signalcaptcha://` token from signalcaptchas.org and sends it as `register`, then the SMS or call code as `verify`, both over the stdin of a multi-account `signal-cli jsonRpc` (an argv is readable in `/proc` by the agent's uid), then runs `updateProfile --given-name zephyr`. `link` is for a number whose account lives on a spare phone: `link -n zephyr` prints the `sgnl://linkdevice` URI, shown as a terminal QR with `/usr/bin/qrencode -t ansiutf8` (printed as text without it). A device linked to the owner's own account would receive every conversation they have, and its keys would speak as them to all of their contacts; the adapter takes nothing from such an account (below), so that mistake fails closed.
  - **What is taken:** a `dataMessage` with no `groupInfo`, `groupV2`, `reaction` or `remoteDelete`, with text or files, from a `sourceUuid` that is neither our own ACI (signal-cli's `data/accounts.json`) nor from our own number. Every `syncMessage`, `editMessage`, typing, receipt, story and call is dropped. The row is `platform_msg_id = "<sourceUuid>-<timestamp>"`, `sender = sourceUuid`: a number may be hidden and can change, the ACI is stable. `sourceName` and `sourceNumber` are remembered (256 senders) for `known_as` only. No read receipts are sent; signal-cli's delivery receipts stay, so a stranger learns that the number is on Signal and nothing more.
  - **Files.** signal-cli saves every attachment, a stranger's too, to `<state>/signal/attachments/<id>`. An owner's reach `inbox::append` as `Src::Path` (an id that is not a plain file name is listed `not downloaded`), read as root and copied into `<home>/inbox` as the agent. Then every attachment the envelope names (quotes' thumbnails, sync and group messages' included) is deleted from the data dir, owner or not; a stranger's is never read.
  - **Durability gap** (`shortcut:`): signal-cli acknowledges a message to the server when it reads it, not when zephyr commits the row, so a message in the pipe when the daemon dies (its file copy is the window) is lost.
  - **Sending:** `send {recipient: [ACI], message, attachments: [<state>/files/<id>/<name>]}`, root's copy, the file on the last chunk. Chunks are 2000 UTF-16 units; the chunks a client id already delivered are remembered in memory for 5 min (the retry window), so a retry sends only the rest. Activity is `sendTyping` every 10 s and `sendTyping {stop: true}` on Stop; there is no progress note (`shortcut:`, Signal's edit-a-message makes one possible later).
  - **Safety numbers.** signal-cli keeps `on-first-use`. When an owner's identity key changes (a new phone), sends to them fail with `IDENTITY_FAILURE`, and the owner is told once per ACI per daemon run on their other channels (`router::notify_owners`): `[zephyr] the Signal safety number of <ACI> changed; compare it, then run zephyr channel signal trust <ACI>`. The daemon's signal-cli holds the account's lock, so `zephyr signal-setup trust ACI` drops the ACI in `<state>/signal/.trust` (0600) and waits up to 30 s; the adapter looks every 2 s, removes it and sends `trust {recipient, trustAllKnownKeys: true}`.
  - **doctor:** the data dir is the daemon's and 0700; `.ok` in it names `account` (the adapter writes it when `listAccounts` names the account at each child start and removes it when the child exits); a warning when `Config::signal_cli` is missing.
- **Files the owner sends** on Discord, iMessage, Telegram or Signal (`inbox.rs`). rpi 0.15's `prompt` takes text only, so a file reaches the model as a path: `read` inlines png, jpg, gif and webp for the model (checked on the `claude-code` provider).
  - The adapter saves each file as the agent (`agent::fs`) to `<home>/inbox/<channel>-<msg id>-<n>.<ext>` before the row goes to the router, and appends one line per file to the row's text: `[attached image: /zephyr/inbox/discord-<id>-1.png (screenshot.png, image/png, 240 KB); open it with read]`, or `[attached file: …]` for anything else. The inbox schema, dedupe, reconcile and the TUI are unchanged, and a message that is only files is no longer dropped. iMessage's U+FFFC placeholders are removed from the text.
  - iMessage takes only messages whose `handle.service` is `iMessage`: an SMS forwarded to the Mac can carry a spoofed sender number, so it never counts as the owner.
  - Only an owner's files are fetched. The router hands each adapter its live config once at start (`Channel::live`, a `watch` that `/reload` updates), and the adapter checks `is_owner` on it; before that, or for anyone else, files are listed `not downloaded`. The router still drops a stranger's row as before.
  - At most 10 files a message and 25 MB a file; others are listed `too large, not downloaded` or `over 10 files, not downloaded`. A fetch is tried 3 times, 2 s apart (an iMessage file may still be arriving on the Mac), then listed `download failed`, and the row still goes.
  - Discord: the attachment's CDN `url`. iMessage: `GET /api/v1/attachment/{guid}/download` with the password, as the other BlueBubbles calls; backfill asks for `with: ["chats", "attachment"]`. BlueBubbles converts HEIC photos to JPEG on download, so the served `Content-Type` picks the extension. A webhook is answered once its row is queued, and one worker fetches each row's files and passes the rows on in arrival order: BlueBubbles gives up on a webhook after 15 s and never retries it, and a crash meanwhile is covered by the next start's backfill. On Discord, where serenity runs each event on its own task, a lock does the same. Either way a caption sent after a photo (iOS sends them as two messages) stays after it. Backfill re-reads the last day at every start, so a file already saved under its name is reused, not fetched again. A voice note is saved like any other file; nothing transcribes it.
  - Retention (§4.1) deletes these files after 30 days.

#### 4.3.1 Attach protocol: `zephyr.*` extensions

Zephyr's own TUI uses the same port, token and framing (one JSON-RPC 2.0 object per line; events are `{"jsonrpc":"2.0","method":"event","params":{"subscriptionId":1,"event":<event>}}`). Everything here is additive: the stock client never calls these methods, and it drops the `zephyr_*` event types (its `apply_line` fails to decode them as a `RemoteEvent`). Both methods need `authenticate` first (else error `-32001`); so does every method below.

**`zephyr.hello {}`** → `result` is the current `Snapshot`:

```jsonc
{
  "version": "0.4.0",                // zephyr's crate version
  "session": "main",
  "account": "work",                 // string | null: the pooled account the agent runs on; null without [[account]]
  "model": "anthropic/claude-x",     // string | null: that account's model, else `model`; null = rpi's default
  "thinking": "medium",              // string | null: rpi's get_state thinkingLevel, read when the child starts and on /thinking
  "context_window": 200000,          // integer | null: the model's context window in tokens; null when rpi does not know it
  "paused": "user",                  // string | null: "user" or "budget:<YYYY-MM-DD>"; null = not paused
  "channels": [                      // the adapters this daemon runs, then the known ones it doesn't
    {"name": "chat",    "state": "connected"},
    {"name": "discord", "state": "connected"},
    {"name": "imessage","state": "off"},
    {"name": "web",     "state": "off"}        // "connected" while a web socket is open
  ],                                 // state: "connected" | "off" | "reconnecting" (today: running adapter = connected, not configured = off)
  "spend": {
    "tokens": 1234,                  // integer: today's (UTC) tokens, all accounts and jobs
    "cost": 0.0123,                  // number: today's cost in USD
    "daily_tokens_limit": 500000,    // integer | null: [budget] daily_tokens
    "daily_cost_limit": 5.0          // number | null: [budget] daily_cost_usd
  },
  "queue": [                         // inbox rows waiting (status new), oldest first
    {"channel": "discord", "preview": "first 60 chars of the text…", "since_unix": 1793318400}
  ],                                 // since_unix: integer, when the row arrived (seconds); age = now - since_unix
  "failed_replies": 0,               // integer: outbox rows that failed for good
  "run": {
    "busy": true,                    // between agent_start and agent_settled
    "since_unix_ms": 1793318400123,  // integer | null: when agent_start arrived
    "origin": {"channel": "discord", "id": 42, "sender": "1234"},  // object | null: the user message being served (inbox row id)
    "current_tool": "bash",          // string | null: between tool_execution_start and _end
    "tools_done": 3                  // integer: tool_execution_end count this run
  },
  "accounts": [                      // the [[account]] pool in order; [] without one
    {"name": "work", "model": "anthropic/claude-x",
     "state": "cooling",             // "ready" | "cooling" | "needs login"
     "until_unix": 1793322000}       // integer | null: when a cooldown ends
  ],
  "jobs": [                          // the 5 soonest scheduled runs, soonest first
    {"id": 3, "name": "renew domain", "next_unix": 1793350800}
  ],
  "proposals": 0                     // integer: proposals waiting for /ok or /no (not the `queue`)
}
```

When idle, `run` is `{"busy": false, "since_unix_ms": null, "origin": null, "current_tool": null, "tools_done": 0}`. `preview` is the row's text with whitespace runs folded to one space, cut to 60 chars, with `…` appended when cut.

**`zephyr.subscribe {}`** → `result` is `{"subscriptionId": 1, "sessionId": "main", "status": "subscribed", "messages": [...]}`. `messages` is rpi's raw `get_messages` list (user, assistant with `toolCall` blocks, `toolResult`, ...), unchanged except that every user message gets two more fields:

```jsonc
{"kind": "user", "role": "user", "content": "[discord #42] hi", "timestamp": 0,
 "origin": {"channel": "discord", "id": 42},  // object | null: from the [channel #id] tag; null when untagged
 "text": "hi"}                                 // the message text without the tag
```

Then events follow, in order:
1. `{"type": "ready"}`
2. `{"type": "zephyr_status", "snapshot": <Snapshot>}` at once, then again each time the snapshot changes (never twice with the same value). It is a `watch`: each event carries the latest whole snapshot, and quick intermediate values (a tool that starts and ends between two reads) may be skipped. Its order relative to the child events in 3 is not fixed.
3. Every live child event (the `--mode rpc` line: `agent_start`, `message_update`, `tool_execution_start`, `agent_settled`, ...), except `response` lines. User messages in `message_start`/`message_end` get `origin` and `text` as above. Unlike `subscribe`, nothing is quoted or hidden: the client's own turns come back too.
4. `{"type": "zephyr_reply", "text": "agent: account work on ...", "command": "/status", "channel": "tui"}`: a reply to an attached client's channel (`tui`, or the web app's `web`) that the agent's stream does not show; `channel` is where a command's reply belongs, and only that channel's clients are sent it, while a notice has `channel` null and goes to every client. It carries answers to commands (`/status`, `/model`, `/reload`, `/login`, `/stop`, `/pause`, `/resume`, `/memory ...`, `/job ...`; `command` is the command text), notices and job output (`command` null), and `[zephyr] ...` fallbacks for a run that ended without a reply (`command` null). An ordinary agent reply is not repeated. Stock `subscribe` connections get this event too and ignore it.

**`zephyr.models {}`** → `{"accounts": [{"name": "work", "model": "anthropic/claude-x", "models": ["anthropic/claude-x", "anthropic/claude-y"]}]}`: each pooled account, its model, and the models `rpi --list-models` lists on that account's provider (run with the account's agent dir). Without a pool there is one entry with `name` null, the top-level `model`, and everything rpi lists. When rpi cannot list, `models` holds just the account's model. It runs rpi once per account, so a client asks only when it shows the list (the TUI's model picker).

**`zephyr.login_providers {}`** → `{"providers": [{"id": "antigravity", "label": "Antigravity", "kind": "oauth"}]}`: the providers the image ships (§4.4), as `rpi auth login --provider` takes them. `kind` says what finishing the sign-in needs: `oauth` (a URL you open, then the browser comes back), `key` (you paste an API key) or `setup_token` (`claude setup-token` prints a token you paste).

```jsonc
// zephyr.login_start {"provider": "antigravity", "account": null, "model": null}
{"loginId": "l1", "provider": "antigravity", "account": "antigravity-1", "kind": "oauth"}

// zephyr.login_poll {"loginId": "l1"}
{"phase": "need_input",           // "waiting" | "need_input" | "done" | "failed"
 "url": "https://…",              // string | null: the OAuth URL rpi printed, once it has
 "lines": ["Open this URL …"],    // the login process's recent output, for a human: the URL or the prompt
 "account": "antigravity-1",      // string | null: the [[account]] name
 "model": "antigravity/gemini-x", // string | null: the model to record, empty until one is known
 "error": null}                   // string | null: why it failed
```

`zephyr.login_start` spawns the login and answers once the login's child has started, not before: rpi may be asked for a model first, so the `loginId` can take a few seconds, and the sign-in URL follows on the daemon's next 5 s tick rather than in this answer; `account` defaults to the first free `<provider>-<n>`, `model` to the model the request named, else the account's existing model, else the first row `rpi --list-models` lists for that provider (§4.7.1). `phase` is `waiting` while the process runs, `need_input` when it takes a line on stdin (a key, a setup token, or under the network floor an OAuth sign-in's callback address, §4.7.1; an OAuth sign-in under host networking stays `waiting`), `done` once the `[[account]]` row is in the file, `failed` otherwise; those four are what a client can see. There is a fifth, `recording`, for the instant the row is going into the file, and it is internal: a poll takes the login's own lock, the one `recording` is set under, so no client ever reads it. A cancel is refused in `recording` and `done`, because the row cannot be taken back after the fact: the answer must match the file. A sign-in that ends without a row also drops the directory it made — rpi writes `auth.json` before the outcome is known, and an account directory the config does not name would make `rpi auth check` pass for that name later without anyone signing in. `zephyr.login_input {"loginId": "l1", "text": "…"}` → `{}` sends the pasted token to that process's stdin. `zephyr.login_cancel {"loginId": "l1"}` → `{}` kills the login's child and records no phase as done: it writes nothing to `zephyr.toml`. A login that had already finished before the cancel is not cancelled — it stays `done`, and its account stays in the config. Only the `loginId` the daemon returned is a handle: a login is not tied to the connection that started it, so a client may detach and poll later. `lines` is the login process's own output, with whatever went in through `zephyr.login_input` redacted out of it: a token is the one thing the daemon neither echoes back nor keeps.

The same login is a slash command on every channel: `/login` lists the provider ids, `/login PROVIDER [ACCOUNT] [MODEL]` starts one and replies at once that it is signing in (never the token, and an account name only when the command gave one). The start itself runs off the loop that reads the child, which must not wait on a login — resolving the model can spend 20 s on `rpi --list-models` — so the resolved account and model, and then the URL, follow as their own notices on the router's 5 s tick. Each notice goes to the channel sender who asked, never to whoever spoke last: one owner's sign-in URL is not another's news. At most 8 sign-ins wait for their URL at once, and a live one is never dropped to make room: a further `/login` is refused, because a sign-in whose URL was never posted can never be finished. `/login cancel [ID|PROVIDER]` is the way out of that refusal: it cancels the login with that id, the ones started for that provider, or with no argument every sign-in this router started (only its own: the registry is process-wide, so another daemon's or an attached TUI's sign-in is never touched), naming what it cancelled — `[zephyr] cancelled the sign-in to antigravity as antigravity-1`, or `[zephyr] no sign-in to cancel`. A start that has not resolved yet has no id to give, so it is aborted and reported by its provider. A channel can only finish an `oauth` sign-in — the URL is opened on the user's machine and the login completes itself. A `key` or `setup_token` provider needs the token typed, which a chat is no place for, so that command is refused before anything starts and points at `zephyr login` on the host; the TUI's `/login` panel (§4.3.2) takes it masked. These are §4.7.1's machinery.

A slash command goes in as `send {"sessionId": "main", "command": {"type": "prompt", "content": "/status"}}`, as with the stock client. A prompt with `"followUp": true` waits for the run to settle instead of steering in (§4.1).

**`zephyr.dequeue {}`** → `{"texts": ["first", "second"]}`: the `tui` messages rpi has not been sent yet, oldest first, now `withdrawn` (§4.1); `[]` when none wait.

The settings and approvals methods act as the owner on channel `tui`, a strong channel by default, and go through the same code as `/set`, `/ok` and `/no`:

- **`zephyr.settings {}`** → `{"sections": [{"name", "settings": [{"key", "label", "help", "kind", "value", "source", "access", "strong", "until", "modified"}]}], "strong_channels": [...]}`. `kind` is `{"type": "bool" | "int" | "float" | "duration" | "choice" | "model" | "text" | "list" | "mode" | "optional", ...}` with its `min`/`max`, `min_secs`/`max_secs`, `options` or `inner`; `value` is the text replies show (`null`: unset); `source` is `default`, `you`, `agent (#N)` or `until HH:MM`; `access` is the agent's (`never`, `propose`, `tighten`) or `read-only`; `until` is a unix time while a time limit runs, else `null`; `modified` is true on `approvals.preset` while a hand-set class differs from the preset (`semi (modified)`). A connector's setting has one entry per connector, labelled `Connector NAME enabled`.
- **`zephyr.settings_set {"key", "value", "until"?}`** → `{"outcome": "changed", "key", "old", "new", "applied", "until"}`, `{"outcome": "proposed", "id"}` or `{"outcome": "refused", "reason"}`. `until` is `30s`..`30d` as in `/set KEY VALUE for 2h`. A missing `key` or `value` is `-32602`.
- **`zephyr.goals {}`** (params ignored, may be absent) → `{"goals": [{"n", "text", "done"}]}`: the open goals in `GOALS.md` order (`n` is the number `/goal done N` takes), then those marked done since the last daily review (or 24 h; `settings_log`), newest first, with `n: null`. Read-only: changes go through the `/goal` commands as text. Errors: `-32000` `reading the goals failed: …`, `gateway is shutting down`.
- **`zephyr.proposals {}`** → `{"proposals": [{"id", "card", "kind": "setting" | "command" | "run" | "pass" | "wait", "status", "due_at", "key", "age_secs", "expires_in_secs", "strong", "signed"}]}`, newest first; `strong` says the proposal needs a strong channel, and `signed` is the text a passkey signs: for a held action its card made without the time left (`gate::signed_card`), for a command or a setting the stored command itself, whole. It is what the web app shows and a passkey signs (§4.3.3). A held action (`run`, `pass`, `wait`) also carries `class`, `summary` and `once`, and its `card` is the gate's whole card as the chat got it (`gate::card`), not the stored summary; `status` is `pending`, or `scheduled` with `due_at` for one waiting out its delay; `once` says `/ok N once` differs from `/ok N` for it now (its class is `ask-new`); `strong` is set for a payment while `approvals.strong_only` names `money`; a browser wait expires in 10 minutes.
- **`zephyr.decide {"id", "verb": "ok" | "once" | "no" | "cancel"}`** → `{"ok": bool, "text"}`, `text` being what `/ok N`, `/ok N once`, `/no N` or `/cancel N` replies, with the stale and strong-channel checks. `once` is `ok` for a setting. Another `verb` is `-32602`.
- **`zephyr.activity {"range"?, "kind"?, "before"?, "limit"?}`** → the activity record (§4.19), `{"since": 1762646400, "entries": [{"at", "kind", "subject", "status", "text", "line", "stream"}], "next": "1762693320.audit.5512"}`, newest first. Every field is optional (`null` is absent): `range` is `today`, `Nh` or `Nd` (1 h to 90 d, default `24h`), `kind` one of §4.19's kinds (default every kind but `tool`) or `grants`, `before` a previous answer's `next`, `limit` 1 to 200 (default 50); words are read as `/activity` reads them. `text` and `line` are scrubbed as the chat's are, and `line` is the chat line, so no client formats anything. `stream` is true for a row from rpi's event stream (`out`, `tool` and the policy's `refused`), which a hostile agent can forge (§4.4 item 3). `next` is the last entry's cursor (`AT.SRC.ID`, parsed strictly: an integer, one of the six table names, an integer) while more remain, else `null`, and a page starts strictly before it, so a row written meanwhile neither repeats nor shifts a page. With `kind: "grants"`: `{"since": null, "entries": [{"at", "kind": "grant", "subject", "line", "revoke"}], "next": null}`, `revoke` being the command that takes the grant back, or `null` for a time limit whose value could not be shown as it is (scrubbed or cut), which is set back by hand. A bad `range`, `kind`, `before` or `limit` (or a value of the wrong JSON type) is `-32602` with `/activity`'s usage; a store error is `-32000` `reading the activity failed: …`, a router that is gone `-32000` `gateway is shutting down`.
- **On a web app's socket** (§4.3.3) `zephyr.decide` and `zephyr.settings_set` also take `{"challengeId", "assertion": {"id", "clientDataJSON", "authenticatorData", "signature"}}` (fields base64url), from **`zephyr.web_challenge`**, and **`zephyr.web_devices {}`** lists the passkeys, sessions and push devices. The TUI's connection ignores the two params and has neither method.
- **`zephyr.facts_list {}`**, **`zephyr.facts_put {"name", "kind", "value", "allow"}`** and **`zephyr.facts_rm {"name"}`** → `{"facts": [{"name", "kind", "allow"}]}`, the private facts (§4.18) as they are after the call, never a value. `facts_put` adds or replaces a fact; an empty `value` for a saved name keeps the saved value. An error is `-32602` and never quotes a value (a fact with a missing name or an unknown kind is `the fact is malformed`). The agent is not told of these.

#### 4.3.2 The TUI client (`zephyr tui`)

A plain click stores an anchor (its column and transcript row); a Shift+click selects from the anchor's cell, clamped to the rows on screen, to the click. Clicks on one cell within 400 ms count up: the second selects the word under it (letters, digits and `_-./~:@+`), the third the row's text past the gutter. A one-character word cannot be selected this way: rpi-tui reads a press and release on one cell as a click. Some terminals (kitty, WezTerm) keep Shift+click for their own selection and never send it.
- **Panels** open over the bottom of the screen, between header and footer, and from 9 rows up never cover the header: a list taller than the room scrolls. Esc closes; arrows and PgUp/PgDn move; typing filters the lists; the footer shows the panel's keys.

The edit goes out as `zephyr.settings_set`, the TUI being a strong channel; a refusal keeps the editor open with the daemon's reason under it in the error colour, a change closes it and says `KEY OLD → NEW [until HH:MM]`. Read-only rows, subagents and rules say where they change instead (zephyr.toml, `/subagent`, `/rule`).
    - *Private facts* lists each fact as `name  kind · allow: targets`, never a value. `a` adds one and Enter or `e` edits one in a form (name, kind turned with Space or ←/→, value, the targets it may reach without a check, comma separated); the value field is drawn one bullet per character, as the vault's form is, and the value leaves in the `zephyr.facts_put` the moment the form is saved and goes with it, never drawn, kept or printed by `Debug`. The form checks the fact first (`Fact::check`: the minimum length, a name already saved), so a short value is fixed in place; editing keeps the name, and an empty value keeps the saved one. `d` asks, `y` deletes (`zephyr.facts_rm`). Enter on the Approvals section's facts row opens this section.
    - *Waiting* lists the proposals newest first with how long each has waited; a held action shows its class and summary (`message · email to alice@example.com`) and, waiting out its delay, when it goes (`at 14:05`). Enter shows the whole card: the command `/ok` runs (cleaned, wrapped), the setting's value now, when it expires and whether it needs a strong channel; for an action, the gate's own card. `o` approves, `1` approves once, `c` cancels a delayed action, `d` drops, each a `zephyr.decide` whose reply shows in the panel. `1` sends `once` for a setting (where it is `ok`) and for any message or post, whatever the list said its class's mode was, so a mode moved to `ask-new` since the list was read never turns the owner's `1` into an `ok` that remembers the recipients; it is offered only where the class is `ask-new`, the one mode where once differs (the gate's card offers `/ok N once` only there too), and on a payment or another call `1` approves as `o` does. What it saved comes back into the box, unsent; a non-zero exit keeps the draft. The file is deleted either way.

Nothing goes to the agent yet: the result is held and put in front of the owner's next message, `` [the owner ran `cmd` (exit N): ``…`]`, several in the order they finished. A `/` command does not take it; Esc on an empty input drops it.

If it is still going after `[discord] progress_after_secs` (default 20), one note is posted, `≋ working · 0:24 · bash, read ×3`, edited at most every 5 s and deleted on `Stop` or before the reply's first chunk. `progress = false` turns the note off; typing stays.

- **iMessage.**
  - Needs an always-on Mac (any Apple Silicon or recent Intel) signed in to your Apple ID, running BlueBubbles Server, joined to the same Tailscale network.
  - Inbound arrives as a BlueBubbles webhook to the gateway's tailnet-only listener, with a shared secret, and is checked against your handle.
  - Outbound uses the BlueBubbles REST send endpoint.
  - The BlueBubbles API shape was read from source and still needs checking against a running server. Without a Mac, this adapter stays off and the rest works.

#### 4.3.3 The web app

`src/web/`: `mod.rs` (the listener), `passkey.rs` (WebAuthn ES256) and `push.rs` (Web Push), the last two pure functions on `ring`. The app itself is `assets/web/`, plain files embedded in the binary.

**One listener.** With `[web]` set, `web::serve` joins the router's `select!` beside `attach::serve`, with the same handles (`attach::Handles`). A change to `[web]` re-execs the daemon, as `[attach]` does.

```toml
[web]
host = "box.tail1234.ts.net"       # the name tailscale serve answers on; Host and Origin must match
port = 7793                        # the default
# tailnet_users = ["owner@github"] # optional: Tailscale-User-Login must be one of these
```

- **It runs only under the network floor** (§4.20; `web::floored`). Under `network = "host"` the agent's uid could reach the port, and the sign-in limits, which cannot tell one client at the port from another, would be the agent's to use against the owner. So there the app does not start: the daemon logs `zephyr: web app not started: the web app needs the network floor; host.toml network = "bridge"` and runs on, `zephyr status` reads `web: the web app needs the network floor; …`, `doctor` fails that line, `/web` and `/web enrol` answer it instead of a link, and `zephyr web setup` refuses with it.
- It binds through `egress::listen_addr` (`web::address`): the container's own address, which the agent's uid cannot reach and `zephyr up` publishes on the host's `127.0.0.1:<port>` (the `web.port` row of `egress::LISTENERS`; the port is 7793 when `[web]` names only its host). `tailscale serve` on the host forwards to `http://127.0.0.1:<port>`. `doctor` and `status` connect to the same address. An address that cannot be had (no `zephyr` line in `/etc/hosts`) is logged and fails that one line of `status` and `doctor`; it never ends the daemon or either command. It has the iMessage webhook's limits: 32 connections at once, 10 s to send a request head, one request per connection.
- `GET /`, `/app.js`, `/app.css`, `/sw.js`, `/manifest.webmanifest`, `/icon-192.png` and `/icon-512.png` are the embedded files, with `Cache-Control: no-cache` and the crate version as their ETag (a matching `If-None-Match` gets 304). They hold nothing private. Anything else is 404.
- Every response carries `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self' wss://HOST; manifest-src 'self'; worker-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy: same-origin`; `/api/*` answers `Cache-Control: no-store`. Nothing in the app is inline, so the CSP needs no nonce (a test reads the files for `innerHTML`, `eval(`, inline scripts and inline styles).
- A port that cannot be bound is logged (`zephyr: web app not listening on port P: …`) and the daemon runs on without the app; `zephyr status` reads `web: not listening`, and `doctor` fails its `web app listening on 127.0.0.1:P` line.
- At start it makes `<state>/web/` (0700) and the Web Push key `vapid.pk8` (0600) when missing. A key that does not load turns push off and fails `doctor`'s `the web push key loads`; it is never replaced, since each subscription is bound to the key it was made with.

**Reaching it.** The owner fronts the port with `tailscale serve` on the host, which gives HTTPS on the tailnet name: the secure context passkeys and service workers need. `web::admit` checks every request before any route, in this order:

1. **Host** must equal `[web] host` (ignoring case), else 421. That stops DNS rebinding from a page on the owner's laptop. The host is a bare name (`Config::validate`: lowercase letters, digits, `-` and `.`; no scheme, port, path or trailing dot).
2. **`Tailscale-User-Login`**, which `tailscale serve` adds for tailnet users, must be there, and be one of `tailnet_users` when that is set (ignoring case), else 403 `open the app through tailscale serve`. That turns away an accidental `tailscale funnel`, a browser on the box hitting the port, and other people on a shared tailnet. It never authenticates or authorises anyone, excuses a passkey, or appears in a log, an audit row or `settings_log`: anything that can open the port can send any header.
3. **Origin.** A POST, a DELETE and the WebSocket upgrade need `Origin: https://HOST` exactly, and `Sec-Fetch-Site: same-origin` when that header is sent, else 403. A POST or DELETE also needs `Content-Type: application/json` (else 415), which a cross-site form cannot send without a preflight. With the cookie's `SameSite=Strict`, that is the CSRF defence, and it covers WebSocket hijacking.

Tailscale Funnel and any other public exposure are refused by (2); the listen address is not configurable.

**Channels `web` and `passkey`.** A session cookie is a bearer token on a phone, worth what a Discord session is worth. So the app speaks as two channels:

- **`web`** is everything the cookie alone does: chat rows (inbox channel `web`, sender `web`), unsigned `no` and `cancel`, changes to settings that are not `strong`, and the notification buttons. It is weak unless the owner lists it in `strong_channels`.
- **`passkey`** is the actor channel of a `zephyr.decide` or `zephyr.settings_set` that carried a verified passkey assertion for that exact request. It never has inbox or outbox rows: a command it approves runs as a `web` message, and a notice for it goes to `web`.
- `attach::attached(channel)`, true for `tui` and `web`, is the test for "a client on one of the daemon's own ports": `Config::is_owner`, the reply shown on the event stream, notices, and the outbox flush, where a `web` row is handled as a `tui` row is while a web socket is open and waits otherwise.

**The WebSocket bridge.** `GET /api/ws` carries the attach protocol (§4.3.1), one JSON-RPC message per text frame, into the same `attach::Conn` the TUI gets (`attach::serve_stream`, generic over the stream). There is no second protocol.

- The upgrade needs what `admit` checks and the session cookie, else 401; a fifth open socket gets 503. hyper hands the connection over (`hyper::upgrade::on`) and `tokio-tungstenite` frames it (`WebSocketStream::from_raw_socket`, messages and frames of at most 1 MiB, the attach line limit). The listener leaves keep-alive on, since hyper would otherwise answer `Connection: Upgrade, close`; the 10 s head deadline runs again for each request on a connection.
- `web::bridge` joins the socket to the `Conn` through a `tokio::io::duplex`: a text frame goes in with a newline, and each line out is one frame.
- The socket is closed on a binary frame, a text frame holding a newline, a frame over the limit, more than 60 frames in a minute, no frame or pong for two ping intervals (it pings every 30 s; a phone that froze the page answers none), and once its session has ended, which is read again every 60 s and at once when a `/web` command ends sessions (`Hub::revoke`). A send that a stalled client does not take within two ping intervals closes it too.
- `Hub::connected()` is the number of open sockets; `Snapshot.channels` lists `web` as `connected` while it is not 0.
- A web `Conn` starts authenticated and is on channel `web`. **Open to it:** `zephyr.hello`, `zephyr.subscribe`, `send` (`prompt` with `followUp`, `abort`, `get_state`), `zephyr.models`, `zephyr.dequeue` (its own channel's messages), `zephyr.turns`, `zephyr.settings`, `zephyr.settings_set`, `zephyr.proposals`, `zephyr.decide`, `zephyr.facts_list`, `zephyr.vault_list`, `zephyr.activity`, `zephyr.goals`, `ping`, and the app's own `zephyr.web_challenge` and `zephyr.web_devices` (`attach::WEB_METHODS`). **Closed**, with `-32601` `not available in the web app`: everything else, so `authenticate`, the stock `start_session`, `subscribe`, `stop_session` and `list_sessions`, `zephyr.login_*`, `zephyr.vault_put`/`_rm`/`_revoke`, `zephyr.facts_put`/`_rm` and `zephyr.sessions`. Secrets are typed on the TUI or the host, never on the phone.
- The TUI's `Conn` is unchanged: no gate, and channel `tui`.
- **`zephyr.web_devices {}`** (web only) → `{"passkeys": [{"name", "created_at", "last_used_at"}], "sessions": [{"passkey", "created_at", "seen_at", "this"}], "push": [{"passkey", "created_at"}]}`: names and times, never a credential id, a key, a cookie's hash or a push endpoint. `this` marks the asking socket's session.

**Passkeys** (`web/passkey.rs`, `web/signin.rs`). WebAuthn ES256 with user verification, discoverable credentials and `attestation: "none"`, checked by hand on `ring`: a library's challenge is always random, and zephyr's must commit to what is approved (below). The relying party is the full `[web] host`, since `ts.net` is a public suffix.

- **Enrolment is closed.** `/web enrol [NAME]` is taken only from a channel in `strong_channels` other than `passkey` (`tui` or `chat` by default; `zephyr web enrol`, in the container and on the host, asks over the chat socket), and answers `[zephyr] open https://HOST/#enrol=ABCDE-FGHJK on the phone within 10 min, or type the code there; it works once`. The code is 6 random bytes in base32, 10 characters a phone can type (case, the hyphen and spaces do not matter). Only its SHA-256 is kept, in `meta` (`web_enrol`, with the name and the expiry), and a new code replaces it. The fragment never reaches a log or a `Referer`, and the agent never sees the code: it is a reply on `tui` or `chat`, `gateway` refuses `/web`, and a command's reply is sent only to its own channel's clients. A NAME is 1 to 32 of `[A-Za-z0-9_-]`; without one the passkey is `passkey-N`. At most 10 passkeys.
- **`POST /api/enrol/start {code}`** compares the code's hash in constant time and answers `{challengeId, publicKey}`: the creation options (`rp {id: HOST, name: "zephyr"}`, the install's random 16-byte `user.id` kept in `meta`, `pubKeyCredParams [{alg: -7}]`, `residentKey` and `userVerification` `required`, the stored passkeys as `excludeCredentials`) around a random 32-byte challenge. A wrong, used or expired code is 403 and counts as a failure.
- **`POST /api/enrol/finish {challengeId, name?, id, clientDataJSON, authenticatorData, publicKey, alg}`** takes the browser's `getAuthenticatorData()`, `getPublicKey()` and `getPublicKeyAlgorithm()`, so no CBOR is parsed. `passkey::check_created` checks the type `webauthn.create`, the challenge, the origin `https://HOST`, no `crossOrigin`, the `rpIdHash`, the UP, UV and AT flags, that the attested credential id is `id`, that `alg` is −7, and that `publicKey` is the fixed 26-byte P-256 SPKI prefix and a 65-byte point; only the point is stored. The code must still be the one the ceremony started with, and is deleted in one statement (`Store::take_meta`), so of two ceremonies started with it one enrols. The browser is signed in, and every attached client and the owner last answered are told `[zephyr] passkey NAME was added to the web app; /web rm NAME removes it`: that notice is how the owner finds out if someone else used the code.
- **Sign-in.** `POST /api/login/start {}` answers request options with no `allowCredentials`, `userVerification: "required"` and a challenge; `POST /api/login/finish {challengeId, id, clientDataJSON, authenticatorData, signature}` finds the credential by id and runs `passkey::verify`: the type `webauthn.get`, the challenge, the origin, no `crossOrigin` (only those four keys of `clientDataJSON` are read, since browsers add others), at least 37 bytes of authenticator data with `rpIdHash == SHA-256(HOST)` and the UP and UV flags, the signature (`ECDSA_P256_SHA256_ASN1` over `authenticatorData ‖ SHA-256(clientDataJSON)`), and the sign count (WebAuthn §7.2: once the stored or the new count is not zero, the new one must be the greater, else it may be a clone; synced passkeys send 0 both times). It stores the count and `last_used_at` and sets the cookie.
- **Challenges** (`passkey::Challenges`) live in memory for 2 minutes under a random 128-bit id, and are used once: taken out on their owner's first finish, whether or not it verifies, while a finish by anyone else leaves them alone. At most 16 wait. A sign-in anyone may start is turned away when 16 wait (429 `too many sign-ins are waiting; try again in two minutes`) rather than push out one in flight, which may be the owner's; an enrolment, proven by its code, and a session's signing challenge take the oldest one's place instead. A restart drops them and the app asks again.
- **Removal.** `/web rm NAME` works from any owner channel, since it only takes away: it deletes the passkey with its sessions and pushes (`Store::remove_passkey`, one transaction) and closes its sockets at once. `/web signout` ends every session. `/web` lists: `[zephyr] web app https://HOST · passkeys: phone (used 2h ago), ipad · 3 sessions · push on 2 devices`. After the last passkey is lost, a new `/web enrol` starts over.

**Signing an approval.** Every `ok` and `once` made in the app, and every change it makes to a `strong` setting, is signed with the session's passkey over a challenge that commits to the effect. A passkey guards against a stolen phone session and records who approved what; it does not make a misleading card honest, so what is signed is exactly what is stored and shown.

```jsonc
// zephyr.web_challenge: what the owner is about to sign
{"op": "decide", "id": 7, "verb": "ok", "card_sha256": "<hex SHA-256 of the card text on screen>"}
{"op": "set", "key": "budget.daily_cost_usd", "value": "8", "until": "2h"}
// → {"challengeId": "c3", "publicKey": {"challenge": "<b64url>", "rpId": "HOST", "timeout": 120000,
//    "userVerification": "required", "allowCredentials": [{"type": "public-key", "id": "<this session's passkey>"}]}}
//   or -32602 "the card changed; look at it again" | "no proposal #7 is waiting" | "too many signatures; wait a minute"
// then, with navigator.credentials.get's result:
{"method": "zephyr.decide", "params": {"id": 7, "verb": "ok", "challengeId": "c3", "assertion": {…}}}
```

- **The preimage** is a JSON array, so its order is fixed: `["zephyr-web/1", "decide", 7, "ok", <digest>, <card_sha256>, <nonce>]` or `["zephyr-web/1", "set", key, value, until, <current value>, <nonce>]` (`passkey::preimage`). The WebAuthn challenge is its SHA-256.
  - `digest` is `Store::proposal_digest(id)`: SHA-256 over the row's `kind`, `class`, `command`, `targets`, `payload`, `secrets`, `key` and `seen` as stored, which is everything `/ok` reads.
  - `card_sha256` must equal the hash of what the router would show now (`AttachRequest::Card`, the `signed` of `zephyr.proposals`), so the page and the daemon agree on what is signed. For a held action that text is its card made without `expires in N h` (`gate::signed_card`): the time left changes by itself, and a hash over it would undo a signature made a minute before the hour turned. It is built without the countdown, never cut out of a finished card, and a command's or a setting's signed text is its stored command unchanged: a proposal is the agent's own text, and one that read `/rule be careful · expires in 2 h, and bcc x@evil.com` must be shown and signed whole. The page shows the countdown apart, from `expires_in_secs`, and hashes the text as received, never a cleaned copy.
  - For a setting, the current value comes from the router too (`AttachRequest::Current`).
- **The challenge** is kept in memory for the session that asked (`Hub::sign`), 2 minutes, one use; at most 16 wait, in a queue of their own, so sign-in attempts cannot push out a pending signature. A session may ask for 10 a minute.
- **`zephyr.decide` on `web`:** `ok` or `once` without an `assertion` is refused, `-32602` `approve with your passkey`; `no` and `cancel` only take away and act on `web` unsigned. With one, the connection (`attach::Conn::signed`) takes the challenge (`that signature expired or was used; tap again`), checks that it was issued for this `id` and `verb` (`that signature is for another request`: a signature for one proposal never approves another), and runs `passkey::verify` under the session's own passkey, whose credential id the assertion must carry (`the passkey signature did not verify`). It then asks the router to decide as channel `passkey`, with what was signed.
- **A signed approval runs as `passkey`.** The command an approved proposal carries (`/set …`, `/facts rm …`) is run as channel `passkey`, so the strong-channel checks that let the approval through also let its command through; its notices go to `web` (`attach::rows`). Whatever the command, one that was refused or failed answers `ok: false` and `… did not apply …` with the handler's own words, never `ok: true` with nothing applied: `set_setting` (every `/set`, `/model`, `/rule`, `/goal`, `/persona`, `/subagent`), `/vault`, `/facts` and `/switch` note it for the decision (`Router::not_applied`).
- **The last check is the router's**, on its own loop, just before `/ok` (`Router::decide`): the proposal's digest and its card's hash must still be the signed ones, else `{"ok": false, "text": "[zephyr] the card changed; look at it again"}` and nothing runs. So nothing can change between the check and the effect: a payload swapped after the signature, a fact saved or a mode changed that alters the card, all refuse it, and the owner reads the new card. A signed decision that ran adds its own audit row (`session` `web`, `tool` `passkey`, `args` `#7 ok`, `outcome` `signed`), since `audit` has no channel column; `settings_log.channel` and the strong-channel checks read `passkey`.
- **`zephyr.settings_set` on `web`:** without an `assertion` it acts on `web`: a tightening applies, and a strong loosening gets the registry's own refusal (`loosening KEY needs tui or chat or passkey`). With one, the same steps bind the signature to this key, value and time limit, and the router refuses when the value is no longer the one signed over (`KEY changed; look at it again`). The app signs whenever the setting is `strong`.
- Receipts (the signature and what it signed, for a third party to check) are not stored yet; the preimage is shaped so they can be.

**Sessions, cookies, rate limits.**

- The cookie is `__Host-zephyr=<32 random bytes, base64url>; Path=/; Secure; HttpOnly; SameSite=Strict; Max-Age=2592000`. Only its SHA-256 is stored (`web_sessions`, schema v18).
- A session lasts 30 days from sign-in, or until it is 7 days unused; `seen_at` is written at most once a minute. The hourly sweep deletes the ended ones. At most 20 sessions; a new one drops the oldest. `POST /api/logout` ends this one, closes its socket and clears the cookie.
- The limits are global and in memory, since every request comes from 127.0.0.1. The routes that can guess something (`enrol/start` with its code, and both finishes) take 20 requests a minute between them, then answer 429; a sign-in merely started is not counted, and is bounded by the 16 that may wait. Five failed ceremonies in 10 minutes (a wrong code, an unknown credential, a bad signature, a stale or used challenge) close enrolment and sign-in for 15 minutes (429 `sign-in is closed until HH:MM`), and the owner is told once: `[zephyr] 5 failed passkey attempts on the web app; sign-in is closed until 14:05`. Open sessions keep working. These limits cannot tell the owner's phone from anything else at the port, which is why the app runs only under the network floor, where the agent's uid cannot reach it. What is left is another user of the host, who can reach the published loopback port and so can keep sign-in closed or keep 16 sign-ins waiting; they cannot sign in, enrol or touch an open session, and the owner is told of each lockout.
- A refused ceremony is logged with its fixed reason (`wrong origin`, `bad signature`, …), never with a value from the request.

**Web Push** (`web/push.rs`), by hand on `ring` and `reqwest`: the `web-push` crate would bring an OpenSSL-backed `ece` and its own HTTP client.

- **VAPID (RFC 8292).** An ES256 JWT (`ECDSA_P256_SHA256_FIXED_SIGNING`: JOSE takes r‖s, not DER) with `{"aud": <the endpoint's origin>, "exp": now + 12 h, "sub": "https://HOST"}`, so no personal address. The key is `<state>/web/vapid.pk8`. `GET /api/push/key` (cookie) gives its public point; each time the app opens it compares that with its subscription's and subscribes again when they differ, so a remade key heals itself.
- **aes128gcm (RFC 8291).** For each message a fresh ECDH P-256 key pair and salt, two HKDF-SHA256 rounds, AES-128-GCM, one record with the `0x02` delimiter, and the header `salt ‖ 4096 ‖ 65 ‖ as_public`. `encrypt` is pure and matches RFC 8291's example byte for byte; one push holds at most 3993 bytes, which `card` (200 characters) and `reply` (120) stay far below.
- **Subscribing** is a button on the app's Devices screen, since iOS asks for permission only on a tap and only in a Home Screen app. `POST /api/push {endpoint, keys: {p256dh, auth}}` (cookie) saves it against the session's passkey, at most 10 (409 past that); `DELETE /api/push {endpoint}` drops it. The endpoint must be `https`, with no userinfo and no port but 443, on `fcm.googleapis.com`, `*.push.apple.com`, `*.push.services.mozilla.com` or `*.notify.windows.com`, else 400: the daemon posts nowhere else, and checks again when it sends. Tests widen the list with a hidden `Config::push_hosts`.
- **Sending** (`push::spawn`) runs on a task of its own that opens the store and the key itself, so the router never waits. The POST carries `TTL`, `Urgency`, `Content-Encoding: aes128gcm` and `Authorization: vapid t=<jwt>, k=<key>`, follows no redirect and gives up after 10 s. A 404 or 410 deletes the subscription. Any other failure is logged once, with the push service's host and never the endpoint's path or a key (`shortcut: no retry; add one if pushes are seen lost`).
- **Cards.** `Router::push_cards` runs from `publish` and from the tick, so a card the gate stored off the loop goes out within a tick. It pushes each pending proposal whose id is above `pushed_up_to`, which starts at the newest waiting id when the daemon starts, so no card is pushed twice. The payload is `{"kind": "card", "id", "title": "zephyr: approve #7", "body", "quick"}` with `Urgency: high` and `TTL: 86400`. `body` is the class and the summary, facts-scrubbed as `zephyr.proposals` gives them, or the first line of a setting's or a command's card; the agent's reason is never pushed. `quick` is true only for a held `messages` or `posts` action that is not `strong`.
- **Typed approvals.** A `/ok N`, `/vault grant …`, `/memory ok`, `/job ok`, `/skill ok` or `/mcp ok` typed into the app's chat is answered `[zephyr] approve with your passkey: …` and does nothing: over the socket it would rest on the cookie alone. There is no list of such commands to keep: each handler that approves, grants, adds or undoes is told whether its caller may (`may_approve`, false on channel `web`) and refuses its own verbs, aliases included: `tools::decide` (`/ok`), `vault::command` (`grant`), `memory::command` (`/memory ok`, `undo`), `drafts::command` (`ok`, `add` and `undo` under `/skill`, `/skills` and `/mcp`) and `scheduler::command` (`/job ok`, `add`, `run`). `/no` and `/cancel` are taken, since they only take away. The one approval the cookie carries is the notification button below, for what any owner channel may approve.
- **Replies.** Without `[web]`, a `web` row left in the outbox is marked `failed` rather than kept for its week. The outbox flush pushes a `web` row once while no web socket is open: `{"kind": "reply", "body": <its first 120 characters>}` with `TTL: 3600`, no more than a Discord DM shows. The row stays pending and is shown when a socket next opens. A phone that froze the page without closing its socket stops answering pings, so the bridge closes the socket within two ping intervals and the reply is pushed rather than marked sent to nobody (`shortcut: the pushed set is in memory, so a restart may push a reply twice`).
- **`POST /api/push/decide {id, verb}`** (cookie) is a notification's button. It reads the proposal again at the click and takes `no` for anything that waits, and `ok` only for a pending held `messages` or `posts` action whose `strong` is false; anything else is 409 `open the app to approve this`, and so is a decision the router then refuses (paused, handled meanwhile), with the router's `{ok: false, text}`: the service worker opens the app on any answer that is not 2xx. It decides as `web`, so if a setting changed in between, `not_now` and `approve` still refuse anything strong: a lock-screen button never approves a payment or a loosening. A session may press 10 a minute.
- **`sw.js`** shows each push as a notification tagged `card-7` or `reply`. A card gets the buttons `[Approve, Deny]` when `quick`, else `[Deny]`; a button posts `/api/push/decide`, and a refusal there, or a tap on the notification itself, opens the app on `/#held/7` (iOS shows no buttons, so a tap always opens the app). Swiping a card away sends `no`, on Android only (`navigator.userAgent`): it can only refuse, and elsewhere a notification is also "closed" when the system clears it.
- Push trouble never touches the router. An unreadable key turns push off (`doctor` says so), and a clock hours off breaks the token's `exp`, which the push service's refusal shows in the log.

**The app** (`assets/web/`: `index.html`, `app.js`, `app.css`, `sw.js`, `manifest.webmanifest`, two icons) is plain ES2020 with no build step and no framework, phone-first; from 900 px the drawer is a side panel.

- **Text.** Everything the daemon sends goes onto the page through `textContent`, never as markup, with control and direction marks dropped for display (as the TUI's `view::clean` does). Two tests read the files: no `innerHTML`, `eval(` or inline script or style, and every method `app.js` calls is in `attach::WEB_METHODS`.
- **Sign-in.** "Sign in with passkey", and "Add this device" with the code and a name. `#enrol=CODE` fills the code and is then dropped from the address bar (`history.replaceState`).
- **Chat.** The status line is worded from `Snapshot.run` like Discord's progress note (`working · 0:24 · bash · 3 tools`), beside the `paused` and `N waiting` badges; a tap opens the drawer. The transcript comes from `zephyr.subscribe`: user turns with their channel, the reply streamed from `message_update`, a turn's tools folded into one line (`▸ 3 tools  bash, read ×2 ✓ 4.1s`), `zephyr_reply` as notices, code in `<pre>` with a copy button. The queue strip offers "take back" (`zephyr.dequeue`); the composer has an "after this run" toggle (`followUp`) and Stop (`abort`) while a run goes.
- **The drawer** opens on Approvals when something waits. *Approvals* lists `zephyr.proposals`, newest first, with class, summary, age and expiry; *Upcoming* lists `Snapshot.jobs` and the delayed (`scheduled`) actions. *Activity* is the daemon's own record (`zephyr.activity`, §4.19): each entry's `line`, tool calls muted, the next page asked for with `before: next` when the "older" row scrolls into view; above it the standing grants (`kind: "grants"`), each with a Revoke button that sends the grant's `revoke` as the owner's own command. A revoke only takes away (a remembered target forgotten, a job removed, a time limit ended early where going back is stricter by `settings::tighter`), so it goes over the cookie; a grant whose `revoke` is null says `set … back by hand` and has no button. A daemon that answers `-32601` gets no tab.
- **Goals** lists `zephyr.goals` (§4.3.1), and before it sends `/goal done N` or `/goal rm N` reads the list again and acts only if goal N still has the text that was tapped (else it reloads and says the list changed), since N is a position: the open goals by number, each with Done and Remove, then those done since the last review, struck through and with no button, since a done goal has no number (`n` null). A change is the owner's own command sent as a message (`/goal add TEXT`, `/goal done N`, `/goal rm N`): `goal` is not a strong setting, so it goes over the cookie, and its reply reloads the list. A daemon that answers `-32601` gets no screen.
- **The card sheet** shows the daemon's `card` in monospace. Its `the agent says: …` line goes into a closed `<details>`, "the agent's reason (not checked)": that line is safe to pick out, since every line but the first and the last starts with a label of the daemon's and agent text is only ever quoted inside one (§4.16). **Approve** and **Approve once** (shown only when `once`) are signed; **Deny** and **Cancel it** (for a delayed action) are not. The hash that is signed is of the card text as received, never the cleaned copy. An open sheet is never rebuilt: when a reload of `zephyr.proposals` no longer has its id with the same card hash, it greys out (`this card changed or was handled; close and look again`) and its buttons stop.
- **Settings** lists `zephyr.settings` by section, `label · value · source`; a row opens to an editor for its kind (a select, the `zephyr.models` list, or a field) with an optional time limit. A `strong` row is always signed ("Save with passkey"); a refusal shows the daemon's reason. **Private facts** (`zephyr.facts_list`) shows names, kinds and allowed targets, **Vault** (`zephyr.vault_list`) names, sites and grants; both point at the TUI or the CLI for changes, since no secret is typed on the phone.
- **Devices** (`zephyr.web_devices`): notifications on and off for this device, sign out, and remove a passkey (which sends `/web rm NAME`).
- **The socket** reconnects with a backoff of 1 s doubling to 30 s and subscribes again. Before each attempt the app asks `GET /api/push/key`, since a browser cannot read a refused upgrade's status: a 401 shows sign-in. A hidden app closes its socket, so replies are pushed, and reconnects when it is shown.
- Not automated: a real browser. README's manual check (iOS Safari as a Home Screen app, Android Chrome) is run before a release that touches `assets/web/`.

### 4.4 Autonomy and safety (tools run without asking, except the gated classes)

There are no per-call prompts, except for messages, posts and payments, which wait for the owner as far as the owner's approval modes say (§4.16). These hard limits hold every time:

1. **One Docker container, `zephyr`** (`zephyr up`, set up by `zephyr init`). Two users inside it:
   - **The agent** (every rpi child, and every process zephyr starts for it: `rpi auth refresh`, `rpi --list-models`, memory's git) runs as your uid, so files it creates are yours and no ACLs are needed.
   - **The daemon** runs as root holding only SETUID, SETGID and KILL (`--cap-drop ALL`, `no-new-privileges`, `--pids-limit 4096`). Without DAC_OVERRIDE, root is bound by file permissions like anyone else. Its own files live in `~/.zephyr-daemon` (root, 0700), seen as `/var/lib/zephyr`: `zephyr.toml`, `secrets.env`, `tui.token`, `host.toml`, `vault.toml` (§4.15), `facts.toml` (§4.18), `state.db`, the chat socket and the lock. The agent can neither read nor change them, so it cannot learn the bot tokens, rewrite the settings (dropping the policy plugin or adding an owner), or speak as the owner on the chat socket. Whatever the daemon does in the agent's home it does with the agent's file ids (`agent::fs`, setfsuid), so a symlink the agent plants leads nowhere new; a missed call site fails closed, since root cannot even enter `/zephyr`. `zephyr up` moves an older layout over once and gives the dir to root in a throwaway container; the host CLI then reads and writes those files through `zephyr __file` in the container, as root.
   - **signal-cli** (§4.3) is the one program root runs for a channel: a child of the daemon, as root, by full path, its environment cleared, on `<state>/signal` (0700), so its keys stay out of the agent's reach.
   - Before a child starts, secrets.env's variables are removed from its environment (`[agent] env` lets named ones through), and the daemon is undumpable.
   - **PATH.** The image's `ENV PATH` is root's and leaves out `/zephyr/.local/bin`, where the agent installs its own tools: on root's PATH, a `git` or `zephyr` the agent planted there (it owns `/zephyr` and can open its mode) would run as root at the next `docker exec zephyr zephyr status`, `/skill ok` or restart. Every process run for the agent gets `agent::AGENT_PATH` (`agent::cmd`; the host's agent execs pass the same). The image's `CMD` is `/usr/local/bin/zephyr supervise`, and root runs git and tar as `/usr/bin/git` and `/usr/bin/tar`. `doctor` fails when a directory on root's PATH, or one above it, is the agent's to write (`agent::writable_dirs`).
   - Left readable by the agent, by necessity: the provider credentials rpi itself reads (`accounts/*/auth.json`, the Claude config) and the conversation (`sessions/`).
   - **The image's provider sources** are build args of `deploy/Dockerfile`, pinned to commits: `RPI_PACKAGE_REPO`/`_REF` and `PLUGINS_REPO`/`_REF` (§4.7 says what each brings). An empty repo arg leaves that source out (`--build-arg RPI_PACKAGE_REPO= --build-arg PLUGINS_REPO=` builds the minimal image); an empty REF with a repo still fails, as `git fetch` does. The stages that build a source test the arg itself, never a file in the tree: with the arg set, a tree that lacks `Cargo.toml` or `stage.sh` fails the build rather than shipping an image without its providers. The defaults build the full set, so `zephyr up --build`, which passes no build arg, and the tag build make the same image as before. `zephyr.toml` still lists every image extension: rpi skips a path it cannot load, so the child starts (`tests/real_rpi.rs`), and `doctor` warns once per missing path (`…, or the image was built without it`). image.yml's manual `providers: none` builds and smoke-tests that variant as `:dev-minimal`, never pushed.

   The agent can work anywhere it is mounted:
   - Read-write: `~/.zephyr` (seen as `/zephyr`), which holds its memory, sessions and its own rpi agent dir with its own credentials.
   - Read-write: `$PROJECTS` at the same path as on the host. Secrets inside it (`.parity-env.sh`, `.parity-lanes/archive`, every `.env*` outside `node_modules`) are covered with empty mounts.
   - Nothing else of your home: `~/.ssh`, `~/.rpi`, `~/.pi` and browser profiles are not mounted. No docker socket.
   - Network: a user-defined bridge network named after the container, with `--hostname zephyr` (Docker writes the container's address under that name to `/etc/hosts`) and `--cap-add NET_ADMIN`. `supervise` uses the capability once, to load the agent's network floor with `nft` before the first daemon, and each daemon it starts has it dropped from its bounding set (`PR_CAPBSET_DROP` between fork and exec); the daemon checks its own `CapEff` at start and refuses to run while it still holds it. Only the attach port and the iMessage webhook are published, each on the host's `127.0.0.1`. The agent's uid reaches its own loopback and nothing else, so neither zephyr's listeners, the host's services, the LAN nor the tailnet (§4.20). `network = "host"` in host.toml goes back to host networking, where the agent can reach every service on the host's loopback, zephyr's own listeners included; those cap their connections (§4.3).
   - Providers come only from the image: `deploy/Dockerfile` builds `librpi_providers.so`, `libzephyr_cursor.so` (this repo, §4.7.2) and `rpi-claude-agent/` into `/opt/zephyr/ext/`, and `zephyr.toml` loads them with `extensions`. Do not `rpi install rpi-providers` into `~/.zephyr`. A package installed there loads twice (`zephyr doctor` warns).
   - No sudo for the agent: root in the container can read `secrets.env` and drop the policy plugin, and `no-new-privileges` blocks setuid anyway. The agent installs into its own home (§4.11). An apt package is the owner's call: `zephyr packages add NAME` keeps `packages = [...]` in `host.toml` (names checked against `^[a-z0-9][a-z0-9+.-]+$`, no trailing `-`, before they reach a shell) and builds `zephyr-local:<version>-<hash>` with `docker build -t <tag> -`: `FROM` the release image (or `ZEPHYR_IMAGE`) and one `apt-get install` on stdin. The hash is the first 8 hex digits of the sha256 of the base image and the sorted list, so it is stable and two named images never share one. `up` runs it (built when missing), `upgrade` builds it on the target image before the old container goes, so the packages survive upgrades, and `add`/`rm` build first (a name apt does not know saves nothing), then recreate the container once nothing is in flight, as `upgrade` does. `uninstall` removes every `zephyr-local` image. `__file` keeps running on the release image, which always exists beside its local one.
   - `--restart unless-stopped` replaces the systemd unit; `--init` reaps children and forwards SIGTERM.
   - The process tree is `docker-init` (tini, PID 1), then `zephyr supervise` (the image's `CMD`), then `zephyr run`. The supervisor (`supervise.rs`) starts the daemon again when it crashes, without restarting the container: backoff 1 s, doubling to 30 s, reset after 60 s healthy; 5 exits in 2 minutes and it gives up, so Docker's restart policy takes over. SIGTERM and SIGINT are passed to the daemon and nothing is restarted after them, so `docker stop` stays a clean stop. A daemon's re-exec uses `/proc/self/exe`, the binary actually running, so a file replaced underneath it (a build) cannot make the re-exec fail. When the daemon dies, its `exec` processes are re-parented to tini, which keeps and reaps them, and the next daemon adopts them (§4.13). Its rpi children would outlive it too, holding their sessions open so the new daemon could not resume them (rpi refuses a session already open in another process). So each rpi child leads its own process group, and a daemon starting up first ends any rpi a previous one left behind (`rpc::kill_leftovers`): matched exactly by this `rpi` binary, `--mode rpc`, this `--session-dir` and the agent's uid; a whole group only when the process leads it, so a leftover from an older build in the supervisor's group is ended alone.
   - Not systemd in the image: it would need `CAP_SYS_ADMIN` or `--privileged`, a writable cgroup and tmpfs mounts, undoing this item's hardening; its user manager would let the agent's uid make units that outlive everything, the kind of persistence `/job ok` exists to stop (§4.5); and it dies with the container anyway.
   - The GPU, when Docker has the NVIDIA runtime: `--gpus all` with `NVIDIA_DRIVER_CAPABILITIES=graphics,utility`, for the browser's WebGL (§4.11). The agent keeps no supplementary groups (`agent::init_ids`), so it reaches the card only through the world-writable `/dev/nvidia*`, which is all Vulkan needs.
   - Chromium's own sandbox cannot start under `--cap-drop ALL` and `no-new-privileges`, so the browser runs with `--no-sandbox`: the container is its sandbox, as it is for every other process the agent starts.

   This replaced an earlier dedicated Linux account: ACLs over 2.2M files were slow to apply and, on eCryptfs, unreliable to remove.
2. **Policy plugin `gw-policy`** (cdylib, published `rpi-plugin-sdk`, loaded with `--extension`). Its `ToolCall` veto blocks, for `bash` and for main's `exec` alike (§4.13):
   - destructive patterns, as in Hermes's hardline list: `rm -rf /`, `mkfs`, `dd of=/dev/`, fork bombs, `curl | sh`
   - writes outside the granted roots
   - `git push --force`
   - package installs outside the workspace venv/node dirs
   - credential files (`auth.json`, `.credentials.json`, `secrets.env`), `/proc/*/environ`, `.ssh/`, `.git/hooks/` and `.git/config`, named in any tool's path or any bash word. A hook in a project would run as the owner, on the host, at their next commit.
   - git settings that run a program or pull in another config file, however they are passed (`git config KEY`, `-c`, `--config`, `--config-env`; key names case-insensitive): `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `core.pager`, `core.editor`, `core.askpass`, `diff.external`, `credential.helper`, `gpg.program`, `sequence.editor`, `include.path`, `includeIf.*.path`, `filter.*.clean|smudge|process`, `diff.*.textconv|command`, `merge.*.driver`, `gpg.*.program`. A blocklist, so another key may get through; the uid is the boundary. This is a name check, so a glob or an encoded name gets past it: the boundary is the agent's environment and uid (item 1), not this list.
   - the approvals gate's own parts (§4.16), named in any tool's path or bash word: the real agent-browser (`/opt/zephyr/libexec/…`, or `ZEPHYR_AGENT_BROWSER`, which names it) and `ZEPHYR_GATE_SOCKET` (which would name another gate). Also an `mcp_call` that names no server or tool, which the gate could not class. A name check like the rest: a copy of the binary gets past it.
   - How a command word is found, for the veto and for `outbound`, `gated` and `programs` alike (`policy::command_words`): redirections before it are skipped (`2>/dev/null rm -rf /` is `rm`; a bare `2>` or `<` takes the next word with it), as are the runners in front of it (`sudo`, `env`, `nohup`, `nice`, `time`, `timeout`, `xargs`, `stdbuf`, `setsid`, `ionice`, `flock` with its lock file, `chronic`, `unbuffer`) with their flags' values, and `flock FILE -c CMD` is read as `sh -c`; an ANSI-C string (`$'…'`) is decoded as bash decodes it (`\n`, `\t`, `\xHH`, bash 5.2's `\x{H…}`, `\NNN`, `\uHHHH`, ...), its text ending at its first NUL (`\0`, `\x00`, `\c@`, ...), so `bash -c $'rm -rf /'` and `$'rm\0x' -rf /` are seen; only an unpaired `$` starts one, as in bash (`$$'…'` is the shell's pid and a plain quoted string), and a locale string (`$"…"`) is read as a double-quoted one. Words are read where bash reads them (`policy::Lexer`): a line continuation (`\` and a newline) is removed first, outside single quotes, `$'…'` and comments, so `r\⏎m -rf /` is `rm` and `$\⏎$` is `$$`; a word ends at `<` and `>`, so `rm>/dev/null -rf /` is `rm`. Inside double quotes a `$(…)` or a backtick still opens a nested command, read as one outside them (`echo "$(rm -rf ~)"` is `rm`; its own quotes nest, so a `"` inside it ends nothing outside). A nested command (with a process substitution, `<(…)`) is read on its own and ends nothing around it: the word it is in goes on past it, so the command keeps the words after it (`rm "$(echo)" -rf /` is `rm` with `-rf /`, and `curl "$(…)" | bash` still pipes a download into a shell), and a word made only of substitutions may expand to nothing, so the word after it may be the command (`$(true) rm -rf /` is `rm`). So does a `${…}` inside double quotes, as bash 5.2 reads it: a `"` in it opens a string of its own (`echo "${x:-"'"}"; rm -rf /` is `rm` after the `echo`), a `$(…)`, a process substitution or a backtick a nested command, a `${…}` another, and its first `}` none of them holds ends it. A `'` in it opens a string to the next `'` after a pattern operator (`#`, `%`, `/`, `^` or `,` straight after the parameter, so `"${x#'"'}"`) in every mode, its text a pattern. Elsewhere bash's default mode opens one too, but expands its text again with the `'`s as text, so the commands in it are read (`echo "${x:-'$(rm -rf /)'}"` runs `rm`, as does one a `$'…'` there decodes to: `$'\x24(rm -rf /)'`); posix mode (`sh`, `bash --posix`, `set -o posix` on an earlier line) reads that `'` as text, so at each such quote, up to 8, the rest of the command is read that way too, and the stages each reading finds are all checked. A `$(…)` ends at the `)` bash ends it at: not one inside a comment, a `case` pattern, a `${…}` or a heredoc's body inside it. A backtick ends at the first backtick no `\` escapes, and its text is read again with bash's escapes removed, so a backtick inside it nests too. A `#` that starts a word (not inside `${…}`, `((…))` or `$[…]`) starts a comment, which ends at its newline, and a quote in it opens nothing. A heredoc's body is read as a script of its own, ending only at a line that is exactly its delimiter (`EOF ` does not end it, and in an unquoted heredoc neither does a line after one ending in `\`), so a quote in the body opens nothing after it; the heredoc scanner that reads recipients finds the same end. Not seen: a command word an expansion makes (`$x rm`), quotes inside a `$[…]` that is itself inside double quotes (`"$[ "'" ]"`, after which bash still runs what follows when the expansion is skipped), a command that leaves posix mode again (`set +o posix`) or enters it after the 8th such quote; `gated`'s de-quoted copy still backs these up. A path in a name check is read as written and with `.` and `..` resolved, so `/opt/zephyr/../zephyr/libexec/agent-browser` is still the real browser.

   The plugin also asks the approvals gate (§4.16) before a call runs: a `bash` command that `policy::gated` classes as a message, a post or a payment, or that `policy::outbound` lists (for the private facts, §4.18), and every `mcp_call` (the owner's connector classes are the daemon's to apply). It sends one request on the gate socket and waits at most 5 s; only `{"verdict": "allow"}` lets the call run, and no socket, no answer, a malformed one, a hold or a deny blocks it, as every veto fails closed. rpi shows the model only its own line for a vetoed call (`` extension `libzephyr_policy` blocked tool `bash` ``), so the daemon steers in what the hold means. Main's `exec` is decided in the daemon, which runs it, never in the plugin.

   The daemon, not the plugin, writes the audit (item 6).
3. **Untrusted content and what leaves.** Text the agent reads is not wrapped in `<untrusted>` tags: the plugin cannot rewrite tool output, and wrapping only lowered attack success from 57.7% to 41.7% in AgentDojo (Table 5). The agent's egress goes only through the daemon's proxy, to public addresses on ports 80 and 443 plus the owner's `network.allow` entries (§4.20). That closes loopback, private ranges, cloud metadata and raw protocols; it does not stop a leak to a public HTTPS host, and an egress allowlist of hostnames did not lower attack success in ClawSafety (NemoClaw, 45.8% vs 40%), because most leaks went into normal replies. The exceptions are the gated classes: a message, a post or a payment goes through the approvals gate (§4.16), and every call that sends data out is checked for the owner's private facts (§4.18), beside this list. For the rest the owner sees what left: the daemon reads each bash `tool_execution_start` from rpi's event stream and, after the turn, lists every command that sent data off the machine (`zephyr_policy::policy::outbound`: curl/wget with a body or a non-GET method, ssh, scp, sftp, rsync to a host, nc, socat, telnet, `git push`). Plain GETs are not listed, though a URL can carry data too (CaMeL §7). Each command that list names is also an `audit` row (item 6) from the moment rpi starts the call: `tool = 'outbound'`, its label as the args (scrubbed of vault and fact values), and the call's own outcome (`started`, or `refused` when the policy vetoes it), so a run the daemon dies in still leaves it. The row is confirmed by the call's end, never by its start: `sent` once it ran, `held` when the gate holds it (the plugin's block, or main's `exec` held in the daemon), `refused` when the gate denies main's `exec`, `error` when it failed or the plugin blocked it; one whose end never came stays `started` and reads `unconfirmed`. The notice is unchanged. The stream is advisory, not proof: the agent shares rpi's uid and could write frames into rpi's stdout through `/proc/<pid>/fd/1`, so what it reports (the outbound list, a run's tool counts) can be forged by a hostile agent; nothing that grants authority is read from it except proposals, which still need the owner's `/ok`.
4. **Budgets.** Daily token and cost limits, summed from the `usage` on each assistant `message_end` event. rpi 0.15.0's `get_stats` totals count only usage that extensions record, never the replies' own, so they stay at 0. When a limit is hit, the gateway pauses and notifies you. Per run, `[budget] run_turns` (model turns, counted from `turn_end`) and `run_minutes` stop a main-session run with `abort` and tell the owner `[zephyr] stopped the run after …` once it settles; jobs and background tasks (§4.12) get `run_turns` too, and their fixed 30-minute cap (`JOB_TIMEOUT`) instead of `run_minutes`. Both are off unless set.
   - **Stalls**, always on (Hermes's stall monitor). A run with no rpi event for 10 minutes, or 20 while a tool call is in progress, is stuck: main's run is aborted and the owner told `[zephyr] stopped a run that made no progress for 10 min` (`cap_run`; a child that then never settles is killed, §4.2), and a task's or job's run ends `failed: stalled` (`scheduler::follow`). Two limits because rpi 0.15 sends no progress while a silent command runs: `sleep 30` in `bash` gave `tool_execution_update` only at 0 s and 30 s.
   - **Repeated failures**, always on (OpenClaw's loop detection, done in the daemon because a plugin veto shows the model no reason). `rpc::Tally` keeps a streak keyed on the tool, its args and the first line of the error, from `tool_execution_start` and `tool_execution_end` with `isError`; any other result ends it. At 3 in a row the router steers in `[zephyr] <tool> failed 3 times in a row with the same error (<line>). Don't retry it unchanged: change approach, or stop and tell the owner.` It is kept out of `reconcile`'s idea of the run's request, and if the run settles without reaching it, the settle takes it back with `clear_queue` as it does the resume note. At 5 the run is aborted and the owner told `[zephyr] stopped a run that repeated a failing <tool> call 5 times` (`cap_run`). A task's or job's run gets the same note, and at 5 ends `failed: stopped: repeated a failing <tool> call 5 times` (`scheduler::follow`).
5. **Kill switch.**
   - `/stop` from any owner channel aborts the run.
   - `/pause` stops all dispatch and scheduling until `/resume`.
   - `rpi-gateway pause` does the same from a shell.
   - `docker stop zephyr` is the hard stop.
6. **Audit.** Inbound and outbound messages are rows in `state.db`. Tool calls go to its `audit` table (schema v14), written by the daemon from rpi's event stream for main (`Router::tapped`) and for tasks and jobs (`scheduler::follow`): each `tool_execution_start` as `started`, or `refused` when `zephyr_policy::policy::check` denies it, and each failed `tool_execution_end` as `error`, with the session, the tool and its arguments scrubbed of vault values and cut to 500 bytes. The approvals gate's decisions and the owner's answers are rows too (§4.16), scrubbed of fact values as well. Kept 90 days, as are finished job runs (`runs`), tasks and processes (`procs`), with two guards: each job's latest run always stays, since `claim_due` dates a job's next time from it and a one-shot job would otherwise fire again, and each table's highest id always stays, since SQLite would reuse it and a new report keyed `task-<id>` or `proc-<id>` would be dropped as a duplicate of an inbox row from before. The plugin's own `$ZEPHYR_AUDIT_LOG` is optional and off in production: it would be written as the agent's uid. The table is as trustworthy as the event stream (item 3).
7. **The agent's text is marked.** A line of the agent's reply that starts with `[zephyr]` goes out as `[agent]`, so the agent cannot pass for a daemon notice (to bait an `/ok N`, say); the vault's request notice quotes the agent's reason as `The agent says: "…"` on one line; and `/ok N` answers `[zephyr] /ok N approved <command>` in the daemon's words before the command's own output. A held action's card (§4.16) is the daemon's words, built from the call; what came from the agent or a page sits on a labelled line of its own, quoted.
8. **Start failures.** A child that fails to start three times in a row is told to the owner once (`[zephyr] the agent cannot start: <why>; messages wait`), to the sender of the oldest waiting message or else the last owner; a start resets the count.

### 4.5 Scheduler and proactivity

- Jobs live in `state.db` (cron expression or one-shot time, prompt, granted dirs, delivery channel). Create them with `/job add …`. The agent's `schedule` tool (§4.11) only proposes one: it is stored with `enabled = 0`, the owner is shown its schedule and prompt, and it runs after `/job ok N` (`/job rm N` drops it). An approved job counts from its approval, not its proposal, so a daily job approved late does not run at once. A job is a standing instruction, so it gets the same human gate as memory (§4.6): an injected page cannot leave one behind.
- A tick every 30 s claims due runs in a transaction:
  - `runs(claimed → running → completed|failed|unknown)`
  - On restart, `running` becomes `unknown` and is reported, never retried automatically.
  - Missed runs are skipped, except one catch-up run per job after downtime.
- A run's output is delivered to its channel, unless the reply is exactly `[SILENT]`.
- A heartbeat is just a job: for example "every 30 min: check inbox/todo, reply `[SILENT]` if nothing to do". It is off by default.
- A job counts from its last run, or from its creation or last move, whichever is later (`claim_due`): `set_job_schedule` dates the job, so a schedule moved to a time earlier today than now fires next at the new time, not at once.
- **The daily review** (`review.rs`) is a built-in job, off by default, on when the registry setting `review.at` is `HH:MM` (in `timezone`; `[review] at` in `zephyr.toml`). `review::sync`, at the scheduler's start and at each config change, keeps one `jobs` row with `builtin = 'review'` (schema v17), name `review`, schedule `M H * * *`, made (counted from now), moved or removed (`review.at none`; while a review runs its row is only turned off, and goes when that run ends); a failure is logged and `doctor` warns while `review.at` is set and the row is missing. From then on it is an ordinary run on the job ledger: claimed, `unknown` after a crash and reported, one catch-up after downtime. Before a review run the row is pointed at the channel the owner last used (`last_owner`), so the run's output and an interrupted run's report go where the block goes; with no owner yet the run is `failed` (`no owner to send the review to`) and nothing is sent. The daemon composes and sends, with no model, `[zephyr] daily review, Mon 9 Nov`, `Goals` (numbered, or `no goals; add one with /goal add <text>`), `Done since the last review: TEXT (you, HH:MM), …` (from `settings_log`; `proposed as #N` for an approved proposal), `Activity since HH:MM` (the activity record, §4.19: at most 50 records, every kind but `tool`, as `/activity` shows them, cut at 3000 characters), `Memory` (`memory::digest`, or `no changes`). It counts from the last completed review's due time, else 24 h ago. With no goals, no activity and no memory change nothing is sent. Only when there are goals does the model run, in `job-<id>-<run>`, on the block and `review::PROMPT` (at most 10 lines: per goal, what moved and one next step; no work, no memory change; `[SILENT]` if nothing useful); with none the run is `completed`, `[SILENT]`, with no model call. As in any job, `gateway` and `task` answer `not available in scheduled runs`. `/job list` shows it as `#5 review (built-in, review.at 21:30)`, `/job run 5` runs it now, and `/job rm 5` and `/job ok 5` answer `[zephyr] job #5 is the daily review; /set review.at none turns it off`; the agent's `schedule` tool cannot make a built-in row.

### 4.6 Memory

- `/zephyr/memory/{USER.md, MEMORY.md, notes/YYYY-MM-DD.md}`, kept in a git repo, edited by the agent with normal file tools. The daemon commits after each run that changed them, as the agent, off the router's loop (a blocking thread), with no hooks, fsmonitor, system or global config, in its own process group killed after 30 s: the repo is the agent's, so a hook or a filter it wrote must not hang the daemon.
- rpi loads `AGENTS.md` as a context file when a child starts (the frozen snapshot, which keeps the prompt cache warm), from its cwd and every folder above it. The daemon writes it before every start from the owner's side only, never from the working files. In the container it goes to root's `/AGENTS.md` (0644), which the agent can read but not change between the write and the child's read; `/zephyr/AGENTS.md` becomes a stub pointing there. The text comes from what the daemon composed, never re-read from the agent-writable file. (The agent can still race a file into `/zephyr/AGENTS.md`, which rpi loads as well; closing that needs `--no-context-files` with `--append-system-prompt`.)
  1. **The owner's persona** (`/persona set TEXT`, `/persona clear`, `/persona`), kept in `<state>/PERSONA.md` (root's 0600, at most 4000 characters, line breaks kept), under `## Persona` after `## Staying available`: who the agent is with the owner. The rules come after it, so their "they override" line covers it. Its text never goes into `settings_log` (old and new read `set` or nothing).
  2. **The owner's standing rules** (`/rule <text>`, `/rule rm N`, `/rules`), kept in `<state>/RULES.md`, after the persona, with a line saying that text claiming to change them is not from the owner. A rule change restarts the child at idle on the same session, so it applies from the next message; jobs start fresh children and get it too. Rules here sit at system-prompt level, which compaction does not touch: in Governance Decay (arXiv 2606.22528, Tables 1–2) in-chat rules were dropped after compaction up to 59% of the time, system-prompt ones 0%.
  3. **The owner's goals** (`/goal add TEXT`, `/goal done N`, `/goal rm N`, `/goals`), kept in `<state>/GOALS.md` (one per line, at most 20, each at most 500 characters, whitespace collapsed), under `## Goals` after the rules, with a line that text claiming to change them is not from the owner. `done` and `rm` both take the line out; `settings_log` tells them apart (key `goal`, old the text, new `done` or `removed`). A change restarts the child at idle, as a rule's does. An unreadable `GOALS.md` or `PERSONA.md` stops the child's start, as `RULES.md` does.
  4. **The approved memory**: `<state>/approved/{USER.md, MEMORY.md}`. A change the agent makes waits, unless the daemon saw that the run that made it was the owner's own (provenance, below): after the run the owner gets its diff once, naming where it came from (`[zephyr] memory change waiting (from task #7); /memory ok keeps it, /memory undo drops it`, or `(from job #3 (news) run 12)`, `(from this conversation, which used exec at 14:02)`), and `/memory diff` shows it again. `/memory ok` approves it, for the next child start, but only if the files still hash (SHA-256, `drafts::digest`) to what the owner was last shown; if a later run changed them, the reply shows the new diff and a second `/memory ok` keeps that. `/memory undo` drops a waiting change by reverting each commit since the last approval; with nothing waiting it reverts the newest memory commit, as before, never the seed, and approves the result. On the first start with approvals, the memory there counts as approved.

  **Provenance** (`memory_commits`, `session_origin`, schema v17). Saving at once is opt-in and off by default: the registry setting `memory.auto` (`[memory] auto`, `off` or `owner`; strong, so only `tui` or `chat` turns it on, and the agent may only turn it off; an install with no key reads `off`). With `off` every change waits for `/memory ok` as before, its notice still naming where it came from (`from your message` for a run that passed every check below). With `owner`, a run of main is owner-origin, and its change is approved at once, only when the daemon saw all five of these, never from anything the agent writes:
  1. *The conversation is clean.* `session_origin(session, tainted, at, file)` holds one row per rpi session id; `/new` (`new_session`, not `switch_main`, so `/switch` back never cleans) inserts the new id clean. A session with no row (every conversation from before v17, every task's and job's) counts as tainted. The first taint writes its reason, as the phrase after "which" (`used exec at 14:02`, `took in task #7's report at 14:05`), and is never cleared: text a run read stays in the conversation and its compaction summary, so `/undo` and `/compact` do not clean either. A fresh install's first conversation starts clean. The saved conversation is the agent's to write, so a clean one is watched, under one invariant: auto-save is allowed only if, from the run's start to the commit under the memory lock, no process of the agent's existed but the daemon's own tree (the desktop on root's config among it) and the run itself ran nothing, and every record of the saved files is made from the exact bytes that were checked. `session_origin.file` records its files (`rpc::SessionPrint`, as JSON: how many, the newest one's path, and for it and its `.progress.jsonl` the length, inode, change and modification times and SHA-256 of the bytes read between two looks that agree; a file whose length, inode and both times are as recorded is not hashed again, unless it was hashed within a second of its last change, since file times tick coarsely and the change time cannot be set back). A window opens (`open_window`) with a look for strays of the agent's, any of which taints it at once (one that ends before the window closes would go unseen there), then a check (`check_session`): at each run's start (before `prompt`, `resume_pending` or `compact` is sent), before a child loads it (a restart, a `/switch`) and before each idle command that writes it (`set_model`, `set_thinking_level`, `navigate`, a restart's stop). A difference, a file where none was recorded, or a file that is a link, a folder or unreadable taints it (`was changed on disk outside zephyr at 14:02`); a match records the fresh print, unless not even the hash was taken again. The window closes after rpi wrote (a run's settle, a child's start, a stop, an idle command): when other work of the agent's ran or runs since it opened, or a stray of its lives, it is tainted (`was written while other work of the agent's was running`, or the stray named, with `/stop` and `/new` as the cure); else the file must be the one recorded with lines added after the bytes hashed (or, from no file, rpi's first, read once: `SessionPrint::follow`), and the print of exactly those bytes is recorded; a file unchanged since it was hashed, by the same rule as above, is not read again. A taint at the settle takes the run's trust with it, so its memory waits. A stray seen at a run's start taints the conversation then, since it may end before the settle. A settle of a run zephyr did not see start saves nothing at once and leaves the conversation as it is. A record that cannot be written taints it too. `/new` names the conversation `main-<unix seconds>`, past any id zephyr already gave one (two `/new`s in one second make two conversations); one whose file is already there starts tainted (`was already on disk when /new made it`).
  2. *Every row the run took in is the owner's.* An allowlist: a row is the owner's only when the router wrote it from an owner on a channel (`insert_inbox_as` marks it, `inbox.owner`, schema v17), and that sender is still an owner; a `/retry` row is as much the owner's as the row it retries. Any other row (a task's or process's report, a held action's result, anything zephyr writes) taints before `dispatch_new` sends it, as a prompt or a steer, named by its platform id when zephyr knows it (`took in task #7's report`) and `took in a message zephyr wrote` otherwise. Crash re-sends and the daemon's own steered notes do not taint.
  3. *Every tool call is on the clean list*, judged at `tool_execution_start` by main's `rpc::Tally` (`Tally::main`): `read` and `edit` of exactly `memory/USER.md` or `memory/MEMORY.md`, `write` of a file under `memory/`, each path plain folders down to a plain file (a `write` may make one; a link anywhere on it is off the list). The path is taken relative to the home when absolute; `~`, `..`, `.`, an empty part or any dot-named one (`memory/.git/config`) is off the list. Any other call taints, success or not: `exec`, `process`, `recall`, `gateway`, `task`, `vault`, `mcp_*`, a `read` of anything else, a file the owner sent (`inbox/…`) included, since an image or a PDF can carry instructions. The router writes the taint at once, so a crash cannot leave the conversation clean; a failed write is logged and kept in the router's memory for that session, so neither this run nor a later one is the owner's. At start, a `dispatched` row (a run in flight when the daemon stopped, whose events it may never have read) taints main's conversation `was cut off by a restart at HH:MM`; when main's conversation cannot be read then, no run of main is the owner's until the daemon starts again. A child that dies mid-run taints the conversation it was in (`was cut off when its agent stopped at HH:MM`), and the dead run's taint and trust are dropped, never carried into the next run.
  4. *Nothing else could have written memory.* At the run's start (before the saved conversation is checked) and again at its settle (asked under the memory lock, right before the commit reads the files), no job run, task or `procs` command is running or started since the run began (`Store::writers_since`, at second granularity, so a doubt waits), and no process of the agent's lives outside the daemon's own tree (`Procs::stray`, the same search `/stop`'s `kill_strays` makes): only what descends from the daemon (the desktop it started among it) or a tracked command is spared, whatever a process is named or where its parent chain ends, so a `setsid` left from an earlier conversation, the agent-browser daemon (owner confirmed 2026-11-10), a desktop a crashed daemon left and a shell the owner opened as the agent under `docker exec` (doctor's brief `__netcheck` too) all count; and a `/proc` that cannot be listed, an entry that cannot be read for any reason but having ended, or a parent chain that breaks counts as one. Anything the desktop started but its own programs (`Xvfb`, `xkbcomp`, `openbox`) is a stray too, and openbox reads root's `/opt/zephyr/openbox/rc.xml` (`deploy/openbox/`: no key bindings, an empty menu, nothing to start), never the agent's `~/.config/openbox`; without that file there is no window manager. Once, at its start, the daemon ends desktop programs left over from a daemon before it (reparented to pid 1; one under a `docker exec` is left running, a stray all the same), so the one in use is always its own child. A stray seen when a run starts taints the conversation then, since it may end before the settle: the run's notice names it, and the cure is `/stop` (which kills every stray this check counts) and then `/new`: `(from this conversation, which was open at 14:02 while the agent's browser was still open; /stop closes it, then /new starts clean)`.

  **What `memory.auto owner` cannot see**, and why it is off by default: a program the owner starts as the agent's uid outside the daemon (a `zephyr shell`, which sources the agent's `~/.profile`; `docker exec -u agent x11vnc`, which reads `~/.x11vncrc`) runs what the agent left there, and is a stray only while it lives; the desktop's programs are spared by their command names under the daemon's tree, so on a host where `kernel.yama.ptrace_scope` is 0 an agent process can attach to one and run code as its child's parent. Leave it off where either applies.
  5. *The base was approved.* At the run's start the working files equal the approved ones and nothing is uncommitted (`memory::clean_base`, the HEAD then); commits that touched only `notes/` do not count, so a job's note never blocks it. Memory as it lies must be what zephyr made (`memory::untouched`, an allowlist read directly, never through git, under the memory lock before any git call, at the start and right before the settle's commit): `memory/` and everything in it plain folders and files, no link (`your message, but memory holds a link or something that is not a plain file`); no `.gitattributes` and no `.git` below the repo's own; and `.git` holding only what `git init`, `prepare` and zephyr's commits, undos and squashes make (`HEAD`, `config`, `description`, `index`, `objects` without alternates (looked at only at its top: two-hex loose-object folders, `pack`, `info`), `refs`, `packed-refs`, `logs`, `info/exclude` and `info/refs`, `COMMIT_EDITMSG`, `ORIG_HEAD`, `hooks` with git's samples only, `branches`), its config only the `core` basics, `user.name` and `user.email` (`your message, but memory's git setup was changed`). Either failure waits and is told to the owner, in digest mode too, even when nothing differs. The programs the daemon runs as the agent here and beside a run (memory's and the checkpoints' `git`, the desktop's `Xvfb` and `openbox`, a sign-in's `script`) are named by full path, never looked up on the agent's PATH, whose `~/.local/bin` is the agent's to fill. At the settle, under the memory lock, the run's commit must be the one new commit on that base (HEAD's only parent).

  Then `commit_if_changed` approves the working files and tells the owner `[zephyr] memory saved from your message; /memory undo drops it:` with the diff (nothing for a notes-only change), and the child restarts at idle so the next message sees it. When check 5 fails at the settle the change waits `(from your message, but another run wrote memory meanwhile)`; when check 4 does, `(from your message, while other work of the agent's was running)`; with a change already waiting, `(from your message, on top of a change still waiting)`; on a conversation with no row, `(from a conversation from before zephyr kept track; /new starts a clean one)`. Jobs, tasks and the review are never owner-origin: their changes always wait. `memory_commits(sha, at, origin, auto)` records each commit zephyr makes, with that origin; it, not the agent's git log, is what the daemon trusts (commit messages stay `memory: <utc time>`), and it is pruned at 90 days. Undoing a saved change is `/memory undo` with nothing waiting. AGENTS.md's `## Memory` says so: what the agent writes reaches the context after the owner approves it; when the owner tells it something to remember and it only reads and edits `memory/USER.md` and `MEMORY.md`, zephyr saves it at once; and a rule the owner states in chat is not enforced until it is a `/rule`, so the agent says so and offers to propose it with `gateway "/rule TEXT"`.

  **Digest mode.** `memory.notify = digest` (`[memory] notify`, default `each`) stops the notice after each run: `commit_if_changed` neither tells nor marks the change shown (a change saved at once is still saved). Not marking it matters: `/memory ok` keeps only what was shown, so an owner who types it before the review is shown the diff first, as before. The daily review's `Memory` part (`memory::digest`) lists every `memory_commits` row since the last review, one line each (`- 14:02 a1b2c3d saved, from your message`, `- 15:30 e4f5a6b from task #7`), then `Waiting (/memory ok keeps it, /memory undo drops it):` and the diff, which it marks shown, so a `/memory ok` after the review keeps it without a second ask. `Config::validate` refuses digest with no `[review] at` (`[memory] notify = "digest" needs [review] at: the digest goes in the daily review`), in either order of edits, so no change goes untold.
  **`/forget TEXT`** (the owner's, at least 3 characters, compared in lower case with whitespace collapsed), under the memory lock: what is uncommitted is committed first, and while a change waits it is refused (`[zephyr] a memory change is waiting; /memory ok or /memory undo it first, then /forget`: the waiting change may be the very thing to forget, and a later undo would bring the lines back). Every line holding TEXT goes from `USER.md`, `MEMORY.md` and `notes/*.md` (as the agent), in one `memory: <time>` commit that is approved at once and recorded in `memory_commits` as `you (/forget)`, saved; TEXT goes in no commit message, log line or row. The child restarts at idle. The reply lists the lines, file by file (`[zephyr] forgot 2 lines (commit a1b2c3d); /memory undo puts them back:`), then where the text still is: the memory's git history, past conversations (recall), state.db's message log and audit and its backups, other files in `/zephyr`, the model provider's logs, and lines that say it in other words; and when a rule, a goal or the persona holds TEXT, `Also in your rules (/rules), …, which /forget does not change.` Nothing found: `[zephyr] no memory line holds that`.
  **`/memory squash yes`** (bare `/memory squash` explains and asks for `yes`), refused while a change waits: as the agent, `checkout --orphan`, a `memory: <time> squashed` commit of the files as they are, `branch -M` onto the old branch's name (up to here a failure checks the old branch out again and deletes the orphan, so nothing changed), then every other ref deleted (`for-each-ref`, `update-ref -d`), `ORIG_HEAD` and `FETCH_HEAD` removed, `reflog expire --expire=now --all` and `gc --prune=now`; the result is approved and every `memory_commits` row deleted. The new commit is the root, so `/memory undo` stops there. A failed `gc` is reported: the old commits are unreachable but still on disk until the next one.

  Why a human gate rather than a scanner: an agent that writes its own memory saved fabricated memories planted by one web page above 97% of the time on frontier GPT models, retrieved them in 60–89% of later sessions, and every model tested acted on them (Sleeper Memory Poisoning, arXiv 2605.15338); pattern and LLM-trust filters let poisoned entries through (arXiv 2601.05504 §8.2).
- rpi 0.15.0 loads the first of `AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, `CLAUDE.MD` from the agent dir and from each dir up from the cwd, so an agent that wrote `AGENTS.override.md` or `CLAUDE.md` in `/zephyr`, or `AGENTS.md` in its agent dir, would get around both rules and approval. It also reads `SYSTEM.md` (which replaces its own system prompt) and `APPEND_SYSTEM.md` from `/zephyr/.rpi/` and from the agent dir. Before each start the daemon renames any of those to `<name>.ignored-by-zephyr` and logs it.
- Two more sources are closed on the child's command line. `--no-skills`: skill descriptions go into every prompt, and the agent can write skills under `/zephyr/.rpi/skills` or its agent dir. `--approve`: rpi skips `AGENTS.md` for a cwd that `trust.json` marks `false`, and the agent can write that file too. `--local-only`: rpi otherwise also loads extensions from `/zephyr/.rpi/extensions`, the agent dir's `extensions/`, project packages and the `extensionDirs` setting, all writable by the agent; an extension can rewrite the system prompt (`before_agent_start`) or shadow a provider, and it loads before the policy plugin. With the flag only the `--extension` files zephyr passes (the policy plugin and the image's providers) load. The image also ships `rpi-mcp-adapter` (`librpi_mcp_adapter.so`), which is loaded by default: its `mcp_list`/`mcp_call`/`mcp_resource`/`mcp_request` calls are audit-logged like any other, and the policy plugin denies a `configPath` (or path) that names a credential file, so MCP cannot read `auth.json`, `secrets.env` or an ssh key. They may also use only the approved connectors (below).
- `AGENTS.md`'s order: `## Staying available`, `## Persona` (when set), `## Owner's standing rules`, `## Goals` (when any), `## Tools`, `## Settings`, `## Approvals`, the skills, connectors and subagents (`drafts::prepare`, which looks for the `## Memory` heading only after `## Approvals`, so a persona holding one cannot move them), `## Memory`.
- Between the rules and the memory, `AGENTS.md` carries a fixed `## Tools` block: how to use the browser, the desktop, `send_file` and `schedule` (§4.11). It is compiled into the daemon, so the agent cannot change it either.
- **Skills and connectors** go through the same gate as memory (`drafts.rs`): the agent proposes, the owner approves, and only approved content reaches the context.
  - The agent writes drafts: `/zephyr/skills/drafts/<name>/` (an agentskills.io `SKILL.md` whose YAML frontmatter has `name`, equal to the folder, and a one-line `description`, plus any files beside it) and `/zephyr/connectors/drafts/<name>.json` (one server spec in `[[mcp]]`'s shape). After each run (main, task or job) `drafts::scan` sends the owner each draft that is new or changed since last shown, once: the diff against the approved version, or the whole text, cut at 1500 characters (`[zephyr] the agent drafted a new skill tea; /skill ok tea approves it, /skill no tea drops it`). A draft that fails the checks is told once, with why. The shown hashes are in `<state>/drafts-shown.json`.
  - `/skill ok NAME` and `/mcp ok NAME` approve only if the draft still hashes to what was shown (SHA-256 over length-prefixed paths and contents, so no draft can be made to collide with the one shown; a fingerprint stored in the older 64-bit form just shows the draft again); otherwise the reply is the new diff, as for `/memory ok`. Checked at approval (a trust boundary): the name is `[a-z0-9-]{1,64}`; a skill holds regular files only (no symlinks, and no `.git` at any depth, in any case: root's git would read it as an embedded repo with its own config), at most 32 files and 256 KB, and its frontmatter is right; a connector is one JSON object that parses as `[[mcp]]` (unknown keys refused) with either `url` or `command`.
  - Approved skills live in `<state>/skills/<name>/`, a git repo of the daemon's (run as `/usr/bin/git` with `core.fsmonitor=false`, `core.hooksPath=/dev/null` and no system or global config), one commit per approval or removal, so `/skill undo NAME` reverts the newest one not undone yet (repeated undos walk back). `/skill rm NAME`, `/skill no NAME` (drops the draft), `/skill diff NAME`, `/skills` (approved and waiting). On the host `zephyr skill add DIR` checks the folder the same way, sends it as a tar to `zephyr skill add` in the container, which unpacks it into `<state>/incoming/` and sends `/skill add NAME`; the owner adding it is the approval. Approving, removing or undoing restarts the child at idle, as a rule change does.
  - Approved connectors are `[[mcp]]` tables in `zephyr.toml` (`name`; `url` and `headers`, or `command`, `args`, `cwd`; `env`, `timeout`, `enabled`; the owner's `classes`, §4.16, which `zephyr mcp add` keeps when it adds a connector of that name again, D4; and the broker's `hosts` and `secrets`, §4.21, kept the same way and set with `--host HOST..` and `--plain`). Any string value may say `${NAME}` for a secrets.env key, except zephyr's own (`ZEPHYR_*`) and the channels' (`discord.token_env`, `imessage.password_env`, `imessage.secret_env`, `attach.token_env`): those would land in a file the agent reads and let it post as the owner, so they count as missing, named `(zephyr's own secret, never a connector's)`. `/mcp ok NAME` writes the draft there (`toml_edit`, comments kept) and reloads, which restarts the child (§4.10); a secret it needs and secrets.env lacks is named in the reply. `/mcp no|rm|diff NAME`, `/mcp`. On the host, `zephyr mcp add NAME (--url URL [--header K=V].. | -- CMD ARGS..) [--secret NAME]..` asks for each secret hidden and writes it to secrets.env.
  - Before each child start `drafts::prepare` runs `memory::prepare`, then, as the agent, rewrites `/zephyr/.approved/skills/` from `<state>/skills`, and, as the daemon, writes `mcp.json` in the adapter's `mcpServers` shape, each `${NAME}` filled with its stand-in under the network floor (§4.21; with the secret itself for a `secrets = "plain"` connector and under host networking; a remote connector with a secret and no `secrets` key is not published), to `<state>-public/mcp.json` (`/var/lib/zephyr-public/` in the container: root's, folder 0755, file 0644, refused if others may write the folder), where the agent can read it but not rewrite it before a child loads it. A connector whose secret is missing is left out, and `doctor` warns; so is one that names a secret and has no host to send it to (`drafts::left_out`, shown by `/mcp`). An edit the agent makes to the skills lasts only until the next start. `AGENTS.md` gets a `## Skills` section (each skill's name, description and `SKILL.md` path, "read a skill's SKILL.md before a task it covers", and when to draft one) and a `## Connectors` section (each server's name and kind, how to call `mcp_list`/`mcp_call` with that `configPath`, that `arguments` is a JSON object, and how to propose one with secrets only as `${NAME}`), after the tools and before the memory. Only this index is in context; a skill's body is read when needed.
  - rpi has no option to load skills from another folder, so `--no-skills` stays on and the index replaces rpi's own skill listing.
  - **The MCP gate** (`zephyr-policy` `check_mcp`, after the name check): the child gets `ZEPHYR_MCP_CONFIG=/var/lib/zephyr-public/mcp.json`; the plugin reads that file once, when it loads. An `mcp_*` call must pass exactly that `configPath`, and the file must still hold those bytes; the `url` form is refused, and with no connectors every call is. So a config the agent writes (a server's `command` is a lasting hook that runs at every call) or a URL it names never runs, and an edit to the file mid-session is refused. This ended ad-hoc MCP use: a server the agent wants goes through `/mcp ok`.
- `<state>` is root's in the container (§4.4), so the agent can change neither the rules nor the approved copies.

### 4.7 Auth and providers

- **Until upstream PR #144 is merged**, the AuthKeeper calls `get_auth_status` on the child every `[auth] refresh_minutes` (default 10; `enabled`, default true). For each OAuth provider with a stored credential that expires within 15 minutes (or has expired), it runs `rpi auth refresh --provider <id>` as a subprocess, with the child's `RPI_CODING_AGENT_DIR` and cwd. It does not use the `oauth` RPC: upstream `rpi-cli/src/auth.rs` `run_refresh` passes the stored `{access, refresh, expires_at}` to the plugin, while the RPC handler (`modes.rs` `rpc_oauth`) forwards only the request's `input`, so it would not give the plugin the refresh token. Expiry is read from `<agent_dir>/auth.json`, field `expires` only, because `get_auth_status` has no expiry. Tokens are never read into a struct or logged.
  - Then the child must restart to bind the new token. Upstream builds each provider's request auth once, at session start (`rpi-runtime/src/provider/binding.rs:6`, `RequestAuth`). `set_model` only swaps the model descriptor (`rpi-harness/src/agent_harness.rs:5146`), so it keeps the old token and is not used. The child is restarted when idle; if a run is in progress, the restart waits for its settle.
  - Once #144 is released, this timer is removed.
- **What each provider source brings** (§4.4 item 1). `RPI_PACKAGE_REPO` (`yansigit/rpi-package`, a fork of `pi-rust/rpi-package`): `librpi_providers.so` (OpenCode Go, Antigravity, ChatGPT/Codex) and `librpi_mcp_adapter.so` (every `[[mcp]]` connector's `mcp_*` tool, §4.6). `PLUGINS_REPO` (`yansigit/rpi-provider-plugins`): `rpi-claude-agent/`, Claude through the Agent SDK and `zephyr login claude-code`. Without both, what is left is zephyr, the policy plugin, Cursor (`crates/zephyr-cursor`, this repo) and rpi's built-in providers: of init's menu, the Anthropic API key and Cursor.
- Failover between accounts: §4.9. With `[[account]]` set, the AuthKeeper checks every account's `<home>/accounts/<name>/auth.json` for its model's provider, without asking the child, so a cooling account stays fresh. Only a refresh of the account the child runs on restarts it.

#### 4.7.1 Signing in from the running gateway

`zephyr login` on the host signs in through `docker exec`. The same login also runs in the daemon, so a channel or an attached TUI can add an account without `zephyr restart` and without a shell. The attach methods are §4.3.1's `zephyr.login_*`.

- **Provider table.** `crates/zephyr/src/auth.rs` keeps `id`, `label` and `kind` for each provider (`antigravity`, `openai-codex`: `oauth`; `opencode-go`, `cursor`, `anthropic`: `key`; `claude-code`: `setup_token`). The ids are still rpi's own; the table only says what finishing the sign-in takes. Providers come only from the image (§4.4): a login authenticates against `/opt/zephyr/ext/`, it does not install one.
- **The login process.** One `rpi auth login --provider <p>` child per login, tracked in a registry the daemon owns, with `RPI_CODING_AGENT_DIR=<home>/accounts/<name>`: the dir the pool uses for that account (§4.9), 0700 and holding that account's `auth.json`, with the shared `models.json` and `settings.json` symlinked in. rpi asks for a TTY, so the child runs under a pty: `script -qfc '<cmd>' /dev/null`. Its output is read for a human, not parsed for credentials.
  - `oauth`: rpi prints a URL. The user opens it in their own browser, not on the box. Under the network floor (§4.20) the provider's redirect to `http://127.0.0.1:<port>/…` no longer reaches the container, so the browser shows that the page cannot be opened, and the owner pastes that address, with the code in it, at rpi's own `Paste OAuth code or response` prompt: under the floor the login is `need_input` from the start (`Config::floor`), and the line arrives through `zephyr.login_input` (the panel's input row), a channel's `/login paste ADDRESS`, or the terminal of the host's `zephyr login`, which prints `if the browser then cannot open 127.0.0.1, paste its address here` first. The router keeps a `/login` sign-in after its URL notice (`posted`), feeds a paste only to the newest one the same channel and sender started, takes only text that starts with `http://127.0.0.1` or `http://localhost` or holds `code=` (angle brackets around it, as Discord sends a link without a preview, are dropped) (so a token pasted by mistake goes nowhere), and posts how the sign-in ended. The pasted text is handled as a key is: kept only to redact the pty's echo, never logged or stored by the login; a channel paste stays in its inbox row as any message does, where it is a used, single-use code. The token exchange that follows goes through the proxy, since the login runs as the agent. With `network = "host"` the callback reaches the login process: the login stays `waiting`, no paste is offered in the URL notice or the panel, and `/login paste` finds nothing to feed. `/login cancel` stops a sign-in whose URL was posted as well as one still waiting for it.
  - `key` / `setup_token`: the child waits for a paste. The text goes to that child's stdin and nowhere else: not into a struct, `state.db`, a log line or the channel reply, and the daemon never sends it back in `lines`.
- **The model, resolved twice.** Before the spawn, the same way `zephyr login` resolves it: the model the request named, else the account's existing model, else the first row `rpi --list-models` lists for that provider (run with the main agent dir). Then again after the check, inside the new account's dir, because some providers list no models until they are signed in; a login that found none before, or that the request gave none, takes rpi's first row there. A provider that lists none either way is `failed`, and nothing is recorded.
- **On exit.** The daemon re-checks the credential with `rpi auth check --json --provider <p>`; if it does not pass, the login is `failed` with a sentence of the daemon's own (`rpi stored no credential for <p>; see the lines above`), not with the child's output: what rpi printed is already in `lines`, redacted, and an error travels further — into a chat notice. Then the model is resolved as above. Then the `[[account]]` row is appended to `zephyr.toml` with `toml_edit`, so comments and the existing order are kept and the new account goes last.
- **Why nothing re-execs.** No daemon-level setting changed, so the plan is not §4.10's re-exec: the `[[account]]` row is read where it is used, and the router's 5 s config tick loads the new file. A login into the account the child is already running on leaves a newer `auth.json` than the child's stamp, which is exactly the re-login branch of §4.10: the router restarts the child on the same session (`--session-id main`) when idle, never mid-turn. A brand-new account is not a re-exec, but it is not always free of a restart either: `reload::diff` answers `(None, Some(_))` with `Plan::RestartChild`, so the first account of an empty install — `/login` into a gateway with no `[[account]]` — does restart the child, once, when it is idle. With a pool already there the child starts on the new account the first time the pool picks it, by `/model`, the TUI's model picker (§4.3.2) or a failover (§4.9), and that pick is what restarts it then.
- A login runs as the agent's uid in the agent's home, like every child (§4.4); the registry and the `zephyr.toml` edit are the daemon's.

#### 4.7.2 The Cursor provider

The `cursor` provider is this repo's own rpi plugin, `crates/zephyr-cursor` (`libzephyr_cursor.so`),
not a staged package. It registers through `rpi-plugin-sdk`'s streaming-provider bridge, and its
manifest lists the models it serves. It talks to Cursor's agent service directly (Connect over
HTTP/2, protobuf), because the package it replaced (`rpi-cursor-lite`) kept the request text-only: a
Cursor model reached through it could never call a tool, which is all the old `Cursor (chat only)`
label admitted.

- **One `Run` per turn.** Every request carries the whole conversation as `root_prompt_messages_json`
  blobs rebuilt from rpi's own history (§4.1's messages), plus this turn's user text (or a fixed
  continuation prompt when the history ends on a tool result). The provider keeps no server-side
  session, so a child restart or a failover (§4.9) costs only the replay.
- **The turn ends at the first tool call.** `mcpArgs` becomes rpi's `toolcall_end` with stop reason
  `toolUse`, the stream is closed, and rpi runs the tool and asks again with the result in the
  history. No tool result travels back into Cursor's stream, so nothing has to stay alive between
  turns, and the loop is the same one every other provider uses.
- **Tools are the only tools.** The request sets `x-cursor-agent-allowed-tools:
  mcp_tool_call,get_mcp_tools_tool_call`, which removes Cursor's own registry (the service refuses a
  run without its catalog lookup). Our tools go out as MCP tools named `zephyr_<tool>` (request
  context and `mcpTools`), but the model does not see them by name: it gets two meta-tools,
  `GetDynamicTools` (catalog lookup) and `CallDynamicTool`. Cursor builds the catalog by sending the
  client an `mcp_state` exec request (`ExecServerMessage` member 36), answered with every rpi tool as
  one connected MCP server named `zephyr`. Expect a lookup round trip before the first call. A native
  tool request that still arrives is answered with an error result on its own member, rather than
  left hanging.
- **Unknown exec requests get a throw.** An exec member the provider has no shape for is answered
  with an `ExecClientThrow` (`UNSUPPORTED_EXEC_REQUEST`), not ignored: an unanswered request stalls
  the turn forever while the server keeps heartbeating.
- **Credentials.** rpi resolves the account's key into `opts.api_key` (§4.7: `[[account]]`, `auth.json`);
  `CURSOR_API_KEY` is the env door for an operator-supplied key. The key is exchanged for a
  short-lived bearer token (`/auth/exchange_user_api_key`, refreshed at `/auth/refresh`) held in the
  child's memory for the life of that child. Nothing is written, logged or echoed, and a failed
  exchange's error names the endpoint and status only — the same rule as every other credential
  (§4.7.1).

### 4.8 Operations

- **Supervision** (§4.4): Docker's `--restart unless-stopped`, then `zephyr supervise`, which restarts a daemon that exits. A daemon that hangs instead is caught by its heartbeat: the router's tick writes `<state>/heartbeat` (`<unix time> <main up 0|1> <failed starts in a row>`), and `supervise` checks it every 15 s; once the daemon has been up 120 s and the heartbeat is 300 s old, it kills the daemon's process group and starts it again, counted toward its give-up limit (5 in 2 minutes). 300 s is well past the longest a tick may wait (an auth check, 60 s per account). The image's `HEALTHCHECK` runs `zephyr status`, so `docker ps` shows a hung daemon as unhealthy.
- **Limits** at `zephyr up`: `--log-opt max-size=20m --log-opt max-file=5` (Docker keeps at most 100 MB of logs), `--ulimit nofile=65536:65536`, and `--memory` from host.toml's `memory`, else 75% of the host's `MemTotal` (no flag if it cannot be read). Each `exec` log stops at 50 MB (§4.13).
- **Backups.** Once a day (the hourly sweep, when today's is missing), `<state>/backups/` (root, 0700) gets `state-YYYYMMDD.db` (`VACUUM INTO` a 0600 temp file, fsynced, renamed; written last, so its presence means the day is complete) and `zephyr.toml`, `vault.toml`, `host.toml` and `secrets.env` as `<name>.YYYYMMDD`; the newest 7 of each are kept. `doctor` warns when the newest is over 2 days old, or none exists a day after `state.db` was made. An upgrade also keeps `<file>.<version>.bak` beside `state.db` for going back (README). Copying `backups/` off the machine is the owner's (README runbooks).
- **Alerts** come from outside the container, since the channel it would tell you on may be what is down: `zephyr alert setup TOPIC [--server URL]` writes a systemd user timer on the host that runs `zephyr alert check` every 5 minutes. A check is unhealthy when the container is not running or `zephyr status` fails; it posts to ntfy (`curl`) only on a change (down with the reason, then back), and once more each time the failed-reply count grows. The target URL is kept in the owner's `~/.config/zephyr/alert-url`, so a check posts with Docker itself down; the last state in `~/.local/state/zephyr/alert-state`, saved only once a post went out.
- On SIGTERM: stop intake, abort or finish runs, flush the outbox, then exit. rpi drains its session on `stop`. A run that ends during the drain is settled as usual, so its spend and outbound list are booked; one cut off at the 20 s deadline is booked with what it did so far.
- `zephyr doctor`, in the container, also checks the token broker (§4.21): its CA and where it is installed, that the agent can read neither key and add no trust, that `mcp.json` holds no brokered secret, the hosts that are decrypted, and what still reaches the agent in plain.
- `zephyr status` shows the daemon and its heartbeat age, whether main's child is up and its failed starts in a row, the oldest waiting message, replies pending (with the oldest) and failed, the accounts, budgets and row counts. It exits non-zero when the daemon does not answer or the heartbeat is stale (the `HEALTHCHECK` and `zephyr alert check` use that). `doctor` checks the binary version, the protocol commands, bwrap, Tailscale reachability of the Mac, and credentials. It reports whether each credential is present, never its value. Under the network floor (§4.20) it also proves the floor by running `zephyr __netcheck` as the agent: a direct connection to `1.1.1.1:443` and one to the daemon's attach port must be refused at once (a connection, a timeout or an unreachable network all mean the rules are missing), `example.com` must not resolve, and through the proxy the metadata address and an IPv4-mapped loopback must get 403; `example.com:443` not answering 200, or the proxy not answering at all (the daemon is stopped), is only a warning. It then reads `/proc/net/{tcp,tcp6,udp,udp6}` and fails with `root listens on ADDR, where the agent can reach it` for any root TCP listener or unconnected UDP socket on loopback or a wildcard address other than the proxy and Docker's DNS, which is what lets the rules go without a port list. Under `network = "host"` it prints one warning instead (`network floor off (host networking): …`), and the host's `doctor` warns when the container still runs host networking although host.toml does not ask for it.
- **Self-hosting knobs.** Nothing of this owner's is required: each value is a knob with today's value as its default (README "Self-hosting" lists them): `ZEPHYR_REPO`, `ZEPHYR_IMAGE`, `ZEPHYR_CONTAINER` and `ZEPHYR_SRC` for the CLI, `ZEPHYR_BUILD_REPO` when it is built, the Dockerfile's provider and `ZEPHYR_BUILD_REPO` args, `RPI_BIN` for `release.sh`, `ZEPHYR_GH_REPO` for the fallback runner. What publishing would take is a checklist in the distribution spec (§5 there), not done.
- **The image's repository.** The host CLI runs `<repo>:<its version>` and upgrades from `<repo>:latest`, where `<repo>` is `ZEPHYR_REPO` from the environment, else the value it was built with under a name of its own, so a `ZEPHYR_REPO` exported while building is never baked in (`ZEPHYR_BUILD_REPO=… cargo install`, or the Dockerfile's `ZEPHYR_BUILD_REPO` arg, which image.yml sets to `ghcr.io/<this repository>`), else `ghcr.io/yansigit/zephyr` (`host::DEFAULT_REPO`); empty counts as unset. It is not a host.toml key: host.toml is read through the image when the container is stopped. `ZEPHYR_IMAGE` still wins over all of them and turns versioned upgrades off. A pull that fails logs in with the `gh` token only for a `ghcr.io/…` image; another registry is never sent it, and the error says `docker login <registry>`.
- **`deploy/install.sh [--from-image | --from-source] [--no-init] [-- INIT ARGS..]`** installs the CLI on a fresh Linux machine, run from a checkout as the owner's own user (it refuses root). It checks that `docker version` answers (else it names Docker's install page), then refuses an existing install, the container `${ZEPHYR_CONTAINER:-zephyr}`, `~/.zephyr-daemon`, `~/.zephyr` or a `~/.local/bin/zephyr` it would replace (never moved over: `mv -n`), with `zephyr is installed here; upgrade with zephyr upgrade`: a new CLI and `init` would upgrade a live container. `--from-image` (x86_64 only, as image.yml builds) pulls `${ZEPHYR_REPO:-ghcr.io/yansigit/zephyr}:latest` (logging in with the `gh` token only for ghcr.io) and copies its `/usr/local/bin/zephyr` through a temp file in `~/.local/bin`, which a `trap` removes if it stops midway, checks that its `--version` is the image's own `zephyr --version` (as `zephyr upgrade` checks the CLI it fetches), and `mv`s it to `~/.local/bin/zephyr`; that CLI upgrades from the repository its image was built for, so with `ZEPHYR_REPO` set it says to keep it set for `zephyr upgrade`; `--from-source` needs `cargo` 1.89 and `docker buildx`, and runs `cargo install --locked --path crates/zephyr`, with `ZEPHYR_BUILD_REPO` set to `ZEPHYR_REPO` when that is set, so the CLI upgrades from where it was installed for; neither flag tries the image, then the source. It warns when Docker's root has under 20 GB free, when the install folder is not on `PATH` or another `zephyr` comes first, then `exec`s the new binary's `init` unless `--no-init` (with which init arguments after `--` are a usage error). It never runs `sudo`, `curl` or `wget`, installs no Docker, Rust, gh or Tailscale, edits no rc file, group or systemd unit, logs in to no registry but ghcr.io, and writes only that one binary. Its default repo is `host::DEFAULT_REPO` (a test checks the string), and CI runs `shellcheck` on it.
- **`zephyr init`** (host, `host/setup.rs`) also sets the network mode: `--network bridge|host` writes host.toml `network` (`Data::set_network`; anything else is refused before a file is written), and without it a fresh install gets `bridge` with the comment naming the way back while a re-run keeps what is there. There is no prompt for it, since the floor is the safe default and a wizard should not offer the weaker one; init prints `network: bridge (the agent's network floor)` or `network: host (no network floor; zephyr init --network bridge turns it on)`. The flag is the only CLI way to change it: after the first `up`, host.toml is root's. Interactive init then, after the approvals preset: offers the web app (`Set up the web app (needs Tailscale with HTTPS certificates)?`, or with `[web] host` set `web app: https://HOST` and `Change the web app?`, both default no), and a yes runs `zephyr web setup` (an error is printed and init carries on); under `network = "host"` it prints the floor line instead. Init records the published ports after its first `up`; when a step changed them (an `[imessage] listen` added) under the floor, its last step is `up` again, since a `docker restart` cannot publish a port (`Host::republish`, which `config set` and `channel add|remove` share), else the `docker restart` as before. Neither runs when web setup made the container again (its `Restart::Done`, recorded as it happens, so it holds when a later setup step fails) or when the owner declined that restart (`Declined`: init says `zephyr up` applies the changes). Non-interactive init adds `add a channel: zephyr channel add discord|imessage` when neither channel is set and `web app: zephyr web setup` when `[web]` is unset under the floor. A re-run on a configured install with Enter at every prompt writes the same `zephyr.toml` and `host.toml`, byte for byte, and ends in one `docker restart` (`tests/host.rs`).
- **The iMessage webhook forward.** Under the network floor the webhook is published on the host's loopback while BlueBubbles posts to the Tailscale address, so `tailscale serve --bg --tcp P tcp://127.0.0.1:P` joins them. `channel add imessage` (which `init` also runs) asks `Forward this machine's Tailscale port P to the webhook?` (default yes: the channel does not work without it) after writing `[imessage]`, only under bridge and only when `tailscale serve status` has no word `tcp://127.0.0.1:P`. A yes runs it through the helper `web setup` uses (`web::serve`), which on a refusal prints the `sudo tailscale serve …` and `sudo tailscale set --operator=$USER` forms; the channel stays saved either way. A missed detection only asks again, and the same mapping twice is harmless.
- **`zephyr web setup [--yes]`** (host, `host/web.rs`) puts the web app behind `tailscale serve` (§4.3.3). It prints each step and asks before each change (`--yes` answers yes; with neither that nor a terminal it changes nothing):
  1. it reads this machine's name from `tailscale status --json` (`.Self.DNSName`), or says how to install or log in;
  2. it checks that the name is in `.CertDomains`, else `turn on HTTPS certificates in the Tailscale admin console (DNS → HTTPS Certificates)`;
  3. it writes `[web] host` and `port = 7793` to `zephyr.toml`;
  4. it runs `tailscale serve --bg http://127.0.0.1:7793`, and when that is refused prints `sudo tailscale serve --bg …` and `sudo tailscale set --operator=$USER`;
  5. it warns `never point tailscale funnel at this port`;
  6. it starts the container again (`zephyr up`);
  7. when `zephyr.toml` sets `settings.strong_channels` without `passkey`, it offers to add it, through the daemon (`zephyr set`);
  8. it runs `zephyr web enrol` in the container, which prints the code;
  9. once the owner has pressed Enter, it reads `zephyr web`, and when a passkey is listed offers `approvals.strong_only = loosen,money` (§4.16).

  The host's `zephyr status` then says `web: tailscale serve forwards https://HOST`, or `web: tailscale serve does not forward to 127.0.0.1:7793; run zephyr web setup`, from `tailscale serve status`.
- `zephyr web enrol [NAME]` (in the container; the host command runs it there) asks the daemon for a passkey enrolment code over the chat socket and prints the reply (§4.3.3); `zephyr web` prints `/web`'s. Exit 1 when the reply names no address (the app is not set up), 3 when no daemon answers.
- Logs go to the container's stderr (`zephyr logs`), rotated by Docker. No secrets in logs, since credentials stay in rpi's agent dir.

### 4.9 Accounts and failover

- `[[account]]` entries (`name`, `model`), in failover order, replace `model`. Without them nothing changes: one child on `agent_dir` and `model`. A name must be a plain path segment (letters, digits, `-`, `_`, `.`, not starting with `.`) and unique; a model must be `<provider>/<model>`.
- Each account's `RPI_CODING_AGENT_DIR` is `<home>/accounts/<name>/` (mode 0700, made absolute because rpi refuses a relative one). It holds only that account's `auth.json`. Zephyr links `models.json` and `settings.json` in it to the ones in `agent_dir`, when they exist. Other agent-dir files (`trust.json`, skills, a global `AGENTS.md`) are not linked; trust is forced on and skills are off anyway (§4.6).
- The child runs on the first account not cooling down. Cooldowns are in `state.db` (`account_cooldown(name, until, reason, level)`), so they survive restarts.
- **Detection.** rpi 0.15.0 puts the last assistant message's `errorMessage` into `agent_settled.error` (checked against the pinned binary), so the router reads the settle. It is a rate limit when the text contains the providers' marker `rate_limited;` (with an optional `resets_at=<unix>`), or matches `\b429\b|rate.?limit|usage limit|quota|too many requests`, case-insensitive: 429 only as a whole word, so `204290 tokens` or task #1429 is not one. A task or job run is classified on its own error only, never its label or the agent's last message. Without a reset time (or one already past) the cooldown backs off 15 min, 1 h, then 4 h. A completed turn on the account resets the backoff.
- **Failover.** The router marks the cooldown, puts the turn's unanswered rows back to `new`, and restarts the child the same way the AuthKeeper does (when idle), on the next ready account, with the same `--session-id main` and session dir. After an error turn rpi 0.15.0 keeps the user message and the error message, and `pendingResume` is false, so there is nothing to resume. The new child re-sends each row as a prompt with the same `[channel #id]` tag, and reconcile matches the reply to the later copy. The owner is told on the row's channel: `account a is rate-limited until <time>; switched to b`.
  - A failed account cools down until a time in the future, so it is not tried twice in one turn.
  - When every account is cooling down, no child runs. Messages wait in the inbox, the owner is told the earliest reset, and the child starts at that time and sends what waited.
  - Jobs (§4.5) start on the first ready account. A rate-limited attempt cools that account and retries once per account in a fresh session; when every account is cooling down the run fails at once.
- **rpi's own retries.** rpi 0.12.0 retries an error whose text says `429`, `rate limit` or `too many requests` (`rpi-harness` `is_retryable_assistant_error`) up to `retry.maxRetries` times, default 10, with a delay doubling from 2 s, bounded by `maxAgentDelayMs` (60 s) (`RetryPolicy`, `settings.json` key `retry`: `enabled`, `maxRetries`, `baseDelayMs`, `maxAgentDelayMs`). There is no per-error switch, and `enabled = false` would also drop retries of 5xx and network errors. So in pool mode Zephyr sets `retry.maxRetries` to 1 in the shared `settings.json` (it writes the file only if it is plain JSON; a file with comments is left alone and logged). Failover then starts after one 2 s retry. Quota texts (`insufficient_quota`, `quota exceeded`, `usage limit`) and the `rate_limited` marker are not retried by rpi at all.
- **Budget.** Daily totals are unchanged and count every account. Each settle's usage is also added to `account_spend(day, account)`, shown by `zephyr status`.
- **`zephyr status`** prints one line per account: `ready`, `cooling until <time> (<reason>)`, or `needs login` when the account's `auth.json` has no key for its provider (only the keys are read). An API key given by environment variable shows as `needs login`.

### 4.10 Live settings

- The router owns the config as an `Arc<Config>` and sends each new one to the scheduler on a `watch` channel. `Config::load` records the file it read.
- `home` is the agent's (sessions, memory, accounts); `state` (default `home`; `/var/lib/zephyr` in the container) holds `state.db`, `secrets.env`, the socket and the lock. Changing either re-execs.
- **Triggers.** `/reload` (owner-only, outside the queue, like `/pause`; `zephyr reload` sends it over the chat socket, and the host CLI runs it after every edit), and the router's 5 s tick when the mtime of `zephyr.toml` or `secrets.env` changed. A file that does not load or validate is reported and not applied.
- **Plan** (`reload::diff`), the least disruptive that covers the change:
  - `rpi`, `home`, `[discord]`, `[imessage]`, `[attach]`, or any `secrets.env` pair: **re-exec**. Once main is settled and no job runs, the router drains as on SIGTERM and `zephyr run` execs itself with the same args, minus the variables secrets.env set, so the new process reads them again. The lock and sockets are close-on-exec; under `--init` the PID stays.
  - `extensions`, `policy_plugin`, `agent_dir`, `[[mcp]]` (the connectors file is written at start, §4.6), the active account changing (the pool would now pick another), a model on another provider, or a newer `auth.json` for the active account (a re-login): **restart the child** when idle, as the AuthKeeper does, on the same session.
  - The active account's model on the same provider: **`set_model`** when idle (before reconcile sends the next row). rpi checks it against its catalogue; the sign-in stays the same, so the bound credentials (§4.7) are still right. A refusal is told to the owner.
  - Anything else (budget, owners, time zone, `[auth]`, the pool order, `[approvals]`, a connector's `classes`): read where it is used. The gate reads the approval modes on every decision (§4.16), so AGENTS.md does not list them and a change needs no restart.
- **Writers.** A registered setting (§4.17) is written through the daemon, by `set_setting`, which edits `zephyr.toml` and then runs the reload below. The host CLI is the other writer: `zephyr config set` hands a registered key to the daemon through `zephyr set` in the container, and edits the file itself, as before, for a key the registry does not know or when no daemon answers (the 5 s tick then applies it). Hand edits stay the third path. All of them end in the same `reload::diff`.
- **`/model PROVIDER/MODEL`** sets it on the active account if that is on the provider, else on the first account that is, moved to the front; checks that `rpi --list-models`, signed in as that account, lists it (the running child lists only its own sign-in's models); writes `zephyr.toml` (atomically, comments kept), then reloads. `/status` adds the agent's account and model to what `zephyr status` prints.

### 4.11 Tools

The image adds tools to rpi's own (`read`, `bash`, `edit`, `write`, ...). The agent learns them from a fixed `## Tools` block that `memory::agents_md` writes into `AGENTS.md`, between the rules and the memory (skills are off, §4.6).

- **CLIs through `bash`**, so the policy veto, the audit log and the outbound list (§4.4) see them with no new code:
  - **Browser:** `agent-browser` (vercel-labs, a Rust CLI: snapshots with refs, `click @e3`, `fill`, `screenshot`) drives **fingerprint-chromium** (ungoogled-chromium with fingerprint patches; release tarball pinned by sha256; Playwright's Chromium on arm64, which it does not build). The image's `ENV` sets the binary, the profile `/zephyr/browser` (persistent, the agent's own; signed into sites through the vault's `fill`, §4.15, or by the owner by hand), headed mode, and `--no-sandbox,--disable-dev-shm-usage,--use-angle=vulkan,--enable-features=Vulkan,--ignore-gpu-blocklist`. Vulkan reaches the GPU both headless and on Xvfb; `gl-egl` falls back to llvmpipe on Xvfb. Docker's 64 MB `/dev/shm` is enough with `--disable-dev-shm-usage`. Checked 2026-11-01: 0 failed checks on bot.sannysoft.com, the Cloudflare check at nowsecure.nl passed, WebGL `ANGLE (NVIDIA, Vulkan ...)`.
    - `agent-browser` on the agent's PATH is the approvals gate's wrapper (§4.16): `/opt/zephyr/gate/bin/agent-browser`, a root-owned link to the zephyr binary, in a root-owned 0755 folder first on `agent::AGENT_PATH`, so a copy the agent drops in `~/.local/bin` cannot shadow it. The real binary (0.41.0, pinned by sha256) is `/opt/zephyr/libexec/agent-browser`, off the PATH; the wrapper runs it in its own place once a command may go, and the daemon's own browser calls (the vault's fill) name it by full path (`Config::agent_browser`). The image's `ENV` above is unchanged and reaches both.
  - **Python:** `deploy/python` (`pyproject.toml` and `uv.lock`) is installed with `uv sync --frozen` into `/opt/zephyr/py`, a venv on the image's python3.12, read-only and first on `PATH`: requests, beautifulsoup4, pandas, pypdf, pillow and Camoufox. The image also has `uv` (pinned by digest), so the agent adds a package per script with `uv run --with`, or makes a venv of its own; uv's cache is in its home. The venv has no pip, so nothing installs into the shared environment.
  - **Fallback browser:** Camoufox (anti-detect Firefox, in that environment), from Python through `camoufox-python`. Firefox has no CDP, so agent-browser cannot drive it. It spoofs Linux only (`os="linux"`, matching the real GPU), so the image drops its macOS- and Windows-only fonts. It runs headed: headless it has no WebGL. What a Camoufox script submits is not in the outbound list, so the Tools block says to submit through agent-browser.
  - **Desktop:** with `ZEPHYR_DESKTOP` set (the image sets `:99`), `desktop::ensure` starts `Xvfb` and `openbox` as the agent before each child starts, restarting them if they died, and the child gets `DISPLAY`. The agent uses `xdotool` and `import -window root`, then `read`s the PNG. Nothing listens; the owner can start `x11vnc -localhost -once` with `docker exec` (README).
    - The server requires an MIT-MAGIC-COOKIE (`Xvfb -auth`). With `--network host` the container shares the host's abstract socket namespace, so `@/tmp/.X11-unix/X99` is reachable by every process on the host, and abstract sockets carry no file permissions: before the cookie, any local user or host-network container could connect without authorization, screenshot the agent's signed-in browser and type into it (checked with a bare X11 handshake from the host, which the server accepted). The cookie lives in `$HOME/.zephyr-xauthority` (the agent's, mode 0600, one wildcard-host entry, kept across daemon restarts so a server left by a crashed daemon still lets the agent in); `desktop::xauthority` puts it in `XAUTHORITY` for openbox, the rpi children and `exec` commands. The server keeps listening on the abstract name rather than `-nolisten local`: clients try that name first, so a free name could be claimed by anyone on the host, and the agent's browser would draw on their server. The host's own desktop already refuses the agent (`Xorg :0` with lightdm's `-auth`). Under the network floor (§4.20) the container has a network namespace of its own, and abstract sockets belong to it, so the host no longer sees `@/tmp/.X11-unix/X99` at all; the cookie stays, for the processes in the container and for `network = "host"`.
  - **Command-line tools:** `gh` and `himalaya` (mail) from their release tarballs, pinned by sha256 per architecture (himalaya's are static musl builds), and from apt `jq`, `ripgrep`, `fd-find` (with an `fd` link), `unzip`, `zip`, `less`, `nano`, `sqlite3`, `openssh-client`, `zsh`, `file` and `tree`. node's `npm` and `npx` come from the same `node:24-bookworm-slim` as `node`. `gh` works once the owner gives the agent a token; himalaya reads `~/.config/himalaya/config.toml` in the agent's home. `zephyr doctor` runs `gh --version` and `himalaya --version` as the agent (warnings, not failures).
  - **User-space installs:** `ENV PATH=/zephyr/.local/bin:...` and `NPM_CONFIG_PREFIX=/zephyr/.local` (the literal path: `HOME=/zephyr` is set at `docker run`), so `uv tool install`, `npm i -g` and a binary dropped in `~/.local/bin` land in the agent's home and outlive the image. There is no pip (above). An apt package goes through the owner (`zephyr packages`, §4.4).
  - `policy::outbound` lists `agent-browser fill|type|keyboard|upload|eval`; navigating is a plain GET and is not listed. It lists `gh` writes (`pr create|merge|comment|review|edit|close|ready`, `issue create|comment|close|edit`, `release create|upload|delete`, `repo create|delete|fork`, `gist create`, and `gh api` with a method other than GET, or with a field or `--input`, which make it a POST), and himalaya commands that send mail: a `send` subcommand (`message`, `smtp`, `gmail ... drafts|messages`, `msgraph messages`), `--send` on `message compose|reply|forward`, `smtp raw` and `jmap submission create`. A vault fill runs the real `agent-browser` from the daemon, not through `bash` or the wrapper, so it is not in that list; the owner allowed the login before its first fill (§4.15). The `gh` writes and the himalaya sends are also the gate's posts and messages (§4.16); the list still names them after the turn, whatever the gate decided.
- **Connectors (MCP)** through `rpi-mcp-adapter`'s `mcp_list`/`mcp_call`/`mcp_resource`/`mcp_request`, on the approved connectors only (§4.6, the MCP gate). Checked live on rpi 0.15 with Haiku: a stdio server in `mcpServers`, called with `mcp_list {configPath, server}` then `mcp_call {configPath, server, tool, arguments}`. The model first passed `arguments` as a JSON string and failed twice, so the `## Connectors` section says it is an object, left out for a tool with no parameters.
- **Tools the daemon carries out**, registered by `zephyr-policy` (`tools.rs`, `register_tool`). In the child they only check their arguments and answer at once. The router (and the scheduler, for job runs) reads each successful call from rpi's event stream into the run's `Tally` (`tool_execution_start` args, kept on a `tool_execution_end` without `isError`; advisory, §4.4 item 3), and `crate::tools::apply` acts on it when the run settles:
  - `send_file {path, caption?}`: at most 10 MB (Discord's bot limit). The policy veto's name check covers `path`. The daemon reads the file as the agent (`agent::fs`), copies it to `<state>/files/<id>/<name>`, and queues an outbox row with that `attachment` (schema v5) to the channel the run answers. Discord adds it to the last chunk, BlueBubbles gets `POST /api/v1/message/attachment` (multipart, `tempGuid` `<client id>-f`), and the chat line client shows `[file] <name>`. The copy is deleted once the row is sent or given up. Shortcut: the file is read at settle, so one the agent deletes before then is reported missing.
  - `schedule {name, schedule, prompt}`: checked with `scheduler::check` and stored off (§4.5); a bad schedule is told to the owner.
- **Files the owner sends** arrive in `/zephyr/inbox/`, one line per file in the message (§4.3). The Tools block says so, and that an image opens with `read`.
- **`gateway {command}`**, answered mid-turn (as `task` is, §4.12): the agent runs a read-only slash command (`zephyr_policy::tools::GATEWAY_COMMANDS`: `/status`, `/model`, `/switch`, `/rules`, `/goals`, `/persona`, `/memory diff`, `/memory log`, `/job list`, `/settings`, `/approvals`, `/facts`) and reads its output. `/approvals` is the modes in effect (§4.16); `/facts` is the private facts' names and kinds, never a value or an allowed target (§4.18). `/activity [today|Nh|Nd] [KIND]` is zephyr's own record (§4.19), the owner's text in the daemon's words, with at most two printable ASCII words and 40 bytes in all, and never `grants` (any case): the grants view names who passes without asking, which is what an injected run would aim at. AGENTS.md tells the agent to read it, not its memory, when the owner asks what it did, sent or was refused. `/settings` also takes words (`/settings Budget`, `/settings tasks.parallel`; printable ASCII, at most 100 bytes). It can also propose an action, in these exact shapes only: `/model PROVIDER/MODEL`, `/new`, `/switch ID`, `/pause`, `/reload`, `/subagent add|prompt|model|rm …` `/rule TEXT` or `/rule rm N` (plain text on one line, the whole command at most 1500 characters, `zephyr_policy::tools::CARD_CHARS`), `/goal add TEXT` (the same), `/goal done N` and `/goal rm N` (N in digits), and `/persona set TEXT` (as plain text, but line breaks allowed) or `/persona clear`; like a rule, a goal or persona proposal goes through `set_setting` and goes stale when `GOALS.md` or `PERSONA.md` changes (§4.17). `/forget` and `/memory squash` are not the agent's. One more form, `/set KEY VALUE [for D]` (`Gateway::Set`: a registry key of `[a-z0-9_.-]`, one printable word of at most 200 bytes, an optional `for` and a duration word), is decided by the daemon: a setting made stricter applies at once, anything else becomes a proposal (§4.17). The `approvals.*` settings are among them, so the agent tightens a class's mode at once; the one-word value means it can set a preset or a one-word mode (`ask`, `ask-new`, `auto`; `hold`, `warn`, `off`), never `delay N` or `auto N` (`ask`, the strictest, is always open to it). The private facts take three forms (`/facts add NAME text|digits|email VALUE`, a name of `[a-z0-9][a-z0-9_-]{0,63}` and a one-line value of at most 500 characters; `/facts rm NAME`; `/facts allow NAME TARGET`, one printable word of at most 200 bytes): the daemon applies `add` at once, since a new fact only makes calls stricter, tells the owner the fact's name (never its value) and answers `saved the private fact NAME`; `rm` and `allow` loosen the check and are proposals whose `/ok` needs a strong channel (§4.18). All of it is `zephyr_policy::tools::gateway_kind`, shared by the plugin and the router, which checks again. The router does not run a proposal (a `/set` goes through §4.17's `set_setting` instead): it stores it (`proposals`, schema v6), asks the owner on the channel the run answers (`[zephyr] the agent asks to run /new (#3); /ok 3 runs it, /no 3 drops it`) and answers the call `proposed as #3`. The owner's `/ok 3` runs it through the same router path as typing it, outside the queue, and marks it done; `/no 3` drops it; a proposal already settled or older than 24 h is an error. The approvals (`/ok`, `/no`, `/cancel`, `/held`, `/memory ok|undo`, `/job ok|rm|add|run`, `/login`, `/resume`) and `/stop` are never readable or proposable (`/rule` and `/subagent` are, as proposals the owner reads in full, §4.12 and §4.17): an approval the agent could run is one injected text could run (§4.5, §4.6). A job's proposal is answered `not available in scheduled runs` and stores nothing.
  - The plugin checks the list, then returns `Pending` from `poll` (sleeping 20 ms a poll) until `$ZEPHYR_GATEWAY_DIR/<tool call id>` exists, at most 10 s; a cancel (`/stop`) ends it. The dir is `<home>/.gateway`.
  - The router answers when the call's `tool_execution_start` reaches `tapped`, so in the main loop and while draining: it checks the list again (rpi reports the start of a call the plugin refused too; that one gets no answer and nothing runs), runs the same function the owner's command runs, and writes the text as the agent, then renames it into place. Each answer also sweeps files there older than a minute: an answer that came after its call gave up. A job's child gets `not available in scheduled runs`. rpi 0.15.0 keeps reading commands while the call waits (`rpi_load` checks `get_state` mid-call).
  - The agent can write `.gateway/` too, so it can fake an answer to its own call; that fools only itself, as every answer is read-only and a proposal is stored from rpi's event stream, not from the file.

- **`vault {action: list|request|fill, ...}`**, main only, answered mid-turn through the gateway file like `exec` (§4.15).

- **`recall {query}`, or `{session, around, include?}`**, answered in the plugin (`tools.rs`) with no daemon round trip. It reads the rpi session files under `$ZEPHYR_SESSIONS_DIR`, which `rpc::spawn_as` sets in every child, so jobs and tasks have it too. Only user and assistant text counts: no records, tool results or non-text blocks. `query` finds the messages with every word in them, case-insensitively: at most 10, ranked by occurrences then recency, each with its session, ISO time, role, entry id and a 200-character excerpt around the first hit. `session` with `around` (an entry id from a hit) returns the 5 messages either side, each cut to 2000 characters and 12000 in all, the entry itself kept. Job and task sessions (`job-*`, `task-*`) are left out unless `include` is `"all"`, for `around` too. An unknown session, an unknown entry or no match is an error the agent sees. Shortcut: a linear scan of every session file; a SQLite FTS5 index once `sessions/` grows past about 200 MB.

### 4.12 Background tasks

The owner should be able to talk to the agent while it works. rpi runs one prompt at a time and 0.15 cannot steer a running one (§4.1), so the agent hands long work to a child of its own and keeps its turns short, as Hermes's `delegate_task` and OpenClaw's `sessions_spawn` do. We copy Hermes: the result comes back into the main session as a new turn, delivered durably, and a task cut off by a crash is `unknown`, never retried, the same rule as job runs (§4.5).

- **The `task` tool**, registered by `zephyr-policy` and answered mid-turn through `$ZEPHYR_GATEWAY_DIR/<tool call id>`, the same way `gateway` is (§4.11). Its description tells the model to start a task for anything that takes more than about a minute, put the whole brief in `goal` (the child sees none of the conversation), and end its turn with a one-line reply.
  - `{"action":"start","goal":"…"}` answers `task #7 started` at once. The goal is at most 8 KB (`zephyr_policy::tools::MAX_GOAL`).
  - An optional `"model":"PROVIDER/MODEL"` runs the task on that model, e.g. a cheaper one for a simple lookup (`tasks.model`, schema v12; `task list` shows it as `#3 running (2 min ago) on openai-codex/gpt-5.5-mini: …`). The check is its shape only (provider and name split on the first `/`, no whitespace, at most 200 bytes). With a pool, the router refuses a provider no `[[account]]` is on (`not started: no account on <provider>; the accounts are a (p/m), b (q/n)`); it does not ask rpi whether the model exists mid-turn, so an unknown one fails the task at start and the report says so. The run (`scheduler::Spec::model`) picks and fails over only among that provider's accounts, each started with the requested `--model` instead of its own; when all of them are cooling it fails `every <provider> account is rate-limited until …`. With no pool the model stands in for `model` in `zephyr.toml`.
  - **Subagents and the default model.** `[[subagent]]` tables in `zephyr.toml` (`Config::subagents`) are the owner's named helpers: `name` (`[a-z0-9][a-z0-9_-]{0,31}`, unique, `zephyr_policy::tools::subagent_name`), `prompt` (1 byte to 8 KB) and an optional `model`; `[tasks] model` is the default for tasks. Both models are checked for their shape (`zephyr_policy::tools::model_shape`, the same check as the call's `model`). `{"action":"start","goal":"…","subagent":"explorer"}` runs the task as that subagent: the plugin checks the name's shape, the router that it exists (`not started: no subagent nope; the subagents are explorer, builder`, or `none are set up`). The router resolves the model at the start: the call's `model`, else the subagent's, else `[tasks] model`, else the account's own (none stored); the provider check above applies to it, and names where a configured model came from (`no account on nope ([tasks] model in zephyr.toml); …`). The resolved model, the subagent's name and its prompt as it is then are stored with the task (`tasks.subagent`, `tasks.preamble`, schema v13), so a resume after a restart uses what it started with, even if the owner has edited it since. The child's prompt is the brief, then the subagent's prompt, then `Goal: ` and the goal; the checkpoint before it is labelled with the goal alone (`scheduler::Spec::goal`). `task list` shows `#3 running (2 min ago) as explorer on claude-code/claude-haiku-5-5: …`. The main child's AGENTS.md lists them under `## Subagents`, after `## Connectors` (`drafts::prepare`; left out when there are none), each with its model (or `default model`) and its prompt's first line, so a change to `[[subagent]]` restarts the main child after the current reply (`reload::diff`); `[tasks]` applies live.
  - **Owner's commands, and the agent's proposals.** The owner sets them from any channel: `/subagent` (list), `/subagent add NAME [PROVIDER/MODEL] PROMPT` (the second word is a model when it has a `/`; the rest, line breaks and all, is the prompt; an existing name is refused), `/subagent model NAME PROVIDER/MODEL|default`, `/subagent prompt NAME PROMPT`, `/subagent rm NAME`, `/task parallel N` and `/task model PROVIDER/MODEL|default`, or `zephyr subagent list|add|edit|rm` and `zephyr config set tasks.*` on the host. A model is checked as `/model` checks one (an account on its provider, and that account's `rpi --list-models` lists it); the edit goes through `toml_edit` (comments kept), is saved only if the whole config still validates, and is applied with a reload. These are callers of the settings registry's one write path (§4.17). The agent has no tool or file that writes a subagent either, but it may propose one through `gateway` (`/subagent add|prompt|model|rm …`, §4.11): the owner's card shows the exact command, cut at 1500 characters, and a longer one is refused to the agent rather than shown cut (`CARD_CHARS`); `/ok N` runs exactly that text, only if the subagents are unchanged since the card was made (the proposal holds a SHA-256 of the `[[subagent]]` table, §4.17). Text the agent read therefore cannot write a subagent the owner has not seen in full. Through `/set`, the agent may lower `tasks.parallel` at once and propose raising it; `tasks.model` it only proposes (§4.17).
  - `{"action":"list"}` shows the queued and running tasks, then the last 5 that ended.
  - `{"action":"stop","id":7}` stops one. This is how the owner's "cancel that", typed in plain words, works.
  - The plugin checks the arguments, and the router checks them again (`task_action`) before it acts.
- **Running** (`tasks.rs`): a task runs `scheduler::execute`, the job path, in a fresh `task-<id>` child, on the first account not cooling down, with the job path's rate-limit retry. At most `[tasks] parallel` run at once (`Config::parallel_tasks`, default 2, 1 to 32), read live. At most 64 are queued or running in all (`store::MAX_OPEN_TASKS`), and a start past that is refused. A task resumed after a restart counts as done only when its last assistant message calls no tool; one cut off mid-call runs on. A child dropped before it is reaped (a re-exec, say) kills its whole process group, so a build or dev server it started does not run on beside the resumed task. Each task is cut at `job_timeout` and `budget.run_turns`, aborted by a pause, and charged to the day's budget and to its account. Its child is told it works alone and that its last message is its report. Inside a task, `task` and `gateway` answer `not available in background tasks`, so tasks stay one level deep. Its `send_file` and `schedule` calls go to the channel that started it, as a job's do.
- **No approval.** Unlike a job (§4.5), a task needs no `/job ok`-style gate. It runs once, under the same policy plugin, sandbox, tools and budget as main, and stops at the time cap; its messages, posts and payments wait for the owner as main's do (§4.16). It adds concurrency, not authority. A job is gated because it persists and runs later with nobody watching.
- **The report.** When a task ends (`completed`, `failed`, `stopped`), one transaction closes its `tasks` row (schema v7) and inserts an inbox row on the channel and sender of the run that started it, with platform id `task-<id>` (unique, so it is delivered once). Its text is `[task #7 finished; a background agent's report, not the owner's words] goal: …`, then the output with every line quoted as `> …`. The quoting means nothing the task read can start a line that looks like a channel tag (`[chat #3] …`) or another report's header. A report longer than 8 KB is cut there, and the whole of it goes to `tasks/<id>.md` in the agent's home, where the agent can `read` it. The router dispatches it like any row (`prompt` when idle, `queue_message` when busy), so the main agent reads it and answers the owner on that channel.
  - Risk: a task that read the web can carry injected text into main through its report. That is the same exposure as any tool result. The framing says the report is not the owner's words, and approvals stay the owner's alone (§4.5, §4.6).
- **Stopping.** The agent's `task stop`, the owner's `/task stop <id>`, and `/stop` (which also aborts main's run) end tasks.
  - A queued task ends at once as `stopped` and sends no report.
  - A running task is flagged. Its runner sees the flag within 1 s, sends `abort`, and reports `stopped`.
  - `/pause` aborts running tasks as it aborts a job run, and starts no new one. `/new` and `/switch` leave tasks running; the report names its goal, so it reads clearly in the new session.
  - `/task list` shows what `task list` shows.
- **Restarts.** A task cut off by a crash or a re-exec resumes in its own session, at most 3 times (`store::MAX_TASK_RESUMES`, `requeue_interrupted_tasks`); after that it ends `unknown` with a report row. This is Absurd's durable Pi-agent pattern (earendil-works/absurd `docs/patterns/pi-ai-agent.md`): the message log is the checkpoint, and rpi's session file is that log. Each attempt records its session id (`tasks.session`) before it starts, so the resume reopens the right one, failover attempts included. On resume (`scheduler::resume`):
  - the run is pending: `resume_pending`, with `RESUME_NOTE` steered in (§4.2);
  - the last message is the agent's: it had finished, and that text is the report, with no new model call;
  - the session is empty: the original brief again;
  - otherwise: a prompt with `RESUME_NOTE`.

  A task that was being stopped ends `stopped`. A task or job cut by a stop, a pause, its timeout or a stall ends its report with its last message before that (`Its last message before that:`, cut to 8 KB), as Hermes's interrupted children return partial output. Queued tasks never started, so they still run. Re-exec for a reload no longer waits for running tasks: they are cut like a crash and resume.
- The model is nudged to delegate by a fixed `## Staying available` section that `memory::agents_md` puts before the owner's rules in `AGENTS.md`: work with several long steps goes to `task`, then a one-line status and END YOUR TURN (Hermes's wording for `delegate_task`). Responsiveness does not depend on it: steering (§4.1) and `exec` (§4.13) work whether or not the model delegates.
- Not done yet: steering a running task, nested tasks, a stopped task's partial output.

### 4.13 Long commands: `exec` and `process`

Steering (§4.1) waits for the tool call in progress, so one long command would still hold the owner's message: in the live check, `sleep 120` in rpi's `bash` kept "what is 2+2?" waiting two minutes. rpi's `bash` cannot be moved to the background (it takes only a `timeout`) and the plugin can veto a call but not take over its process. So main's child is started with `--exclude-tools bash`, and runs commands through two tools of ours instead. Job, task and `/btw` children keep rpi's `bash`: nobody is waiting on them.

- **`exec {command, timeout?, background?, secrets?}`**, registered by `zephyr-policy` only in main's child (`ZEPHYR_EXEC=1`) and answered by the daemon through `$ZEPHYR_GATEWAY_DIR/<tool call id>`, as `gateway` is. The router checks the hardline veto again (`policy::check("exec", …)`, the `bash` rules), then `procs.rs` runs `bash -c` as the agent (`agent::cmd`), in its home, leading its own process group, with output in `<home>/.procs/<id>.log`.
  - A command that ends in its own turn answers `exited N` with the output, cut like rpi's `bash` (the last 2000 lines or 50 KB) and naming the log. Nothing else is sent.
  - It moves to the background, not killed, when something needs the agent: a new inbox row for main (an owner message, a task or process report), `background: true` (servers, watchers), or the 10-minute backstop (Hermes's foreground cap). The tool then answers with Hermes's note: the command was moved to the background, is still running as process #N, the output so far, a message follows when it exits, reply to the owner now. This takes the advantages of both: Hermes yields only when someone is waiting (hermes#103884), so a build nobody is waiting on finishes in its turn; OpenClaw (`yieldMs`) lets a command ask for the background and never holds a turn for long. "Still running" feedback comes from the channel's progress notes, not from splitting the work.
  - When a backgrounded command exits, its report comes back to main as an inbox row on the channel it served (platform id `proc-<id>`, quoted and cut at 8 KB like a task report, §4.12).
  - `secrets: [NAME]` names vault tokens (§4.15). The router checks them before anything starts (`vault::exec_env`): each token must be allowed for every program the command runs, or the call is answered with the proposal it made and nothing runs. Then `procs::spawn` sets each one in the command's environment, under the network floor as its stand-in (§4.21: `vault::value_for`; the real value only for a `raw` token or under host networking, and a token bound to no host is answered `not run: the token NAME is bound to no host; ask the owner with vault bind`), and every text returned from its log (the answer, `process log`, the report) has the vault's values replaced with `[vault:NAME]` (`vault::scrubbed`, reading the vault as it is then, so a command adopted after a re-exec is scrubbed too; no value is kept anywhere else). The log itself is scrubbed as it is written: the command's output reaches `.procs/<id>.log` through `zephyr __scrublog` (`vault::scrub_stream`, started by `procs::spawn` as the daemon, in a process group of its own), which replaces every vault value and its base64 forms with `[vault:NAME]`, finds one cut across two reads, lets go of a held-back start of one after 250 ms with nothing more, reads the vault again when its file changes and withholds the output while it cannot be read. So the log the agent can read holds no vault value, a `raw` token's included. It is a process and not a task of the daemon's, so a command still outlives a re-exec or a crash; the wrapper closes its own output and waits at most a second for the scrubber before it records the exit code, so the answer has all of the output. `shortcut:` a scrubber that ends after a re-exec stays a zombie until the daemon exits. What it cannot cover: output the command itself writes to a file (`cmd > out.txt`), which only a `raw` token's value can reach, and a value in a form other than itself or base64.
- **`process {action: list|log|stop, id?}`**, answered mid-turn: the open and recent processes, a log's tail, or a kill. The owner has `/process list` and `/process stop N`.
- **Limits.** At most 8 run at once. `timeout` defaults to 30 minutes, at most 2 hours, and then the process group is killed and reported. `/stop`, `/pause` and shutdown kill every process group (the daemon holds `KILL`) and report them `stopped`. `/stop` and `/pause` also kill the agent's processes that left their process group (`setsid`, a double fork) and so outlived that kill (`Procs::kill_strays`): every agent-uid process under PID 1 whose parent chain reaches neither the daemon (main's, tasks' and jobs' rpi children, the commands it runs), a tracked command, nor the desktop (`Xvfb`, `openbox`), each killed through a pidfd after its start time is checked; the reply counts them. A routine child restart leaves them alone, so a server the agent meant to keep survives a token refresh.
- **Log size.** The wrapper sends the command's output through `stdbuf -o0 head -c` so a log stays within 50 MB; what is past that is counted and dropped, with a closing note, and the command keeps running. A process substitution, not a pipe, so a server the command leaves in the background cannot hold the wrapper (it waits at most a second for the output side). - **Re-exec.** A reload's re-exec runs `exec()` in the same process, so the processes keep running, and the new image adopts them (`Procs::adopt`, Hermes's process checkpoint):
  - Each `procs` row records the pid (also the process group), its kernel start time (field 22 of `/proc/<pid>/stat`, read after the last `)`) and its deadline (schema v9).
  - On start, for each `running` row the router opens a `pidfd` on the pid first, so the pid cannot be reused while it checks, then compares the start time. Only an exact match is adopted: reaped with `waitid(P_PIDFD)`, still listed and stoppable, its timeout kept, its report sent on exit.
  - A start time that no longer matches means the pid was reused by something else: it is reported `unknown` and never signalled.
- **Daemon crash.** The supervisor (§4.4) starts the daemon again without restarting the container, so the processes live on as tini's orphans. The new daemon is not their parent, so `waitid` cannot give their exit codes: each command runs through a wrapper (`procs::WRAPPER`, the command and the path passed as positional arguments, never spliced in) that writes its exit code to `.procs/<id>.exit`, Hermes's recorded exit. `watch` tries `waitid` first (after a re-exec it is still the parent) and reads the file on `ECHILD`. A `running` row whose pid is gone or reused but whose exit file exists is reported `exited N` without touching the pid: it ended while no daemon watched. The file is the agent's; faking it fools only the agent about its own command.
- Shutdown (SIGTERM) still kills every process group. A container restart (an upgrade, `docker restart`, a reboot) kills them anyway, and those are reported `unknown`, never re-run.
- The veto, the audit line and the outbound alert (`rpc::Tally`) treat `exec` as `bash`.

### 4.14 Checkpoints and `/rollback`

The agent edits the projects folder with nobody approving each change, so the owner gets an undo for files, as Hermes's checkpoints give one (`checkpoint.rs`). It is a safety net, not a security boundary: the store is the agent's, so an agent that deletes it only takes away the undo.

- **On or off.** `zephyr up` passes `ZEPHYR_PROJECTS=<projects>` (`Config::projects`, not a `zephyr.toml` key). A container started without it has no checkpoints, and `/rollback` says to recreate it.
- **Store.** Hermes's shadow-git layout: one bare repo at `<home>/.checkpoints` (`GIT_DIR`), and for each top-level folder of the projects folder that is a git repo (a "project": it has `.git`) its own index (`GIT_INDEX_FILE=index-<project>`) and ref (`refs/zephyr/<project>`), with the project as `GIT_WORK_TREE`. Git runs as the agent (`agent::cmd`), with the system and global git config ignored; the daemon cannot read the agent's files itself (§4.4).
  - Only repos: a folder without `.git` has no `.gitignore` either and is often data (the live projects folder holds a 51 GB model folder and a 5 GB game world beside ~1.5 GB of repos), far too big to copy at every run.
  - Skipped: `info/exclude` lists `node_modules/`, `target/`, `.venv/`, `__pycache__/`, `dist/`, `build/`, `*.log` and `.env*` (those are covered with empty mounts, §4.4, which a restore could not write over). Each project's own `.gitignore` applies too, since it lives in the work tree.
  - `shortcut:` hidden folders, files at the projects root and folders whose names a ref cannot carry (a space) are not covered, and nested repos become gitlinks; fix this if that ever matters.
- **Taking a snapshot.** Per project, `git add -A`, then `write-tree`; it commits (`commit-tree`, `update-ref`) only when the tree differs from the ref's, with the subject `before: <the message, folded, first 60 characters>` and a `zephyr-checkpoint: <unix ms> <project>` line that groups one snapshot's commits across projects. Up to 4 projects at once. An index naming an object a prune removed is started again (one full re-read).
- **When.** In the router, right before an inbox row goes as `prompt` or `continue`; steers are skipped, since their run already has one. In `scheduler::execute`, before a task or job starts (`before: task #7: <goal>`); a resumed run is skipped. One snapshot at a time per store; a run waits at most 1 s for one still going, then goes ahead without. A snapshot holds the run back at most 10 s (`checkpoint::LIMIT`); one still going then (the first one over a big folder) finishes in the background rather than being killed, so it is not thrown away and the next only reads what changed since; it may then hold that run's first changes. An error is logged and the run goes ahead. Lock files left by a git killed in a crash are removed before the next one.
- **`/rollback`** (owner, any channel) lists the newest 10: `#1, 12 min ago, before "fix the login…", nyacode, zephyr (14 files changed since)`. The projects named are the ones that snapshot committed; the count is over every project, against the folder as it is now (each index is refreshed first).
- **`/rollback diff N`** shows, per project, the diffstat from checkpoint N to now, cut at 4000 characters.
- **`/rollback N [PROJECT]`** restores every project (or one) to how it stood at checkpoint N: a project's newest commit at or before that snapshot. N is resolved before anything is written.
  - Refused while a run, a job run, an open task or a running `exec` process is active (`[zephyr] not rolled back: a run still running; /stop them first`); a store error counts as busy.
  - It first snapshots everything as `before rollback`, so `/rollback 1` undoes it; if that fails, nothing is restored. Then, per project, `git read-tree -u --reset <commit>` against the index just written: changed and deleted files come back, files created since are removed, and ignored files are left alone. A deleted project folder is created again. The restore itself is not timed: one cut halfway would be worse than a slow one.
- **Pruning** (from the hourly retention sweep, §4.1): a project with more than 50 checkpoints has its chain rebuilt from the newest 50 trees with `commit-tree`, keeping their messages and dates (no file is stored again), then `git gc --prune=now`. Skipped that hour while a snapshot runs.

### 4.15 Vault

The owner keeps website logins and tokens for the agent in a vault (`vault.rs`), so a credential never has to be pasted into a chat, and the agent uses each by name without seeing it.

- **Store.** `<state>/vault.toml` (the daemon dir: root's, 0600, out of the agent's reach, §4.4), one of `DAEMON_FILES`, so the host CLI reaches it through `zephyr __file`. The daemon reads it on every use, so an edit needs no reload or re-exec; it is edited with toml_edit (comments survive) under one in-process lock. It is not encrypted at rest: a passphrase would stop unattended restarts.

  ```toml
  [[login]]
  name = "github"                  # [a-z0-9][a-z0-9_-]{0,63}
  site = "https://github.com"      # fill only when the page's origin is exactly this
  username = "aiden"
  password = "…"
  totp = "BASE32SEED"              # optional
  granted = true                   # the owner OK'd filling it

  [[token]]
  name = "GH_TOKEN"                # an env var name, [A-Z_][A-Z0-9_]{0,63}
  value = "…"
  programs = ["gh"]                # the programs the owner OK'd it for
  hosts = ["api.github.com:443"]   # exact; the only places it is swapped in (§4.21)
  headers = ["x-api-key"]          # swapped in these request headers besides Authorization
  url = false                      # also swap it in the path and query
  raw = false                      # hand the program the real value, as before the broker
  ```

- **The agent's `vault` tool** (`zephyr-policy` `tools.rs`), registered in main's child only, like `exec` (§4.13); tasks and jobs keep rpi's `bash` and get no vault (`shortcut:` tasks and jobs ask main). The plugin checks the arguments (`vault_action`) and waits on the gateway file up to 90 s; the router answers from `tapped`, checking them again. No action waits on the owner.
  - `list`: names, kinds, sites, usernames, whether a TOTP seed is set, and the grants. Never a value.
  - `request {name, kind, site?, why}`: tells the owner (`notify_last_owner`) what to save and the exact commands (`/vault add login NAME SITE` in `zephyr attach`, `zephyr vault add login NAME --site SITE` on the host), and answers at once. A new entry saved through the attach port is told to main as an inbox row of its own (`[zephyr] the owner saved the login NAME in the vault; you can use it now`), so the agent carries on; a save from the host CLI writes the file only.
  - `fill {name, user?, password?, totp?}` (CSS selectors): without the login's grant, it stores a proposal `/vault grant login NAME` (§4.11's `proposals`, so `/ok N` works on every channel) and answers that it waits for the owner. With it, a task of its own runs `agent-browser get url` as the agent (`procs::for_agent`: `agent::cmd`, the desktop's `DISPLAY` and `XAUTHORITY`, `HOME` the agent's), refuses unless the page's origin (scheme, host, port, parsed with `url`) equals the site's, then `agent-browser fill <selector> <value>` per field, the one-time code made now (RFC 6238: HMAC-SHA1, 30 s, 6 digits), reading the address again after each field: once the page has left the site it stops before the next one and answers `stopped: after the username was typed the page was on <origin>, not <site>; … Submit nothing there, and tell the owner`. Otherwise it answers `filled the username and password on <page>`; a failure is scrubbed of the values. `shortcut:` agent-browser has no fill-if-origin, so a redirect in the moment before a fill still gets that one value.
- **`bind {name, hosts}`** stores the proposal `/vault bind NAME HOST..`, as `fill` stores a grant, and answers that it waits; the owner's notice puts the hosts first (`the agent asks to send the token GH_TOKEN to api.github.com, github.com`). A host that is not an exact name is not asked at all.
- **Tokens** go through `exec`'s `secrets` (§4.13), as a stand-in the proxy swaps on the token's hosts (§4.21). The programs a command runs are `policy::programs`: the command word of each stage of the policy's own splitter, the runners in front of it (`env`, `xargs`, `timeout`, ...), and those inside `sh -c`/`eval`, basenamed; `cd` is left out. A word that is not a plain file name (`$X`) is refused. Each (token, program) pair without a grant becomes a proposal `/vault grant token NAME PROGRAM..`, and the call is answered without running.
- **Grants come only from the owner.** `/vault grant …` is an owner command (`vault::command`, from `router::command`); an approved proposal reaches it through `/ok N` as the owner's own text (§4.11). The agent cannot propose one through `gateway` (`gateway_kind` refuses `/vault`), and proposals are stored by the daemon from rpi's event stream, never from a file the agent can write (it can write `.gateway/` answers, which fool only itself). A saved entry never carries grants in: `put` keeps the old ones (a login's only while its site is unchanged) and a new entry starts with none.
- **Proposal storage.** A grant proposal is a `kind = 'command'` row in `proposals`, the table the approvals gate's held actions share since schema v16 (§4.16): one id space for both, so `/ok N` and `/no N` find either, and the TUI's Waiting tab lists both. Nothing else about the vault's proposals changed: `/ok N` still runs the stored `/vault grant …` as the owner's own command, and `/ok N once` on one is a plain `/ok N`.
- **The owner.** From any channel: `/vault` (names only), `/vault rm NAME`, `/vault revoke NAME [PROGRAM]`, `/vault grant login NAME`, `/vault grant token NAME PROGRAM..`, `/ok N`, `/no N`; and a token's bindings (§4.21): `/vault bind NAME HOST..`, `/vault header NAME HEADER..` (the request headers it is swapped in besides `Authorization`), `/vault url NAME on` and `/vault raw NAME on` loosen: they need a strong channel, and in the web app a passkey, while `/vault unbind NAME [HOST]`, `/vault unheader NAME [HEADER]`, `/vault url NAME off` and `/vault raw NAME off` tighten and are taken anywhere. Each such change is a `settings_log` row (`vault.NAME.hosts`, `.headers`, `.url` or `.raw`, with the channel; host and header names are not secrets). A chat never takes a value: `/vault add` there is refused and points at the TUI or the CLI. In `zephyr attach`, `/vault` opens a panel (entries and their grants; `a` adds a login, `t` a token, `e` edits, `d` deletes after a `y`, `r` revokes), and `/vault add login NAME SITE` or `/vault add token NAME` opens its form filled in (a token's form has a `hosts` field after the value, space or comma separated, which `vault_put` checks with `broker::parse_host` and saves normalized; the panel and the saved card say where a token is sent, §4.21); the TUI never sends a `/vault add` line. Secret fields are drawn masked and handed over at once, like the sign-in panel's token (§4.7). The attach methods `zephyr.vault_list`, `zephyr.vault_put`, `zephyr.vault_rm` and `zephyr.vault_revoke` are behind the attach token like the rest; each answers with the entries as `Entry::public` (no values), from which the TUI draws a card for the entry it just saved (`VaultEntry::saved`: kind, name, site, user, whether a one-time seed is kept, what it may be used for), and an error never quotes the value (a malformed entry is "the entry is malformed", not serde's message). On the host, `zephyr vault list | add login NAME --site URL [--user U] [--totp] | add token NAME [--host HOST].. [--header HEADER].. | edit NAME [--host HOST].. [--header HEADER].. | rm NAME | revoke NAME [PROGRAM]` (a token's hosts are asked for at a terminal when no `--host` is given; `edit` without `--host` or `--header` keeps what is saved) asks values with hidden prompts, or reads one per line from stdin when it is not a terminal; never from arguments. `[agent] env` (§4.4) stays, for a secret every command needs.
- **Never logged.** `Entry`, the TUI's `Form` and `Ask::VaultPut` print only the secrets' lengths in `Debug`; no value is ever in an answer, a notice, an error or the audit log (the plugin's audit redacts `password`-named arguments, which are selectors anyway). Output scrubbing replaces each value, and its standard and URL-safe base64 forms at all three byte alignments (`curl -v -u x:$TOKEN` prints a Basic header), with `[vault:NAME]`, then masks any run of 8 or more characters of a value as `[redacted]` (`auth::redact`), for a cut-off or partial print. It skips values shorter than 4 characters (`shortcut:` such a value is shown as is). When `vault.toml` does not load, output is withheld (`[output withheld: the vault could not be read]`) rather than shown unscrubbed.
- **Threat model.** The vault keeps credentials out of chat history, transcripts and the model's context in normal use; a login is filled only on its own site, which defeats phishing pages; and each new use needs the owner's OK. A token bound to hosts never reaches the agent (§4.21); a `raw` token and a login still can be read by a hostile agent: it can read a filled field back, `cat` its own `.procs` log, have an allowed program print its environment to a file, or put a script named like an allowed program first on its `PATH`. For a bound token those yield the stand-in, which only the proxy turns into the token, and only on its hosts; and whatever a command prints reaches its `.procs` log with vault values already replaced (§4.13).

### 4.16 Approvals

Before the gate, every tool call ran without asking, and the owner saw outbound commands only after the turn (§4.4 item 3). The Muse audit found every consent failure in Muse's record at the moment of acting: an "Allow Always" grant that sent a seller's home address to strangers, and emails sent without approval in Meta's own testing before launch (Business Insider, via Dataconomy; `reports/Muse agent audit.md`). "Approve What, Exactly?" (arXiv 2610.21063) found that half the runtimes it tested let an action's arguments change after approval, and that flooding the owner with requests still worked 45–60% of the time. So the actions that reach other people or spend money stop for the owner, as far as the owner wants, and what runs after `/ok` is exactly what the card showed: the daemon runs the stored action itself rather than letting the agent retry it. Everything else stays autonomous and listed after the turn. The design is `docs/superpowers/specs/2026-11-07-approvals-gate-design.md`; where it and this section differ, this section is what was built.

- **The classes** (`zephyr_policy::policy::gated`, beside `outbound`; the plugin, the gate and the card all read it):

  | Class | Recognized | Targets |
  |---|---|---|
  | messages | a `himalaya` send (the forms `outbound` lists, §4.11) | `To`/`Cc`/`Bcc`, lower-cased, read only from the send's own `-H` arguments or a heredoc that is provably the message it reads (its own, or a bare `cat`'s piped straight into it); anything else, a message piped from a file or a recipient header with an expansion in it (`-H "To: a@x.org, $(cat more)"`) included, is `unknown` |
  | messages | an `mcp_call` whose tool name has the word `send`, `reply`, `message`, `email` or `dm` | `server/tool`, then the values of its recipient-like arguments (`to`, `cc`, `bcc`, `recipient`, `recipients`, `email`, `channel`, `channel_id`, `user`, `user_id`, `chat_id`, `thread`, `thread_id`, `phone`, `number`, however the key is written: `channelId` is `channel_id`) at any depth, and any key with `to`, `cc`, `bcc`, `recipient(s)`, `email(s)`, `channel(s)`, `user(s)`, `chat`, `thread` or `phone` among its words (`toRecipients`, `cc_emails`, `user_ids`), read the same way unless its last word says it holds text (`email_subject`, `user_agent`, `go_to_url`, a `…message_id`), addresses taken out of `Name <a@x.org>` and lists; a recipient given as an object counts by its `id`, `address`, `email_address`, `handle`, `username`, recipient keys or an email anywhere in it (B3); one naming none of those, a `true` or `null` recipient, no recipient left once the tool's own name is taken out, or none named by the listed keys at the top level of the arguments (R69: what lies deeper, or under a key read by its words, is a target too, never a stand-in) is `unknown` |
  | messages | a browser Send or Reply, or Enter in a composer (below) | the page's origin |
  | posts | a `gh` write: `pr create\|merge\|comment\|review\|edit\|close\|ready`, `issue create\|comment\|close\|edit`, `release create\|upload\|delete`, `repo create\|delete\|fork`, `gist create`, and `gh api` with a method other than GET or HEAD, or with a field or `--input` | `owner/repo` from `-R`/`--repo` (gh's `[HOST/]OWNER/REPO`: three parts are a host, an owner and a repo, and a host other than github.com stays in the target, `ghe.corp.com/owner/repo`), a URL or the API path; else `unknown` |
  | posts | an `mcp_call` with `post`, `publish`, `comment`, `tweet`, `share`, `create issue` or `create pull` | as for a connector message |
  | posts | a browser Post, Publish, Tweet, Share or Comment, or Submit in a form with a textarea | the page's origin |
  | money | an `mcp_call` with `pay`, `purchase`, `order`, `checkout`, `transfer`, `refund`, `charge` or `subscribe`; the amount from `amount`, `total` or `price`, with `currency` | `server/tool` |
  | money | a browser checkout or payment button | the page's origin; the amount is the page's labelled total |

  - A connector tool's name is normalized (`createIssue`, `create-issue` and `Create_Issue` are `create_issue`) and matched by whole `_` words (a plural too), money before posts before messages, so `unsubscribe` and `payload` are no verbs; a name whose first word is a read verb (`get`, `list`, `read`, `search`, `find`, `fetch`, `view`, `show`, `count`, `describe`) is not gated. `[[mcp]]`'s `classes = { TOOL = "messages" | "posts" | "money" | "none" }` overrides the verb rule per tool: the owner's, through `/set mcp.NAME.classes.TOOL CLASS` or the file (one registry row per classed tool, §4.17); a connector draft cannot set it (§4.6), and an approved update keeps the owner's. A value validation would refuse counts as the class whose mode is strictest now, never `none`.
  - A shell command is classed stage by stage, through `sh -c`, `eval` and the simple shell-feeding forms (`bash <<< …`, a here-string before the shell too, `<<< … bash`, `echo … | sh`, `source /dev/stdin` with a heredoc), heredoc bodies and comments included: over-gating is the safe direction. It is also classed as a de-quoted copy (every quote, backtick and backslash a space), so no quoting trick hides a send; what that copy finds that the plain scan did not goes to `unknown`. Its command words are found as the veto finds them (§4.4 item 2: redirections, runners, ANSI-C strings), and a himalaya `message send` or `template send` counts wherever it comes after the global flags. The highest class found counts (money, then posts, then messages), with every target. Elaborate obfuscation (encoded scripts, interpreters fed from files, a script written now and run later) is out of scope: the gate covers the shell forms it recognizes.
- **Modes** (`approvals.rs`, pure; `Effective` is what is in force). Messages and posts: `ask` (hold every one), `ask-new` (allow when every target was approved before, in `known_targets`; `unknown`, or no target at all, is never known), `delay N` and `auto`. Money: `ask`, `delay N`, `auto` and `auto N`. `delay N` is 1 to 60 minutes: a command or a connector call is stored `scheduled` and goes when it ends unless `/cancel N`; a browser action waits in place for `min(N, 10)` minutes, then goes. `auto N` (N above 0, at most two decimals) lets a payment through when its amount is known, in `approvals.currency` (default `USD`) and at most N, compared rounded up to the cent; an amount in another currency, one naming no currency, or none read is over the cap and held. The facts check has its own mode, `hold`, `warn` or `off` (§4.18). Strictness, which the registry orders by (`approvals::stricter`; no derived order, which would put `delay 10` looser than `delay 5`): `ask` < `ask-new` < `delay N` (a longer delay stricter) < `auto N` (a lower cap stricter) < `auto`; `hold` < `warn` < `off`.
- **Presets.** `[approvals]` in `zephyr.toml` holds `preset`, the hand-set `messages`, `posts`, `money` and `facts`, `currency` and `strong_only`:

  | Preset | messages | posts | money | facts |
  |---|---|---|---|---|
  | `manual` (a new install) | ask | ask | ask | hold |
  | `semi` | ask-new | delay 5 | ask | hold |
  | `full` | auto | auto | auto | warn |

  A class's mode in effect is its hand-set value, else the preset's; no preset is `manual`. A value that does not parse (a hand edit the reload refused that still reached the gate) counts as the strictest, `ask` or `hold`, never as the preset's. Setting a preset (`preset_edits`) writes it and, in the same update, clears every hand-set class looser than the new preset's, keeping the stricter ones, so a preset never loosens what the owner set by hand; while a hand-set class differs from the preset, `/approvals` and the panel read `semi (modified)`. A timed preset goes back to the whole set it replaced (`approvals::snapshot`: the preset and each hand-set class); a class set stricter since stays, and a class whose own time limit the preset ended is saved as what that limit would have put back, so the end of a limit never loosens.
- **Commands** (any channel, callers of §4.17's `set_setting`): `/approvals` shows the modes (`[zephyr] preset semi (modified) · messages ask-new · posts delay 5 · money ask · facts hold`); `/approvals manual|semi|full [for D]`, `/approvals off [for D]` (`full`), `/approvals on [for D]` (`manual`) and `/approvals messages|posts|money|facts MODE [for D]` set `approvals.preset` or the class, and answer with the change and the modes after it. The registry rows are in §4.17's table: every `approvals.*` setting is `strong` (the currency too, C2: another currency changes what an `auto N` cap lets through, and as it has no order every change of it counts as a loosening), so a loosening needs a strong channel; the agent tightens them at once and proposes the rest (§4.11 says which values its one-word `/set` can carry).
- **The decision** (`gate::decide`), the only place the modes, the remembered targets and the private facts are read; none of them is published where the agent could read a value. Three ways in:
  1. Main's `exec`: the router, after the veto and `vault::exec_env`, decides it in process before `procs` starts anything. Allowed, it starts; held or refused, the call is answered with the daemon's words and nothing starts.
  2. Tasks' and jobs' `bash`, and every session's `mcp_call`: the plugin asks over the gate socket (§4.4 item 2).
  3. The browser: the wrapper asks over the gate socket, and waits there (below).

  A call the gate has nothing to look at (no message, post or payment, nothing `outbound` lists, no connector call, nothing typed in the browser) is allowed at once. Otherwise, in order:
  1. A connector call the owner approved goes through, once: its pass is consumed in the same statement.
  2. The private facts (§4.18): one found under `hold`, or `facts.toml` unreadable under anything but `off`, holds the call whatever its class's mode; one found under `warn` lets it go and tells the owner `[zephyr] the agent sent your private fact NAME to TARGETS`.
  3. A browser action on a control the wrapper could not read is held, whatever the modes (under `full` too).
  4. The class's mode. A call that only sends data out, in no class, goes once its facts are checked.
  5. The flood cap, for a call that would wait, never one that goes (R35): at most 3 actions waiting from one run (`RUN_CAP`; main's run is keyed `main:<run start ms>`, a task or job run by its session) and at most 20 held in the last 24 h that the owner did not approve with `/ok` (`DAY_CAP`, R62: waiting, declined, cancelled, expired, or a delay that went by itself; sends the owner approved are no flood). Past either, the call is refused at once (`not run: N actions already wait for the owner in this run`; `not run: N actions held for the owner in the last day are unanswered or were declined`), and the owner gets one summary line per run, not a card per call (kept in memory: a restart may tell once more). A call that `auto` or known targets let through still goes at the cap: only waiting calls flood the owner.

  A store error refuses the call (`not run: the gate could not read its records`): the gate fails closed.
- **The gate socket** (`gate::serve`): `<state>-public/gate.sock` (`/var/lib/zephyr-public/gate.sock`), in root's 0755 public folder beside `mcp.json` (§4.6), mode 0666, so the agent can connect but never replace it. Only the agent's uid is answered (`SO_PEERCRED`; outside the container, the daemon's own). One JSON request line per connection, at most 1 MB, within 10 s of connecting, else it is closed; 32 connections at once, and one more is closed as it arrives. Only `bash`, `mcp_call` and `browser` are taken there (main's `exec` is the router's); anything else, or a `v` other than 1, is `deny`.

  ```jsonc
  // request
  {"v": 1, "session": "task-7", "call_id": "call_abc", "tool": "bash" | "mcp_call" | "browser",
   "args": { ... },                  // the tool call's own arguments; the wrapper's are {"argv": [...]}
   "browser": {"action": "click", "url": "https://…", "origin": "https://…", "role": "button",
               "name": "Send", "typed": ["…"], ...}}     // the wrapper's only (`gate::Browser`)
  // answer
  {"verdict": "allow" | "hold" | "deny", "id": 7, "text": "held for the owner as #7 (…)"}
  ```

  - Every rpi child (`rpc::spawn_as`), main's `exec` commands and approved runs get `gate::agent_env`: `ZEPHYR_GATE_SOCKET`, `ZEPHYR_SESSION` (`main`, `task-7`, `job-2-5`) and `ZEPHYR_AGENT_BROWSER` (the real binary, for the wrapper).
  - The session is named by the agent's own process, so it can be forged. A forged one can send a card to another channel, slip past the per-run cap (the 20-a-day cap still binds), and steer a held or pass note into another run; no verdict depends on it.
  - Who a socket request's card goes to (`whose`): for main, the channel and sender its current run answers, else the owner last answered (R50); for a task, the channel that started it; for a job run, its job's delivery channel; for any other session, the owner last answered. Its card quotes no agent reason: a task's or job's text is in its session, which the socket does not read.
  - A hold's note goes into the asking run before the plugin hears `hold` (R51): a task's or job's through `Steers`, main's through the router, which sends rpi `queue_message {deliverAs: "steer"}`; the gate waits at most 2 s for rpi to take it, then answers anyway. rpi 0.18 takes the steer while the plugin's `ToolCall` handler blocks on the gate and delivers it right after the refused call's result (`crates/zephyr-policy/tests/rpi_load.rs`, under the pinned binary). The call's own `tool_execution_end` carries only rpi's block line, so the note is what tells the agent why; one that did not get in is steered in once at that end instead (`scheduler::held_note`).
  - A gate that cannot start (no store, a socket it cannot bind) says so and serves nothing; the daemon goes on, and the plugin and the wrapper refuse every call they would have asked about (R52). The owner last answered is told once, where the store can still be opened (C7): `[zephyr] the approvals gate could not start, so until zephyr restarts every message, post and payment a task or a job makes, every connector call and the browser's sends are refused`.
  - Only main's `exec` carries vault tokens (`secrets`, §4.13): a request on the socket that names some is held without them, so `/ok` hands none to a task's or job's command (C3).
- **The browser wrapper** (`browser_gate.rs`): `agent-browser` on the agent's PATH (§4.11) is the zephyr binary, which acts as the wrapper when `argv[0]` is `agent-browser`, before any config is read. It reads a command as agent-browser 0.41 does (global flags wherever they stand, `batch` strings split as a shell would, `press` key chords as its `parse_key_chord`), and:
  - passes every command straight to the real binary (`exec`, unchanged), except these;
  - a click (`click`, `dblclick`, `tap`, `find … click`), or Enter however written (`press`, `key`, `keydown` or `keyup` with `Enter`, `Return` or `NumpadEnter`, with modifiers or none, or `\n` or `\r`; a line break typed with `type` or `keyboard type`): it asks the real binary for the page's address (`get url`) and for the control's role and accessible name (`snapshot`, scoped to a selector when one names it, each scoped read followed by a full snapshot so the agent's refs keep resolving, R54; for a key, the focused element, from a read-only script), and classes it with `policy::browser_class` (below). A click on a child of a button (a span inside Send) counts as the button (R53); Enter in a form's field also counts the form's default button, which Enter submits; Space or Enter on a focused button (or on an element a click handler or a tab stop makes one) is a click on it, classed with its form. What is typed before a line break is checked for the private facts. A Tab before a line break (which moves the focus), any key after the first Enter, or a line break typed with `type` into a control that takes no text (a link, a checkbox: 0.41 focuses the target without checking that it took the focus, B7; a text box, search box, combo box or `contenteditable` takes it, and a button is pressed as above), lands where the wrapper did not read, and is held as "a key press the gate could not read" (R57); a control it could not read at all is held as "a click the gate could not read";
  - typing (`fill`, `type`, `keyboard type|inserttext`, `find … fill`): the value goes to the gate for the private facts first; typing is never gated by class;
  - refuses a `batch` that carries a click, a key press or typing, or reads its commands from stdin, and agent-browser's `mcp`, `chat` and `webmcp invoke` (a page's own tools, R55), which act on the page past the gate.

  A message, a post, a payment or a control it could not read goes to the gate as a browser request, which waits in place (`kind = 'wait'`): the wrapper holds its connection open and blocks; nothing touches the page meanwhile. A control it read that is in no class, with nothing typed, goes at once. A connection that closes while it waits (the wrapper killed, with its run or by `/pause`) is the action dropped. A daemon that goes away (a crash, a re-exec) is a closed socket the wrapper sees: it exits non-zero, never hangs and never runs; the action stays waiting until it expires, and an `/ok` then finds no browser waiting (`the browser is no longer waiting, so nothing was done`). After `allow` it reads the page again, the control too, and runs the agent's command as it was only if the page is still the one the owner approved: the same origin, the same control (role, name, form, what is typed) and, for a payment, the same total; otherwise it refuses with `the page changed while the owner decided; not run`. It then tells the gate on the same connection whether it ran (`{"ran": true}` just before it runs), which is what the action's record says: `done`, `failed` (the page changed, or the wrapper went first), or `unknown` with no word in 180 s. The owner is told when an approved click did not run (`[zephyr] #7 (click "Send" on https://mail.example.com) did not run: the page changed while you decided`). A refusal exits 1 with the daemon's words on stderr, which is what the agent reads, or `the gate is not answering; not run`. The wrapper trusts only a gate socket run by root (`gate_client::trusted`: root, or the owner of the program running, root in the image), so a listener the agent starts and names in `ZEPHYR_GATE_SOCKET` is refused before anything is sent to it.
  - `policy::browser_class` reads the control's role and name, case-insensitively, against a lexicon in English and Korean: Latin entries match whole words, Hangul ones by prefix within a word (`구매하기` for `구매`). It looks at a `button` or `menuitem` (or a control with a readable name and no readable role, which is held anyway), and at Enter in a composer:
    - money: `buy`, `buy now`, `pay`, `pay now`, `place order`, `place your order`, `order now`, `complete order`, `submit order`, `confirm order`, `confirm and pay`, `checkout`, `purchase`, `complete purchase`, `subscribe`, `donate`, `transfer`, `결제`, `결제 완료`, `구매`, `바로구매`, `주문`, `주문하기`, `결제하기`, `송금`, `구독`, `후원`, whatever the control's form holds;
    - posts: `post`, `publish`, `tweet`, `share`, `comment`, `게시`, `게시하기`, `공유`, `댓글`, or `submit` in a form with a textarea;
    - messages: `send`, `reply`, `보내기`, `전송`, `답장`, or Enter in a text box that is not a search box;
    - not gated: a search box (`searchbox`, or a name with `search` or `검색`), a Korean history, lookup or list button (`내역`, `조회`, `목록`), a message or post sent by Enter in a field of a form with a password field (a login form submitting its "Send code"; a money label is gated whatever the form holds, R58, since a checkout may carry an optional account password; a click, or a key on a focused button, never reads the form's password field, so clicking "Send code" is held as a message), links, tabs, menus and navigation, and any label outside the lexicon (a documented limit; more languages are data).
  - A payment's amount (`page_total`) is the page's labelled total (`total`, `amount due`, `amount to pay`, `balance due`, `you pay`; `합계`, `총액`, `총 금액`, `결제금액`): of several, the largest, amounts that name a currency before those that name none; `$` reads as US dollars and `¥` names no currency; totals in two currencies, or a number that reads more than one way, are no total. An amount it can't read counts as over any money cap.
  - Not gated by design: `eval`, `mouse`, `select`, `drag` and the rest, and the real binary run by its path or from a copy, which only the plugin's name check stands in front of (§4.4 item 2).
- **Held actions** (`store.rs`, `actions.rs`). Schema v16 adds to `proposals` `kind` (`command` for the slash-command proposals of §4.11, §4.15 and §4.17; `run`, `pass` or `wait` for an action), `class`, `targets`, `summary`, `reason`, `payload`, `secrets`, `origin` (`{channel, sender, session, run, call_id}`), `due_at`, `settled_at` and `result`; the tables `known_targets(class, target)` and `passes(digest, proposal, expires_at, used)`; and `procs.action`, the action a command runs for. One id space, so `/ok N` and `/no N` serve a proposal and an action alike. An action is `pending`, or `scheduled` while it waits out a delay, then `running`, `done`, `failed`, `unknown`, `dropped`, `cancelled` or `expired`. A `run` payload is the exact command with the `timeout` and `background` its call gave, its vault token names beside it; a `pass` payload the `mcp_call` arguments; a `wait` payload the wrapper's request. `Debug` on an action prints lengths only.
  - **`/ok N`** (`actions::approve`) takes the action in one statement (`take_action`), so of two `/ok N` that arrive together (the TUI and Discord) one runs it and the other answers `[zephyr] no proposal #N is waiting: it was never made, is already handled, or is older than 24 h`. While the gateway is paused it answers `[zephyr] paused; /resume first`; a payment while `approvals.strong_only` names `money` needs a strong channel (`[zephyr] approving a payment needs tui or chat or passkey`); a command while all 8 process slots are taken answers `[zephyr] 8 commands are running; /ok N again when one ends`. Each of these leaves it waiting.
    - `run`: the stored command runs word for word, as the agent, through `procs` (the same wrapper, log and limits as `exec`, §4.13, in the agent's home), with the policy veto and its vault tokens' grants checked again now and `gate::agent_env` for the session that asked. Its end reaches main as inbox row `action-<id>`, `[action #7 done; zephyr ran what the owner approved] exited 0 after 3s: email to alice@example.com`, the output quoted and cut as a process report's (§4.13), on the channel of the run that asked, so main tells the owner there; an action held from a task or a job reports to the channel that started it, through main, as task reports do.
    - `pass`: a one-time pass for SHA-256 of the server, the tool and the arguments with their keys sorted, good for 30 minutes; the run that asked is told to make exactly that call again (steered in while it runs, else as main's note), and the gate lets that digest through once.
    - `wait`: the waiting wrapper gets `allow`; the action stays `running` until the wrapper says whether it ran.
    - Under `ask-new`, the owner's `/ok N` remembers the action's targets once it has started (`[zephyr] approved #7 (email to alice@example.com): running it as process #3; the agent gets its report; from now on alice@example.com goes without asking`); `/ok N once` approves without remembering. `/approvals forget N` (any owner channel, since it only makes the gate stricter) forgets remembered target `N` (its `known_targets` rowid, which `/activity grants` lists, §4.19), logged in `settings_log` as `approvals.known.<class>` from the target to none, and answers `[zephyr] forgot alice@example.com for messages; under ask-new a message to it waits for you again`; an unknown `N` is `[zephyr] no remembered target #N; /activity grants lists them`, and a delete whose log row fails still forgets and says so. A delay that runs out never remembers. In any other mode `once` is `/ok N`, and the card offers it only under `ask-new`. An action that did not start is `failed`; the owner's answer and the agent's note say why.
  - **`/no N`**: dropped. The agent is told (`[action #7 declined; zephyr's note, not the owner's words] the owner declined #7 (…); don't try it again`), and a waiting wrapper gets `deny` (`not run: the owner did not approve #7`).
  - **`/cancel N`** is for an action waiting out its delay; a pending one is pointed at `/no N`. It becomes `cancelled`, the agent is told, and a delayed browser wait is denied.
  - **`/held`** lists what waits for the owner or for its delay, newest first: `#7 email to alice@example.com · /ok 7 · /no 7`, or `· sending at 14:05 unless /cancel 7`. The TUI's Waiting tab (§4.3.2) lists the same, with the whole card.
  - **The tick** (the router's 5 s tick): a delay that came due goes as an `/ok` would, and whoever set it in motion is told how it ended (`[zephyr] #7 (…) went at the end of its delay: …`); a due command with no free process slot waits for the owner instead. First its stored payload is read again under the facts and the modes as they are now (`gate::due_check`, R63): a fact found under `hold` (or facts that cannot be read), or a mode that would hold it now (`ask`, `ask-new` with a target not known, a cap it is over) or wait longer, puts it back to `pending`, and the owner is told why and shown its card again (`[zephyr] #7 (…) came due, but approvals.posts is now ask, so it waits for you again`); the same mode or a looser one lets it go. So `/approvals on`, or a fact saved meanwhile, stops a send already counting down. Actions nobody answered expire, `pending` and `scheduled` ones after 24 h and a browser wait after 10 minutes, and the agent is told (`… within a day, so it was not run; ask again if it is still wanted`).
  - **Nothing goes late by itself.** While the gateway is paused (and on the first tick after a budget pause lifts at UTC midnight), at `/resume`, at `/stop` (every delay, due or not, R47) and at start (one that fell due while the daemon was down), a delay goes back to `pending` and its card is shown again (`ask_again`). `/stop` also denies every browser wait, each one's action settled `dropped` so no card is left that can only fail (D10), and kills the approved commands running, which are `procs` processes; held actions stay held. `/pause` denies no wait itself: it aborts the run and stops main's commands, and a wrapper that goes with them drops its action.
  - **At start**, after `procs` adopted what a re-exec handed over: a browser action still waiting (`pending` or `scheduled`) is `failed`, as its wrapper's connection ended with the daemon that held it, and its owner is told (`[zephyr] #7 (…) did not run: zephyr restarted while the browser waited`, D10); an action that was `running` is `unknown`, never run again, unless `procs` still runs its command or finds its exit file (§4.13), and main is told (`[action #7 unknown; zephyr's note, not the owner's words] zephyr restarted while it carried out #7 (…), so whether it went is unknown; it is not run again`).
  - A `delay N` mode is the owner's standing choice: a delayed payment that runs out goes without a strong-channel approval, whatever `approvals.strong_only` says, since that list governs only who may approve (R48).
- **The card** (`gate::card`), on the channel of the run that asked and in the TUI's Waiting tab:

  ```
  [zephyr] approve #7: message (email)
  to: alice@example.com (new) · subject: "Invoice March"
  first lines: "Hi Alice, attached is the invoice for March."
  command: "himalaya message send <<'EOF' To: alice@example.com Subject: Invoice March Hi Alice, attached is the invoice for March. EOF"
  the agent says: "the owner asked me to send the March invoice"
  /ok 7 · /ok 7 once · /no 7 · expires in 24 h
  ```

  Every line but the first and the last starts with a label of the daemon's. The summary is built from the payload, never from the agent's text: a mail's recipients, subject and first lines; a `gh` post's repo and title; a connector call's tool, recipients, amount and arguments; a browser action's origin, page, control, title, what was typed and, for a payment, the total. What came from the agent or a page is on a line of its own, on one line, cut (a subject, first lines, a page, a control's name or typed text at 200 characters; a command or a connector call's arguments at 1500; a command cut adds `not shown: N more characters of the command; /ok 7 runs all of it` and `all it sends:` with every gated stage's summary and every `outbound` label of the whole command, C1), quoted with its quotes and backslashes escaped, and scrubbed of the vault's and the facts' values; none of it is shown when the facts cannot be read, and values a fact is split across are withheld. The agent's reason (main's `exec` only: its latest text in the run) is one quoted line cut at 200 characters. Under `ask-new` a target not approved before is marked `(new)`, and only there is `/ok N once` offered. A fact hold adds `contains your private fact NAME`, never the value. A held `exec` command that names vault tokens shows `vault tokens it gets: "GH_TOKEN"`, names only (C3). The control and direction characters dropped from every quoted or one-line field include the marks U+200E, U+200F and U+061C (D1), and a line or paragraph separator folds to a space. A payment shows `amount: 20 EUR` or `amount: could not be read`; a delayed action starts `[zephyr] delayed #7` and ends `sending at 14:05 unless /cancel 7`; a browser wait `expires in 10 min`; a payment that needs a strong channel to approve says `this one needs tui or chat or passkey`. Lines starting `[zephyr]` in the agent's own replies go out as `[agent]` (§4.4 item 7), so no card can be forged in its text.
- **What the agent sees.** On a hold: `held for the owner as #7 (email to alice@example.com); don't retry it; carry on or end your turn`, as `exec`'s answer or as the note steered in after a vetoed call; on a delay, `delayed as #7 (…): it goes by itself in 5 min unless the owner cancels it with /cancel 7; don't retry it; carry on or end your turn` (C4). A browser action just waits, then runs or exits 1 with why. On a decision: the action's report row, or the decline, cancel, expiry or not-run note (`[action #N WORD; zephyr's note, not the owner's words] …`), once per action. AGENTS.md's fixed `## Approvals` section (`memory::agents_md`, after `## Settings`) says that sending messages, posting publicly and paying wait for the owner when the owner's approval settings say so, that `gateway "/approvals"` reads them, that a held action (`held for the owner as #N`, or `delayed as #N`, which goes by itself unless the owner cancels it) is not to be retried because zephyr runs exactly that action once approved or once the delay ends and says how it went, and that routing around a hold (curl to a mail API, a script, another browser) breaks the owner's rule. It names no mode, so a change needs no child restart.
- **Strong channels.** Loosening an `approvals.*` setting, a connector's class or a private fact needs a strong channel (§4.17), whether the owner types it or approves the agent's proposal: those settings are `strong`, and a fact's `rm` or `allow` is checked in `Router::not_now`. `approvals.strong_only` (default `["loosen"]`; it may add `money`) names what only a strong channel may approve: `loosen` is that rule, which the settings' `strong` flag enforces whether or not the list names it; with `money`, a payment's `/ok` from Discord or iMessage is refused and the payment stays waiting. `money` is off by default, so a purchase can be approved from a phone. The stronger path is the web app: a payment's `/ok` signed there with a passkey is the strong channel `passkey` (§4.3.3), and `zephyr web setup` offers to add `money` once a passkey is enrolled.
- **Audit.** Every decision on a call that sends is an `audit` row (§4.4 item 6), its arguments scrubbed of the vault's and the facts' values and cut to 500 bytes: the gate's `auto`, `known`, `held`, `fact-hold`, `fact-warn`, `pass` and `denied` (the flood cap, a store error, an unreadable browser request), and the owner's and the tick's `approved`, `once`, `due`, `dropped`, `cancelled`, `expired`, `stopped` (a browser wait `/stop` ended), `failed` (one a restart ended) and `re-asked` (put back to the owner, with its card or a notice: a delay come due under stricter settings or with no free process slot, at a pause, `/resume`, `/stop` or a start), these with `#N summary` as their arguments, never the payload. The after-turn outbound list (§4.4 item 3) is unchanged, whatever was decided.
- **`doctor`**, as root in the container: `/opt/zephyr/gate/bin` is first on `AGENT_PATH`, root's and not the agent's to write; its `agent-browser` is this binary; no other `agent-browser` is on the agent's PATH; rpi, this binary, the policy plugin and the real agent-browser are root's, writable by no one else, and under no folder the agent may write (`agent::replaceable`, B5: an agent that could rewrite rpi between child restarts could drop the policy plugin, and `gate_client` trusts a socket served by the program's owner; the image unpacks rpi's tarball with `--no-same-owner`, as gh's and himalaya's, so its `./rpi` is not uid 1001's); and, while the daemon answers, the gate socket is there.
- **Upgrade and `init`.** `Store::open` marks a state.db that existed at a version below 16 when its migrations ran (`meta.upgraded_from`; a brand-new database is not an upgrade). The router's first start after that, with no `[approvals]` table in `zephyr.toml`, writes `approvals.preset = "full"` beside the comment `# kept as before 0.7; /approvals manual turns approvals on`, logs it in `settings_log` as `zephyr` (`manual → full`) and clears the mark; a write that fails leaves the mark for the next start. The owner is told once, `[zephyr] approvals are off, as before this version; /approvals manual or /settings turns them on`, as soon as there is an owner to tell (`meta.upgrade_notice` waits, across restarts, until the agent has taken up a message from one). A fresh install with no `[approvals]` is `manual`. `zephyr init` asks for the preset, showing what each sets (or takes `--preset manual|semi|full`; a re-run keeps an existing `[approvals]` unless `--preset` says otherwise; non-interactive without it leaves the table out), writes the preset as `/approvals PRESET` does (`preset_edits`: a hand-set class looser than it is cleared, a stricter one kept, so a re-run of `init --preset manual` leaves nothing looser behind, D11), and then offers to add facts through the same hidden prompts as `zephyr facts add`.
- **What it does not stop.** The gate stops a confused or prompt-injected agent using zephyr's own tools. A deliberately hostile one can run a copy of the real browser binary, post from a Python script, or reach a mail API over HTTPS with curl and a token it holds. SMTP, IMAP and every other non-HTTP protocol are closed by the network floor (§4.20) unless the owner lists that `host:port`; HTTPS to a public host stays open. Shell forms the classifier does not recognize, a browser label outside the lexicon and a fact inside a file a command sends (an `scp` of a file holding the address) all go through.

### 4.17 Settings

One registry (`settings.rs`, a static table `SETTINGS`) describes every setting the owner or the agent can change, and one function, the router's `set_setting`, changes them. Slash commands on any channel, the host CLI, the TUI's settings panel (§4.3.2, over §4.3.1's `zephyr.settings*` methods) and the agent's `gateway` tool (§4.11) all end there, so a setting added once to the table appears in all of them with the same checks, wording and log. The registry is pure (no I/O, no router types); the texts the owner reads (`changed`, `tightened`, `card`, `reverted`, `stale`, `listing`) are built in it.

- **An entry** has a dotted `zephyr.toml` key, a panel section, a label and a help line, a `Kind`, the agent's `Access`, a `strong` flag, what makes a change stricter (`Stricter`) and how it is applied (`Apply`). Kinds: `Bool`, `Int` and `Float` with bounds, `Duration`, `Choice` (strictest first), `Model` (`PROVIDER/MODEL`), `Text` with a length, `List` (comma-separated names from a fixed set), `Mode(class)` (an approval mode, `approvals::parse_mode`, §4.16) and `Optional(inner)`, where `none` or `default` clears the key. `parse` checks the value against the kind before anything is decided; a model is also checked as `/model` checks one (an account on its provider, listed by that account's `rpi --list-models`). Values stay in `zephyr.toml` (edited by `toml_edit`, comments kept), except the thinking level, which only the router holds (rpi keeps it nowhere), and the subagents and rules, which are lists with their own commands (below).
- **The table.** Read-only means "edit `zephyr.toml`": `set` refuses it and the agent can only read it.

  | Key | Section | Takes | Agent | Loosening needs a strong channel |
  |---|---|---|---|---|
  | `model` | Model | `PROVIDER/MODEL` | propose | no |
  | `thinking` | Model | a level the model offers (off, minimal, low, medium, high, xhigh, max); until the daemon restarts | propose | no |
  | `tasks.parallel` | Background tasks | 1 to 32, lower is stricter | tighten | no |

  `tighten` means a change that is no looser than the value in effect applies at once when the agent makes it, and a loosening is a proposal. A setting with no order (`Stricter::NotOrdered`: a model, a time zone) or a value that does not compare counts as a loosening, so it is `propose` or `never`; `loosens` is true unless `tighter` says so, and `decide` takes it. A setting that is already at the asked value is not looser. `/settings` lists the entries by section; `/settings SECTION` or `/settings KEY` adds the help line, what it takes and who may change it.
- **One write path.** `set_setting(key, raw, actor, until, reason)`:
  1. An unknown key is refused (`no setting KEY; /settings lists them`). `until` on a subagent, a rule, a goal or the persona is refused: those cannot be timed.
  2. `raw` is parsed for its kind (`not changed: …`); a clear (`none`, `default`) skips the parse.
  3. `decide(setting, actor, loosens, strong_channels)`: a read-only entry is refused. The **owner** (`Actor::Owner { channel }`) applies, unless the setting is `strong`, the change loosens it and the channel is not strong: refused as `loosening KEY needs tui or chat or passkey` (the refusal is a row in the change log). The **agent** (`Actor::Agent`) is refused on `never`, applies a tightening on `tighten`, and otherwise proposes. The **revert** that ends a time limit (`Actor::Internal`) always applies.
  4. A proposal is stored in `proposals` (schema v15 adds `key`, `seen` and `strong`) with the command `/set KEY VALUE [for D]` (`/subagent …`, `/rule …` for those two), the value the owner was shown (`seen`) and whether it needs a strong channel. The owner's card (`[zephyr] the agent proposes #12: budget.daily_cost_usd 5 → 8 (for 1d)`, then `the agent says: "…"`, then `/ok 12 · /no 12 · this one needs tui or chat or passkey`) is built by the daemon. What the agent said last in the run is quoted on one line, control and direction-changing characters turned into spaces, cut at 200 characters, so it cannot pass for a line of the daemon's. For a subagent or a rule the card shows the proposed command whole, cut at 1500 characters.
  5. Apply: the file is edited through `toml_edit` and saved only if the whole edited text still loads and validates, then the reload (§4.10) takes the least disruptive `Plan`; a model goes through `switch_model`, the thinking level to the child (checked against its `get_available_thinking_levels`), a subagent through the `/subagent` command, a rule into `RULES.md` with a child restart so the next start reads it, a preset as one update with the hand-set classes it clears (`approvals::preset_edits`, §4.16); `facts` is refused (`change private facts with /facts`).
  6. Log it, set or clear the time limit, and when the agent applied it, tell the owner: `[zephyr] the agent set tasks.parallel 4 → 2 (it says: "…"); /set tasks.parallel 4 puts it back`.
- **The owner's commands** are callers of it: `/set KEY VALUE [for DURATION]` for any registered key (`/set subagent` and `/set rule` point at `/subagent` and `/rule`, `/set goal` and `/set persona` at `/goal` and `/persona`), `/model`, `/thinking`, `/task parallel|model`, `/subagent …` and `/rule …` keep their syntax. A change replies `[zephyr] KEY OLD → NEW`, with ` until HH:MM` when timed and the reload's own words after it; a refusal is `[zephyr] ` and the reason (`settings::is_change` tells the two apart for callers).
- **Strong channels.** `settings.strong_channels` (default `["tui", "chat", "passkey"]`) names the channels that may loosen a `strong` setting. `tui` is the attached terminal client; `chat` is the root-only socket in the state folder (0700), which `zephyr chat` and the host CLI reach the daemon through; `passkey` is a decision in the web app signed with a passkey (§4.3.3), while `web`, the app's session cookie alone, is weak unless the owner lists it. Discord, iMessage, Telegram and Signal are not strong by default, so a stolen session there can tighten a budget but not raise it. `tui` can never be removed (`Config::validate`: `[settings] strong_channels must keep tui`), and the list may name only `tui`, `chat`, `discord`, `imessage`, `telegram`, `signal`, `web` and `passkey`. A proposal that needs a strong channel stays waiting when `/ok` comes from another one (`[zephyr] loosening … needs tui or chat or passkey`), so the TUI or `chat` can still approve it.
- **Approving a proposal.** `/ok N` first re-reads the setting (`not_now`): if the value in the file is not the one on the card (`seen`), the proposal is dropped and the answer says so (`[zephyr] budget.daily_cost_usd is now 6; propose again`), so an approval never lands on a value the owner did not see. For the subagents and the rules `seen` is a SHA-256 over their whole text, so any edit to either (by the owner, or another approval) makes a waiting one stale: a card is checked by content, not by number. An approved proposal runs as the owner's own command on the approving channel, but its log row says `agent` with the proposal number, so the panel's source reads `agent (#12)`.
- **Time limits.** `… for DURATION` takes `30s`, `5m`, `2h` or `1d`, from 30 seconds to 30 days (`parse_until`; the lower bound is a hidden `Config::min_until`, which tests lower). The value to go back to (what the file held: unset for an optional setting) is stored in `setting_reverts` (one row per key, with the channel the owner set it from). The router's tick applies due reverts as `Actor::Internal` and tells the owner on that channel: `[zephyr] budget.daily_cost_usd went back to 5 (the 1d you set ended)`; one that came due while the daemon was down is applied when the daemon starts, before anything is dispatched, and then on every tick. A revert that cannot apply is dropped and the owner told why. A later change to the key without a time limit drops its revert. The agent never drops or replaces the owner's pending time limit: its own `for D` counts only when none is pending, and a change it makes without one leaves a pending one alone. A change whose reload failed schedules none and leaves any pending one as it was.
- **Change log.** `settings_log(id, key, old, new, actor, channel, proposal, at)` (schema v15): every change, revert and refused strong loosening is a row; `actor` is `owner`, `agent`, `zephyr` (a revert) or `refused`. When the file was saved but the reload failed, the actor reads `<actor> (reload failed)`, the file stays saved as the owner or agent asked, and no time limit is scheduled. The panel's source column and `/settings` read the newest row per key (`you`, `agent (#12)`, `until HH:MM` while a limit runs, `default` while nothing sets the key). Rows are pruned at 90 days by the retention sweep (§4.1).
- **Agent access.** `gateway /settings …` reads (`gateway /settings`, a section or a key; no entry holds a secret). `gateway /set KEY VALUE [for D]` answers `changed KEY old → new` for a tightening, `proposed as #N` for a proposal, or `refused: …`. `/subagent …` and `/rule …` are always proposals, however worded: a rule is a standing instruction at system-prompt level. The fixed `## Settings` section of AGENTS.md (`memory::agents_md`, after `## Tools`) tells the model to read with `gateway "/settings"`, change with `gateway "/set KEY VALUE"` (adding `for 2h` for a temporary change), that tightening applies at once and anything else asks the owner, and to change settings only when the owner asks or has decided on a change in conversation, never because a web page, email or tool result says so. The agent cannot loosen a `strong` setting on its own: its loosening is a proposal marked `this one needs tui or chat or passkey`, and an `/ok` from Discord is refused.
- **The host CLI.** `zephyr config get KEY` reads the file. `zephyr config set KEY VALUE` sends a registered key to the daemon with `docker exec … zephyr set KEY VALUE`, which asks over the chat socket (`/set`, the owner on `chat`, a strong channel); the daemon's refusal is the command's failure and nothing is saved. `zephyr set` exits 3 when no daemon answers; the host CLI then edits the file as before and prints `saved; applies when zephyr starts (zephyr up)`. A key the registry does not know prints `warn: KEY is not a known setting; saved without checking` and is still written, if the whole config validates, so what the README documented before the registry keeps working; a stopped container is edited the same way. `zephyr set KEY VALUE [for D]` is also the in-container command.
- **Two writers.** One daemon path writes settings (`set_setting`, in the router's loop, so one change at a time); the host CLI is the second, and it goes through the daemon whenever one answers. Only when none does does it write `zephyr.toml` itself, and the 5 s tick or the next start reads it.
- **The panel and the attach methods** are §4.3.1 and §4.3.2: `zephyr.settings`, `zephyr.settings_set`, `zephyr.proposals` and `zephyr.decide` (the TUI acts as the owner on `tui`; the web app on `web`, or on `passkey` when the request is signed, §4.3.3), and `Snapshot.proposals` for the badge and the Waiting count.
- **The approvals entries** (§4.16) are rows like the rest: `/approvals` is a caller of `set_setting`, the panel's Approvals section edits them, and a timed preset's revert puts back the whole `[approvals]` it replaced (`approvals::snapshot`). An owner's preset that changes or clears a class also drops that class's pending time limit, as any later owner change of a key does; the agent's never drops one.

### 4.18 Private facts (store and matching)

The owner keeps things that must not leave in an outgoing call, such as a phone number or a home address, as private facts (`facts.rs`; the gate that acts on them is §4.16).

- **Store.** `<state>/facts.toml` (root's, 0600, one of `DAEMON_FILES` and `retention::BACKED_UP`), `[[fact]]` tables with `name` (`[a-z0-9][a-z0-9_-]{0,63}`), `kind` (`text`, `digits`, `email`), `value` (one line of at most 500 characters; an email fact holds an `@`) and `allow` (targets the fact may go to, each one line of at most 200 characters). Read fresh on each use; edited with toml_edit under one in-process lock (`facts::edit`). `Fact`'s `Debug` prints the value's length only; notices, audit rows and errors name the fact (`facts::scrub` writes `[fact:NAME]`); a held action's summary, scrubbed when it was held, is scrubbed again with the facts as they are whenever it is shown (every notice and agent note about the action, the store's own reports to main among them, which read the facts file beside `state.db`; `/held`; the `/ok`, `/no` and `/cancel` replies; its audit rows; `zephyr.proposals`, R70), so a fact saved after the hold never shows either; when the facts can't be read only the summary is withheld, and the text still names the action and how to answer it; and a `gateway "/facts add …"` is logged and audited with its value as `[value]` (`facts::redact`): the command read trimmed, as the plugin and the daemon read it, `/facts` and `add` with any whitespace between; its name and kind are kept only when they are a valid name (holding neither the value nor a number of 6 digits) and a valid kind, else it is `/facts add [value]`, and any other `/facts…` that is not well formed is only `/facts …` (A4, B1).
- **Matching** (`facts::found`). NFKC, case folding and whitespace collapsing on both sides, with invisible characters (controls, zero-width and direction marks, U+061C among them, a byte-order mark) left out, so none can split a value; a digits fact is compared digit-only against each run of digits written with the usual separators (spaces, dots, brackets, slashes and dashes), trunk zeros aside and also without a country code of up to three digits (`+1 (555) 010-2345` is `5550102345`, `+82 10…` is `010…`); an email is case-insensitive; text is a substring. A value under 6 digits or 4 characters never matches (and is refused on save). Each value's percent-encoded forms (`%20` and `+`) and `vault::base64_forms` (standard and URL-safe, at each of the three alignments; for a digits fact, of its digit-only value too, A5) match too. NFKC is applied character by character so a match maps back to the text it was found in; a value also counts as found when the whole text, NFKC'd as one, holds the whole value (a decomposed Hangul name, as macOS writes one, against a composed value, D6), and where such a match cannot be placed, `scrub` withholds the whole text (`[withheld: it holds the private fact NAME]`).
- **What is looked at**: the call's own text, for every gated call and every call `outbound` lists; a connector call's argument values, decoded and one per line (so a value split across two arguments still matches their join); and the browser wrapper's typed values. Never the contents of a file a command sends.
- **Allowed targets.** A fact's `allow` list is compared, normalized, with the call's recipient targets only (§4.16): a connector call's `server/tool` is the medium, not a recipient. The fact is skipped only when every recipient is on its list; `unknown` never is, and a call with no recipients (a `curl` POST) is always checked.
- **Modes** (`approvals.facts`, §4.16): `hold` holds the call, its card naming the fact (`contains your private fact phone`), never its value; `warn` lets it go and tells the owner `[zephyr] the agent sent your private fact NAME to TARGETS`; `off` checks nothing. A `facts.toml` that cannot be read holds every call it would have checked, unless `off`.
- **Who changes them.** Values only from the TUI (`zephyr.facts_put`/`_rm`/`_list`, §4.3.1, answered with names, kinds and allowed targets), the host (`zephyr facts`, hidden prompt or one stdin line, writing the file directly, as the owner on the box) or the agent's `gateway "/facts add NAME KIND VALUE"` (§4.11), which applies at once (a new fact only tightens, and it never replaces one) and tells the owner the name: `[zephyr] the agent saved a private fact named NAME; calls holding it follow approvals.facts. /facts lists the facts, /facts rm NAME removes it`. The owner's `/facts` lists names, kinds and allowed targets; the agent's `gateway "/facts"` names and kinds only. `/facts rm NAME` and `/facts allow NAME TARGET` loosen: the owner's only from a strong channel (`[zephyr] loosening the check for a private fact needs a strong channel`), the agent's as proposals whose `/ok` needs one (`Router::not_now`: `[zephyr] #N loosens the check for a private fact: approve it from tui or chat`, and it stays waiting). `/facts disallow NAME TARGET` tightens, from any channel. A chat never takes a value: `/facts add` there points at the TUI's form and at `zephyr facts add`.

### 4.19 Activity

`/activity [today|Nh|Nd] [KIND]` is the daemon's own account of what ran, what left the machine, what waited and what was refused (`activity.rs`). The router answers it outside the queue, as `/held`, so the model never sees the request or writes the answer; the agent's own memory of what it did is not the record.

- **Sources and kinds.** One query (`Store::activity`) over root's `state.db`, a `UNION ALL` over the v16 tables, each row of exactly one kind: `out` (`audit` rows with `tool = 'outbound'`, §4.4 item 3), `refused` (an `audit` outcome `refused`, the policy's veto, or `denied`, the gate's), `tool` (every other call's `started` or `error`), `gate` (every other `audit` outcome: the gate's decisions and the owner's and the tick's answers, §4.16), `setting` (`settings_log`), `proposal` (`proposals` of kind `command`, dated by `settled_at` once decided; one pending over 24 h reads `expired`), `job` (`runs` joined to `jobs`, `(removed)` for a job that is gone), `task` (`tasks`) and `process` (`procs`). A record appears once, at its latest change. A bare `/activity` shows every kind but `tool`, which would bury the rest.
- **The query.** Newest first, from `since` (local midnight in `[timezone]` for `today`, else 1 h to 90 d back; 24 h by default), at most 30 lines (31 are read; a 31st adds `(only the newest 30; /activity KIND or a shorter time narrows it)`). Pages are keyset on `(at, src, id)`, so two rows in one second never overlap or skip, and a row written between two pages changes neither. Only the tables the asked kinds come from are read, each bounded by the window and the cursor itself (`audit` through its `ts` index), so `/activity task 90d` never scans the audit on the router loop.
- **The line.** `WHEN KIND SUBJECT[ STATUS]: TEXT`, `WHEN` being `HH:MM` on today's local date and `MM-DD HH:MM` before it. `STATUS` is left out when `started` and for `setting` (whose subject is the actor), and for an `out` row only once it is `sent`: one still `started` reads `unconfirmed`, so a send that never left never reads as sent; a refusal reads `by the policy` or `by the gate`. Words are read case-insensitively, in either order.
- **Scrubbing at read.** Each text goes through `gate::Scrub`, loaded once per answer (the vault's values, then the facts as they are now, so a fact saved after the row was written is still `[fact:NAME]`), then `settings::one_line(…, 200)`, so agent-written text (a goal, a command) can never start a line of its own. An `audit` row's session is the agent's to forge (gate socket requests name it), so it is scrubbed and cut to 40 too; an unreadable vault or facts file withholds the text (`[output withheld: …]`), and the session too unless it is one of the daemon's own names (`main`, `task-N`, `job-J-R`, `action-N`, with fewer than 6 digits in all, so no digits fact passes for one), while the time and kind still show.
- **Grants.** `/activity grants` is current state, not paged: what still lets something happen without asking, each line ending ` · ` and the command that takes it back. Remembered targets (`messages bob@x.org, known since 11-02 · /approvals forget 4`, §4.16), time limits that loosened something, whose going back is stricter by the registry's own order (`settings::tighter`; a timed tightening such as `/set budget.daily_cost_usd 1 for 2h` is no grant, and its revert would loosen) (`budget.daily_cost_usd until 18:00, then 5 · /set budget.daily_cost_usd 5`, `none` when the key was unset; a revoke is offered only when the value it sends reads as it is, else the line ends `set KEY back by hand` and carries none; a timed preset's value is an `approvals::snapshot`, `then manual; messages=ask`, and its revoke sets the preset its first item names, an unset one (`default`) as `manual`, which is how it reads) and turned-on jobs (`job #3 morning-brief, 0 7 * * *, to discord · /job rm 3`; `/job rm` keeps a removed job's finished runs, which read `(removed)`, and refuses while a run of the job is in progress, whose restart notice needs the job, and a new job's id is past every run's job, so none is dated from them). Targets, names and values are scrubbed and cut as the record is. Not listed: one-time passes (30 minutes, used once) and vault grants (`/vault` lists them, `/vault revoke` takes one back). Empty: `[zephyr] no standing grants`.
- **`stream`.** Rows of kind `out`, `tool` and the policy's `refused` come from rpi's event stream, which a hostile agent can forge (§4.4 item 3); every other row is the daemon's own state.

### 4.20 Network floor

The agent's uid has no direct network. It reaches its own loopback, and through it one proxy in the daemon, which connects only to public addresses on ports 80 and 443 and to the exact `host:port` entries the owner lists (`egress.rs`). Before this the container ran `--network host`, and every process the agent started could reach the host's loopback (zephyr's own attach port and webhook among them), the LAN, the tailnet, cloud metadata at 169.254.169.254, the host's abstract unix sockets and any raw protocol. The floor closes all of that. It does not stop a leak to a public HTTPS host (§4.4 item 3 still holds); what it carries there no longer includes a vault token, which §4.21 takes away from the agent on top of this proxy.

- **The container** (`host/mod.rs` `up`). host.toml's `network` is `"bridge"` (the default, also when the key is absent, so an upgrade moves an install) or `"host"`; anything else fails `up` with `network in host.toml must be "bridge" or "host"`. In bridge mode `up` makes a user-defined bridge network named after the container when `docker network inspect` finds none (no `--ipv6`, no fixed subnet; `uninstall` removes it) and runs the container with `--network <container> --hostname zephyr --cap-add NET_ADMIN --cap-add SETPCAP -e ZEPHYR_NETWORK=bridge` and one `-p 127.0.0.1:<port>:<port>` for each port in `egress::published` (the attach port, the iMessage webhook's). `ZEPHYR_NETWORK=bridge` is the only switch inside the container (`egress::bridge`). In host mode the arguments and the daemon are exactly what they were: no proxy, no rules, listeners on `127.0.0.1` and `listen`.
- **The rules** (`egress::ruleset`, loaded by `supervise`). Before it starts the first daemon, `supervise` pipes the rules to root's `/usr/sbin/nft -f -` (`egress::load_floor`):

  ```
  table inet zephyr
  delete table inet zephyr
  table inet zephyr {
    set allow {
      type ipv4_addr . inet_service
    }
    chain output {
      type filter hook output priority filter; policy accept;
      meta skuid <agent uid> jump agent
    }
    chain agent {
      ip saddr 127.0.0.11 reject            # never as Docker's DNS: root's lookups cannot be answered by the agent
      ct state established accept           # replies on connections made to the agent (x11vnc, a dev server the owner opens)
      ip daddr 127.0.0.11 reject            # Docker's embedded DNS: the agent gets no resolver
      ip daddr 127.0.0.0/8 accept           # its own servers, and the proxy at 127.0.0.1:7792
      ip6 daddr ::1 accept
      ip daddr . tcp dport @allow accept    # network.allow, as supervise resolved it (egress::keep_allow)
      meta l4proto tcp reject with tcp reset
      reject with icmpx admin-prohibited
    }
  }
  ```

  The jump is on the agent's uid rather than an accept on "not the agent", so a packet with no socket (a kernel reset) falls through to `policy accept`. TCP is reset, so a `connect` fails at once with `ECONNREFUSED` instead of retrying until it times out. There is no port list: the daemon's listeners are on the container's own address, so the only thing of root's on loopback is the proxy, which `doctor` enforces (§4.8). The `allow` set holds the direct routes of `network.allow` (below) and is empty until the owner lists something. The first rule is there because any local process may bind 127.0.0.11, the address of Docker's resolver: without it the agent could answer a lookup root makes there, and so choose the address a listed name gets. `route_localnet` is never set and nothing is DNATed to loopback. A container start is a fresh network namespace, so the rules load once per start and outlive a daemon crash or re-exec. The agent cannot change them: it is not root, has no capabilities, runs under `no-new-privileges`, and Docker's seccomp profile refuses it user namespaces.
- **NET_ADMIN stays with `supervise`.** `PR_CAPBSET_DROP` needs SETPCAP, which is why `up` adds it. `supervise` drops NET_ADMIN and then SETPCAP from the bounding set of each daemon it starts, between fork and exec (`egress::drop_net_admin`, in `pre_exec`: the drop is per thread, and `supervise` runs on several), so the daemon and all it starts hold SETUID, SETGID and KILL as before. `supervise` keeps NET_ADMIN, to load the rules once and to keep the `allow` set afterwards; it runs nothing but the daemon and root's `nft`. `docker exec` processes, which are the owner's, still have both.
- **Fail closed.** If the rules do not load, `supervise` prints `network floor could not be loaded: <nft's error>; network = "host" in host.toml runs without it` and exits 1 without starting the daemon (`Policy.floor`); Docker's restart policy retries, the HEALTHCHECK fails and `zephyr alert` fires. The daemon also checks for itself before it starts anything for the agent (`egress::verify`): the container has an address of its own, its `CapEff` lacks NET_ADMIN (`the daemon still holds NET_ADMIN`), and `zephyr __netcheck`, run as the agent, is refused a direct connection to `1.1.1.1:443` within 2 s. Otherwise `run` exits non-zero.
- **The proxy** (`egress::serve`, in the router's `select!`, bridge mode only) listens on `127.0.0.1:7792` with hyper: at most 256 connections at once, one more closed at once; 10 s to send a request head; one request per connection. It takes `CONNECT host:port`, which it tunnels after `200`, and absolute-form `http://host[:port]/path`, which it sends on in origin form over a new connection with `Proxy-Authorization` and `Proxy-Connection` removed and `Host` set to the URI's own authority. Anything else gets `400`: an origin-form request, `https://` or another scheme in absolute form, a `CONNECT` without a port, userinfo. It follows no redirects; a client that follows one sends a new request, checked the same way. Nothing holds a slot for ever: a tunnel is closed after 30 minutes with no byte moving either way (websockets and event streams ping far more often, and an IMAP IDLE is renewed within 29), a forwarded request's server has 5 minutes to start its reply (longer than a long-poll waits, and the client's upload is inside it, answered `502 zephyr: the server did not answer`), and a forwarded reply whose body stops for 30 minutes is cut. A client that stops reading its reply is not timed. Only the agent's own egress can be used up: the daemon's channels do not go through the proxy. Telegram's long poll, sends and file downloads are the daemon's own connections, made directly to `api.telegram.org`, as Discord's are. signal-cli's connections are the daemon's own too (a root child, §4.3), made directly under the floor.
- **The destination check** (`egress::target`, `egress::decide`), in this order:
  1. The host is read as a browser reads it (WHATWG, through `url`), so `2130706433`, `0x7f.1`, `0177.0.0.1` and `127.1` are all 127.0.0.1, and names are lower-cased and IDNA-mapped. The port is taken from the text, never from `Url::port`, which drops a default one.
  2. The port is 80 or 443, or this exact `host:port` is in `network.allow`. Otherwise `403 zephyr: port <p> needs network.allow`, before any lookup.
  3. An IP literal is used as it is. A name is resolved by the daemon (`tokio::net::lookup_host`, 5 s), never by the agent; no answer is `502`.
  4. Every address must be public (`egress::public`). For a listed entry it may instead be private (`egress::private_ok`: 10/8, 172.16/12, 192.168/16, 100.64/10, fc00::/7). Loopback, link-local, unspecified, multicast, broadcast and the container's own address are never allowed, listed or not. **If any address fails, the whole request is refused**, so an answer mixing a public and a private address gets nowhere and the public one is never tried.
  5. The proxy connects to those checked `SocketAddr`s in order, 10 s each, and to nothing else: it never hands a name to `connect`, so nothing is resolved a second time between the check and the connection (DNS rebinding).
- **What is public.** Two tables in the source, each line citing its RFC from the IANA special-purpose registries. IPv4 is public unless it is in 0/8, 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.0.0/24, 192.0.2/24, 192.88.99/24, 192.168/16, 198.18/15, 198.51.100/24, 203.0.113/24, 224/4 or 240/4. IPv6 is public only inside 2000::/3 and outside 2001::/23 (Teredo among it), 2001:db8::/32, 2002::/16 (6to4) and 3fff::/20. IPv6 is an allowlist so that every form carrying an IPv4 address (`::ffff:127.0.0.1`, `::127.0.0.1`, NAT64 `64:ff9b::/96`) is refused with no unwrapping step that could be got wrong; so are `fe80::/10`, `fc00::/7` and `ff00::/8`.
- **Refusals** answer with the reason in the status line, where `curl -v` and a library's error show it: `403 zephyr: private address 10.0.0.5` for an address that is not listed, `<ip> is never allowed` for a listed one that is never allowed (`loopback is never allowed` when it is loopback). The body adds `the owner can allow HOST:PORT in network.allow; propose it with gateway /set network.allow`.
- **`network.allow`** is one registry row (§4.17): exact `HOST:PORT` entries, comma separated, checked by `egress::parse_allow` (a port from 1 to 65535; no `*`, no scheme, no literal that is never allowed). The agent may only propose it, and loosening needs a strong channel, so "deny, and only the owner allows" runs on the proposal path that already exists. The proxy reads the live config on each request, so a change applies to the next connection. Typical entries: `imap.gmail.com:993`, `smtp.gmail.com:465`, `github.com:22`, `homeassistant.lan:8123`.
- **Direct routes for listed entries** (`egress::keep_allow`, a task of `supervise`). A program that speaks no proxy (himalaya, `ssh` without a `ProxyCommand`, a database client) could not use an entry the proxy alone honoured, so each entry is also a direct route. `supervise` does this, not the daemon, because only it holds NET_ADMIN. Every 5 s it reads `network.allow` from zephyr.toml (by key; a file it cannot read, or a list the daemon would refuse, changes nothing), and when the value changed, or an hour has passed, or a minute while some entry has no route, it:
  1. resolves each listed host (`egress::routes`) under the rule the proxy applies to a listed entry (`egress::refused`): every address public or private, none loopback, link-local or the container's own, or the host gets no route at all, and the reason is logged (`network.allow has no direct route for <host:port>: <reason>`). Names are asked of the nameservers in `/etc/resolv.conf` with a small A-record query of its own (`egress::dns_lookup`), never through `/etc/hosts`, which would answer with the lines written below for ever;
  2. replaces the `allow` set with the `address . port` pairs, in one `nft` transaction, so a removed entry's route goes with it. TCP and IPv4 only, as the rule and the container's network are;
  3. rewrites its own lines of `/etc/hosts` (marked `# zephyr network.allow`, written in place because Docker mounts that one file): one per listed name, on an address that is in the set. The agent still has no resolver; a listed name resolves, to the address its route is for, and nothing else does. Root's lookups read the same line, so the proxy and the direct route agree on the address.
  A direct connection is not in the audit (the proxy's rows are); what it can reach is exactly the pairs in the set, which `nft list set inet zephyr allow` shows. Between refreshes a name keeps its address for up to an hour.
- **What the agent's processes get** (`agent::cmd`, in bridge mode): `HTTP_PROXY`, `HTTPS_PROXY`, `http_proxy`, `https_proxy` = `http://127.0.0.1:7792`; `NO_PROXY`, `no_proxy` = `localhost,127.0.0.1,::1`; `NODE_USE_ENV_PROXY=1`, without which Node 24's `fetch` ignores them; and `,--proxy-server=http://127.0.0.1:7792` appended to `AGENT_BROWSER_ARGS`, so Chromium does not depend on finding the variables. No `ALL_PROXY`: rpi 0.18 refuses a proxy URL that is not HTTP. The image's `ENV` cannot hold these, since it also serves host mode. Every agent spawn goes through `agent::cmd`, and the host's `docker exec` as the agent (`zephyr shell`, `login`, `--list-models`) passes the same variables (`agent::PROXY_ENV`). `git`, `curl`, `wget`, `pip`, `uv`, `npm`, `cargo`, `gh`, rpi and its plugins, agent-browser and Camoufox work through the proxy. What ignores the variables or speaks another protocol fails at once instead of leaking: `ssh`, `scp`, `rsync` over ssh, SMTP and IMAP clients, and any lookup of a name that is not listed, until the owner lists the destination, which then connects directly within a few seconds (above). `dig` and `ping` never work: there is no resolver and no ICMP. A model server on the host's loopback is no longer reachable: the owner has it listen on the bridge gateway and lists that `address:port`.
- **Listeners** (`egress::listen_addr`). In bridge mode every daemon TCP listener binds the container's own address, the `zephyr` line Docker writes to `/etc/hosts` (`egress::own_ip`: IPv4 and not loopback, or the daemon does not start), with the port its host-mode address names; `zephyr tui` and stock `rpi --connect` connect there (the host reads the address with `docker inspect`). The agent's uid is refused that address like any other. Docker publishes each port on the host's `127.0.0.1` only. The web app's port (§4.3.3) is one of them, fronted with `tailscale serve`. The iMessage webhook is published the same way, never on the Tailscale address, which Docker could not bind when tailscaled starts after it: the owner forwards it once with `sudo tailscale serve --bg --tcp <port> tcp://127.0.0.1:<port>`. That line is printed by the `up` that moves a container off host networking, not by later ones. A changed port means a new container: `zephyr config set` and `zephyr channel` run `up` when the published ports changed and the running container is under the floor (`Host::apply_published`; the host reads the ports from zephyr.toml key by key, `egress::published_from`, so a key from a newer zephyr does not stop it). `up` tells the container what it publishes (`ZEPHYR_PUBLISHED`), and a daemon that has listened for a minute on a port not among them, after a hand edit, tells the owner once `[zephyr] <key> changed; run zephyr up on the host to publish it` (`egress::unpublished`). A new listener adds one row to `egress::LISTENERS` and binds through `listen_addr`. Unix sockets (the chat socket, the gate's) are unaffected.
- **Sign-ins and the desktop.** An OAuth provider's redirect to `127.0.0.1` no longer reaches the container; the owner pastes the address the browser could not open (§4.7.1). The container's network namespace is its own, so the host no longer sees the desktop's abstract socket (§4.11); a VNC server listens on the container's address, and its replies leave through the `ct state established` rule.
- **Audit.** Rows go to the `audit` table as session `net`, tool `connect` or `http`, args `host:port -> ip` (the address connected to; `host:port`, or what was asked for, on a refusal) with vault and fact values scrubbed and cut to 500 bytes, since a hostname can carry one. A refusal's outcome is `refused: <reason>`, a 400 and a 502 included, and its reason never repeats the agent's text. At most 60 are written a minute; when the minute ends, one row with tool `proxy` and no destination counts the rest (`refused: N more`), so a looping agent cannot fill state.db. One thread writes the rows (`write_audit`): it owns the cap, reads the vault and the facts and writes state.db, so none of that runs on the runtime the proxy serves from. An allowed destination is written as `allowed` once per `host:port` and hour (kept in memory, so again after a daemon start): a browser's hundreds of connections become a list of where the agent went. Rows say `net`, not which run made the connection.
- **When things fail.** Proxy down (a failed bind, a daemon crash, a re-exec): the agent's connections are refused, since nothing else listens on 7792, and open tunnels close with the daemon; a failed bind is told once, `[zephyr] the network proxy is down, so the agent has no internet: <error>`, and the daemon goes on. If the agent binds 7792 itself while the daemon is down, its processes talk to its own proxy, which has no route out either. A lookup that fails or times out is `502` and an audit row.
- **Migration.** The first `up` or `upgrade` reads the old container's network mode before it steps aside and, if that was `host`, prints once: `the agent now reaches the internet only through zephyr's proxy: ports 80 and 443 to public addresses (DESIGN §4.20). Other destinations: /set network.allow HOST:PORT. Sign-ins: paste the address the browser cannot open. To go back: network = "host" in host.toml, then zephyr up.` Nothing in the agent's home or state.db changes (no schema version); `init` writes `network = "bridge"` with a comment naming the way back.
- **Decided with the owner.** Upgrades default to `bridge`, and one host.toml line goes back. The webhook is published on host loopback and fronted with `tailscale serve`, with no boot-order dependency on tailscaled. Only ports 80 and 443 need no entry. The host's own public address on a VPS stays out of scope (§7).
- **Not done.** Host-side rules as a second layer against a compromised root in the container; TLS interception, SNI or Host matching and anything else against a leak to a public HTTPS host, except for the hosts a token is bound to, which §4.21 decrypts; an in-flight ask (a request is refused and the agent proposes an entry instead); attributing a connection to a run; byte counts and rate limits; SOCKS, PAC and HTTP/2 to the proxy; IPv6 egress.
- **Tested** in `egress.rs` (the address tables, host normalization, the allow list, the proxy against a local upstream with the address check passed in, its timeouts, the audit, the rule set's text, the direct routes with their set, hosts lines and DNS packets, the `/proc/net` reader), `supervise.rs`, `agent.rs`, `tests/host.rs` and `tests/login.rs`, and against a real container by the ignored `tests/net_floor.rs`.

### 4.21 Token broker

A vault token or a connector's secret reaches the agent as a stand-in, and the proxy of §4.20 puts the real value in only on the hosts the owner bound it to (`broker.rs`, `ca.rs`). Before this a token the agent was allowed to use was in its environment, and a connector's in `mcp.json`: one `curl` to any public host took it away.

- **Surrogates** (`broker::surrogate`). `zsur_` and 40 hex digits: the first 20 bytes of HMAC-SHA256 over the kind (`token` for a vault token, `env` for a secrets.env name a connector uses), a zero byte and the name, keyed with 32 random bytes in `<state>/broker.key` (root's, 0600, made on first use). Derived, not stored: there is no table, it survives a re-exec (so a command `procs` adopted and the `mcp.json` a child loaded keep working), and it depends on the name alone, so a changed value needs no restart. Its alphabet passes through URLs, JSON and shells unchanged. It is worth nothing outside the container; deleting `broker.key` and restarting retires them all. `vault::scrub` hides a surrogate, and its base64 forms, as `[vault:NAME]` (`broker::secrets`), so the agent reads the same text as before.
- **Bindings** (`broker::parse_host`). `HOST` or `HOST:PORT` (443 when absent), read through `egress::target`: a name, never an address, a wildcard, a scheme or a path. Exact means exact: `github.com` does not cover `api.github.com`, and `*.github.io` would reach a page anyone can publish. A vault token's are `hosts` on its `[[token]]`, with `url` (also swapped in the path and query) and `raw` (handed out as its real value); a connector's are `hosts` on its `[[mcp]]`, or its own `https` URL's host when it lists none.
- **The map** (`broker::Map`): surrogate to name, value, hosts and `url`, for every token that is not `raw` and every `${NAME}` of a connector that is not `secrets = "plain"`, bound to the union of the hosts of the connectors that use it. The values are in the daemon's memory only; its `Debug` prints names.
- **The swap** (`broker::swap`, pure) works on a request's head only. A surrogate is replaced **only in a credential header**: `Authorization` for every secret, the headers the owner listed for a token (`headers` on its `[[token]]`: `/vault header NAME X-Api-Key`, a loosening; `/vault unheader NAME [HEADER]`; `--header` on the host), and for a connector's secret the headers its own `[[mcp]] headers` put it in. In any other header it is refused, `403 zephyr: NAME is not swapped in a header that is not a credential header`, never swapped and never sent on as it is, with an audit row and a notice to the owner (one per token and host an hour). The header's name is the agent's text, so it is in none of those but the audit's args (`NAME -> host:port (header NAME)`, scrubbed and cut like any): a server may send a header it does not know back, or log it, and `User-Agent`, `Referer` or a forwarding header are the agent's to fill. `Authorization: Basic` is decoded first and encoded again (`git` and `curl -u` send a token that way); the path and query only for a token with `url`, else `403 zephyr: NAME is not swapped in URLs`. A token bound elsewhere is `403 zephyr: the vault token NAME is not sent to HOST`, a `zsur_` that is no token `403 zephyr: unknown vault surrogate`, and a value that cannot be written into a header is refused by name rather than sent cut. A refused request is changed nowhere. **Request bodies are never swapped or scanned**: a bound host that stores what it is sent (an issue, a paste) could show the real token to anyone who reads it there, and swapping would mean buffering and re-framing every upload; a token an API wants in a body is `raw`. **Replies are swapped back** (`broker::unswap`, `Map::unswapper`, `egress::Unswapped`): in a reply from a decrypted host, every real value bound to that host, whether this request carried it or not, is turned back into its surrogate, in the headers, the body and the trailers; so is every other text a value turns into when a server encodes it (`broker::encodings`, worked out once when the map is built: base64 at every alignment; the value as each kind of JSON encoder writes it, `broker::json_forms`, at most 192 forms, every combination of what an encoder may do, so serde's and JavaScript's, Python's, PHP's, Go's (`& < >` and the line separators as `\uXXXX`, never `'`) and .NET's are each among them: `/` raw, `\/` or `\u002f`; `& < >`; `'` with `+` and a backtick; everything not ASCII, with DEL; the line separators; `"` as `\"` or `\u0022`; the hex in either case; and percent-encoding of everything, of a URI component and of a form field, in either case), and a Basic credential this request carried goes back to exactly the one the agent's program wrote (`Swapped::sent`: `curl -u x:$TOKEN` sends base64 of the value, which an echo would otherwise hand over). The status line's own text is dropped for the status's usual words, so a host that sends back what it was sent (an echo endpoint, an error page that prints the request, a `Location` that repeats the URL) does not hand the agent the token. For that the proxy asks for the bytes as they are (`Accept-Encoding: identity` replaces the client's on every request to a bound host), and a reply that comes encoded all the same (`Content-Encoding` other than `identity`, or a `Transfer-Encoding` beyond `chunked`) is not passed on unread: `502 zephyr: HOST sent a reply zephyr cannot read (compressed)`, with an audit row. The body still streams: `broker::Replacer` holds back only an end that could be the start of a value, so a value cut across two frames is caught and nothing else waits. A surrogate is not as long as its value, so `Content-Length` is dropped and the reply goes to the client chunked (a `HEAD`, `204` and `304` keep theirs). A value shorter than 4 characters is not looked for, as in `vault::scrub`.

- **The CA** (`ca.rs`, `rcgen`). `<state>/ca/` is root's, 0700, with `ca.key` (0600), `ca.pem` and `expires`; `<state>` is closed to the agent (§4.4). ECDSA P-256, `CA:TRUE` with path length 0, valid 398 days, subject `zephyr token broker (this container only)`. It is not one of `DAEMON_FILES`: the host CLI has no use for it. **It is made and renewed only at a container start** (`ca::ensure`, from `supervise`): when there is none, or it has under 180 days left, a new one replaces the old key. Every process of the agent's starts after that, so none holds a trust file older than the CA in use; a rotation under running processes would need an overlap period and restarts. `shortcut:` the expiry is read from `expires`, written with the certificate, not parsed out of it; a missing or unreadable one reads as no CA.
- **Leaves** (`ca::Authority::leaf`). One P-256 leaf key per daemon run, in memory. A leaf carries the bound host as its only name, is valid from the day before for 30 days, offers ALPN `http/1.1` only, and its `rustls::ServerConfig` is kept by host until a day before it ends. Nothing but a bound host is ever signed, so the map cannot outgrow the bindings.
- **What the proxy trusts upstream** (`ca::public_roots`): the `webpki-roots` compiled into the binary, and nothing a file, a variable or the system bundle says. The container's own CA is in that bundle, and so would be one the agent planted; neither is here.

- **Using a token** (`vault::exec_env`). After the grant check, a `raw` token is handed out as its value, a bound one as its surrogate, and one bound to nothing is refused (`not run: the token NAME is bound to no host; ask the owner with vault bind`). The `programs` grants stay: they decide which command is first handed the surrogate, not who may use it afterwards. If `broker.key` cannot be read the call is `not run`; the real value is never used in a surrogate's place. **Under host networking** there is no proxy to swap anything, so tokens are handed out as before (`broker::on`).
- **Who binds.** Only the owner, **from a strong channel** (`[settings] strong_channels`, as the connectors' `hosts` and `secrets` rows), and in the web app only on a card signed with a passkey, whatever `strong_channels` says (`may_approve`, as a grant): `/vault bind NAME HOST..` (answering, per new host, `HOST is now decrypted by zephyr for every program the agent runs`), `/vault header NAME HEADER..`, `/vault url NAME on`, `/vault raw NAME on`, and the hosts field where a token is saved (§4.15: the TUI and the host CLI). On another channel they answer `sending a vault token to more hosts, in URLs or as its real value needs a strong channel`, and the `/ok` of the agent's `bind` proposal stays waiting there (`#N sends a vault token to more hosts: approve it from …`, `Router::not_now`). `/vault unbind`, `/vault unheader`, `/vault url NAME off` and `/vault raw NAME off` tighten and are taken anywhere. `Vault::put` keeps a token's hosts across a new value and never sets `url` or `raw`. The agent's `vault bind` is a proposal; `gateway` still refuses `/vault`.
- **Upgrade.** Nothing is rewritten and no value moves. A token saved before the broker has no hosts, so its next use is `not run` until the owner binds it or marks it `raw`; its grants are kept. Once, when there is an owner to tell (`meta` key `broker.upgrade_told`, set only after the vault was read and the notice stored), the daemon lists each such token with its `/vault bind NAME HOST..` line and the way back, `/vault raw NAME on`.

- **Connector secrets** stay in secrets.env. `[[mcp]]` has `hosts` (comma separated, the same entries) and `secrets = "surrogate" | "plain"`. **A connector holds its real secrets only when the owner wrote `secrets = "plain"`** (`broker::plain`); it is never implied. A `command` connector otherwise holds stand-ins. A `url` connector cannot use one: its requests are made by rpi's own MCP client (`librpi_mcp_adapter`), which trusts only the roots compiled into it and so cannot reach a host the proxy decrypts. Checked in a real container with rpi 0.21.2: `mcp_list` against an HTTPS connector on a decrypted host failed with `MCP HTTP request failed: error sending request`, and reached the server once the host was a tunnel again. So for a remote connector that names a secret the owner has two honest choices, and until they make one it is **not published** (`broker::undecided`; `/mcp` and `doctor` name it): `secrets = "plain"`, the real secret in `mcp.json` where the agent can read it (§7), its host a plain tunnel; or `secrets = "surrogate"`, a stand-in bound to its URL's own host, for an rpi whose client can be given a root (with 0.21 its calls fail, and `doctor` says so). **The upgrade** keeps what was there: once (`meta` `broker.remote_kept`), at the first start on a state.db from before the broker, each remote connector with a secret and no `secrets` key gets `secrets = "plain"` written (`Router::settle_remote_connectors`), logged in `settings_log` as `zephyr`'s and told to the owner with the upgrade's notice. "From before the broker" is a state.db without the mark `broker.born`, which `Store::open` writes when it makes a database (`Store::made_with_broker`; a mark that cannot be read counts as there, so nothing is settled on a guess): the broker has no schema step, and `upgraded_from` marks only a move from before v16, so neither could tell. That it was done is also a file of the daemon's own, `<state>/broker-settled` (root's, 0600), written once the edit succeeded or there was nothing to settle, and the upgrade runs only while all three say it has not: no `broker.born`, no `broker.remote_kept`, no such file. The file is outside state.db, so a state.db from before the broker that is put back later (a restored backup) settles nothing more; and it is not in `zephyr.toml`, which is written only when a connector actually gets its `secrets = "plain"`. **Going back to 0.8.0:** its config refuses keys it does not know, and `secrets` and `hosts` on `[[mcp]]` (like `hosts`, `headers`, `url` and `raw` nowhere but in `vault.toml`, which 0.8.0 reads leniently) are new with the broker. `zephyr upgrade 0.8.0` restores the `zephyr.toml` it backed up before the upgrade, so it is unaffected; an image pinned back by hand over a `zephyr.toml` that holds either key does not start until they are removed. A first start, or a state.db made anew, settles nothing. One added later is the owner's to settle: `zephyr mcp add NAME --url … --plain` on the host (without `--plain` it is refused, with the reason), or `/set mcp.NAME.secrets plain` from a strong channel. **One name, one way:** a secrets.env name that one connector holds as it is and another as a stand-in would let the agent read from the first what the second keeps from it (`broker::shared`): neither connector is published, `doctor` fails, and the owner is told at each start. One check refuses the change that would make a secret's name held two ways where it was not (`broker::creates_pair`, comparing those names before and after, so fixing or removing one of several stand-ins passes; with no config that loaded before, the new one alone must hold none): in `/set`, `zephyr config set`, `zephyr mcp add` and `/mcp ok`. A pair that is already there (a hand edit) does not stop an unrelated change. `drafts::prepare` fills each `${NAME}` from `broker::connector_secrets`: the surrogate for each name, or the real value for a `plain` connector, so `mcp.json` is byte-identical from one start to the next and holds no brokered secret. A `url` connector the owner set to `surrogate` and gave no `hosts` is bound to its own URL's host. A connector that holds stand-ins, names a secret and has nowhere to send it (a `command` connector with no `hosts`, or a `surrogate` one on a plain `http://` URL, which the proxy never swaps) is left out at start, as one missing a secret is, and `/mcp` says why with the two ways on: `/set mcp.NAME.hosts HOST..`, or `/set mcp.NAME.secrets plain` for a database password or a signing key. Both are strong registry rows (§4.17): the agent proposes, the owner approves on a strong channel. A secret named in the connector's `url` is swapped in the request target too; one named only in `headers`, `env` or `args` in headers only. A draft can carry neither `hosts` nor `secrets` (`a connector draft cannot set hosts; the owner sets it with /set mcp.NAME.hosts`), and an approved update keeps the owner's: `/mcp ok` is taken on any channel, and these are strong settings, so the agent proposes them with `gateway` `/set mcp.NAME.hosts`. And since everything about a connector decides where its secret goes (its URL, its headers, its command, its environment), **`/mcp ok` needs a strong channel for any draft whose connector names a `${SECRET}`, or that replaces a connector that does** (`connector NAME carries a secret (X), and a draft decides where it goes; approve it from a strong channel (…)`; the draft waits). A weak channel approves only drafts with no secret in them, old or new. An approval never writes `secrets = "plain"`: a new remote connector with a secret is added and stays unpublished, and the reply says why and names what works (`/set mcp.NAME.secrets plain` from a strong channel, or `zephyr mcp add NAME --plain` on the host). The upgrade's notice (above) also lists each connector left out.

- **The proxy's path for a bound host** (`egress.rs` `Conn::serve_tls`, `Decrypted`). `Conn::answer` is as in §4.20 up to the connect: `target`, `decide`, then a connection to the checked addresses. A `CONNECT` whose `host:port` some secret is bound to (`Map::bound`) is then decrypted in place of tunnelled, and only such a host: every other one is the plain tunnel of §4.20, byte for byte.
  1. After `200` the proxy accepts TLS from the client with the host's leaf. If the client's handshake names another host (SNI), every request on the connection is answered `403 zephyr: Host does not match HOST`.
  2. It starts TLS to the already connected, already checked address: SNI is the bound host, and the certificate must verify for that name against `Floor::roots` (`ca::public_roots` when live; tests pass their own). If it does not, every request gets `502 zephyr: HOST did not prove it is HOST` and nothing else is sent.
  3. HTTP/1.1 is served to the client with keep-alive and sent on over that client connection's own upstream connection (made at its `CONNECT`, never pooled or shared with another client's), each request waiting its turn. When the upstream connection ends, the client's is closed after the reply in flight, so the next request starts with a new `CONNECT`, checked afresh. `shortcut:` one timer covers a request head and the wait for the next request, 90 s.
  4. Per request: exactly one `Host`, naming the bound host with or without its port, or `403 zephyr: Host does not match HOST` (a bound host on a shared CDN would otherwise carry the token to another customer's origin); the target is put in origin form; then `broker::swap` with the map as it is now (`broker::Maps`: three `stat`s, the files read again only after an edit), so an `/vault unbind` holds for the next request on a connection opened before it. Before the swap, what belongs to one hop is removed, on the request and on the reply (`egress::hop_by_hop`, RFC 9110 §7.6.1: `Connection` and every header it names except `Host` and the body's framing, `Keep-Alive`, `TE`, `Upgrade`, `Proxy-Authorization`, `Proxy-Connection`; not `Trailer`, which describes the message), and so are `Range` and `If-Range`: the whole reply is asked for, so a value is not cut where the client chose. Bodies pass as hyper frames, never collected, so uploads, downloads and event streams keep their timing; `reply_wait` and `idle` apply as on the forwarded path. `Trailer` is the message's and stays; a reply's trailers reach the client with their values turned back like a header's (the proxy asks for them with its own `TE: trailers`). When the server ends its connection with a reply (`Connection: close`, or the connection is gone), the reply to the client says `Connection: close` too, so hyper does not offer to keep a connection the proxy has no upstream for, and the client reconnects with a new `CONNECT`. A reply whose header **name** holds a bound value of 8 characters or more, or a form of it that long, is refused (`502 zephyr: HOST named a header after a vault token`): a name cannot become a stand-in and stay a name. A trailer's name that does ends the body there, unfinished, with its audit row. A reply that is not the whole body as the server wrote it is refused with `502` and an audit row: `101` (`HOST switched protocols`), `206` (`HOST sent a part of a reply`) and an encoded one. **No websocket is carried on a decrypted host**: its frames would pass unread.
- **HTTP/2 and websockets.** Both legs offer `http/1.1` only, so clients fall back. gRPC, which needs HTTP/2, and a websocket fail on a bound host; such a token is `raw`.
- **DNS rebinding of a bound host** has two locks: `decide` resolves once and refuses any private answer, and the connection is to the checked address (§4.20); and an address that is public but not the host's cannot present a certificate for the bound name under public roots, so step 2 fails before any request is read.
- **A surrogate on its way anywhere else** (`broker::scan`). The proxy looks for `zsur_`, and for a surrogate's base64 forms, in the three places it can see one without decrypting: the host name of any request (before any lookup, which alone would carry it out), and the target and every header of a plain `http://` request, which is never swapped. A token that exists gets `403 zephyr: the vault token NAME is not sent to HOST` (`that host` when the name itself holds the stand-in), nothing is connected, and the owner is told, once per token and host an hour and at most ten times an hour: `[zephyr] the agent tried to send the vault token NAME to HOST, where it is not bound. Nothing was sent.` The notice names no command: the answer to an attack should not be one tap from allowing it. `shortcut:` it leaves with the router's next tick. A `zsur_` that is no token gets `403 zephyr: unknown vault surrogate` and no notice.
- **What the proxy cannot see** is a `CONNECT` tunnel to a host nothing is bound to. A surrogate sent there arrives. That is accepted, and it is why surrogates exist: what arrives is a string no one outside the container can turn into anything. Seeing it would mean decrypting every host, which breaks every pinned client and reads all of the agent's traffic to stop the theft of a worthless string.
- **A bound host that is also in `network.allow`** keeps its direct route (§4.20). A program that connects directly skips the proxy, sends the surrogate, and is refused by the server; nothing leaks.
- **Audit.** Rows go through the proxy's writer (§4.20): session `net`, tool `swap`, args `NAME -> host:port`, `allowed` once per token and host an hour, or `refused: <reason>` under the same cap of 60 a minute. The reason names the token and says `this host`; the destination is in the args, scrubbed like every row, so a host name that holds a stand-in reads `[vault:NAME]`. The `connect` row of a decrypted host is written as before. `/activity` reads them like any `net` row.
- **When things fail.** No CA (`ca::Authority::load` fails at the proxy's start): a `CONNECT` to a bound host answers `502 zephyr: the token broker is down`, the owner is told once (`[zephyr] the token broker is down, so vault tokens do not work: <error>`), surrogates are still what is handed out, and unbound hosts are unaffected. Vault unreadable: the last map still says which hosts are decrypted, and they answer `502 zephyr: the vault could not be read`, on a new `CONNECT` and on an open connection alike, never a plain tunnel. Upstream certificate fails: `502`, one audit row, nothing sent. Proxy down: as §4.20; no swap happens anywhere else.
- **The gate.** Nothing new waits on the owner: `policy::gated` and `gate::decide` still judge a command before it runs, and an approved held action gets its tokens from the same `exec_env`, so surrogates. What this adds under the gate: a token is usable only on its hosts and only through the proxy, and each use leaves an audit row by name.

- **What the agent's tools trust**, all written by root, none in the agent's home:
  - the system bundle: at a container start `supervise` runs `ca::start` after the floor is loaded (`Policy.ca`), which makes or renews the CA, writes `/usr/local/share/ca-certificates/zephyr.crt` and runs root's `/usr/sbin/update-ca-certificates --fresh` with a PATH of root's folders only, rebuilding `/etc/ssl/certs` from scratch so a replaced CA is dropped. This covers curl, wget, git, gh and other Go programs, and OpenSSL. If any of it fails the daemon starts all the same (the floor does not depend on it) and bound hosts answer 502;
  - `<state>-public/ca.pem` (root's 0755 folder, §4.6), and in `agent::proxy_env` (`agent::CA_ENV`, so the host's `docker exec` as the agent gets them too): `NODE_EXTRA_CA_CERTS=/var/lib/zephyr-public/ca.pem`, and `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` = `/etc/ssl/certs/ca-certificates.crt`, for Node, and for Python and Rust tools that carry their own roots (requests, pip, httpx, uv);
  - Chromium: once per daemon start, `/usr/bin/certutil -d sql:/zephyr/.pki/nssdb -A -n zephyr -t C,, -i <state>-public/ca.pem` (after `-D -n zephyr` for the one before a renewal), run **as the agent** through `agent::cmd` (`ca::trust_chromium`): the store is in its home, which root never writes. `libnss3-tools` is in the image;
  - Camoufox: the image adds `Certificates.Install` naming `/var/lib/zephyr-public/ca.pem` to the `distribution/policies.json` Camoufox ships.
- **The agent adding trust of its own changes nothing that matters.** It cannot write `/usr/local/share/ca-certificates`, `/etc/ssl` or `<state>-public`, nor read `ca.key` or `broker.key` (`zephyr __netcheck`, run as the agent by `doctor`, tries each). It can point its own programs at any bundle it likes, or run `curl -k`: that only lets it intercept itself. The one check that guards a real token is the proxy's of the upstream, against roots compiled into the binary, which no file or variable of the agent's reaches. serenity reads the system bundle and so now trusts the CA too; root's traffic does not pass the proxy, and only root holds the key, so nothing follows from it.
- **`doctor`** (`broker::doctor`, in the container). Under host networking, one line: `token broker off (host networking): vault tokens reach the agent in plain`. Otherwise: the CA's folder and key modes and its days left (a warning under 30: `restart with zephyr up`); the CA present in the system bundle and in `<state>-public/ca.pem`; `ca.key` and `broker.key` not readable, and the three trust locations not writable, as the agent; no secrets.env value of a surrogate-mode connector inside the published `mcp.json`; the decrypted hosts; and one warning each for a token with `raw`, a token with `url`, a token bound to nothing, a connector with `secrets = "plain"`, a connector left out, and the `[agent] env` names.
- **Provider credentials are out of scope.** `accounts/*/auth.json`, the Claude config and every `[agent] env` variable stay readable by the agent (§7). rpi rewrites its own credentials (`rpi auth refresh` posts the refresh token in a body and reads the new ones from a body, so brokering them means body swaps both ways and the daemon doing the OAuth itself); some providers read their own token; it would decrypt all model traffic through clients that do not trust the CA; and the loss is different in kind: a provider token spends model quota, it does not read mail or push to a repository. An API key only a script needs belongs in the vault as a bound token, not in `[agent] env`.

- **Pinning: what works on a bound host, and what must stay a tunnel** (checked in a real container, `tests/token_broker.rs`):

  | Client | On a bound host |
  |---|---|
  | curl, git, gh and other Go programs, OpenSSL | works: the system bundle, no pins |
  | Node (`fetch`, npm), Python (`urllib`, requests, pip, httpx), uv | works through `agent::CA_ENV` |
  | Chromium (agent-browser) | works through the agent's NSS store |
  | Camoufox | works through its `policies.json` |
  | rpi's own provider clients and its MCP client (`url` connectors), `zephyr-cursor` | **does not work**: roots compiled in, no file read. With `api.anthropic.com` decrypted, rpi 0.21.2 fails with `http transport error`; tunnelled, it gets the provider's own answer |
  | a program with compiled-in roots or real pins | does not work: a certificate error, at once |

  So a model provider's host must stay a tunnel, and it does: no provider credential is brokered, so nothing is bound there. If the owner binds a token of their own to a provider's host, rpi loses that provider; `/vault bind` says `HOST is now decrypted by zephyr for every program the agent runs`, and `doctor` lists the decrypted hosts. A pinned client's token is `raw`, or the host is left unbound. Every failure here is a refused handshake, never a leaked token.
- **What it does not stop.**
  - A bound host that sends the value back **in a form the proxy does not know**. It looks for the value's own bytes, its base64, its JSON escapes and its percent-encodings (above). Not for: another case (`TOKEN` for `token`, a host that lower-cases what it echoes), HTML entities (`&amp;`, `&#x2F;`), base64 wrapped across lines (MIME), hex, a percent-encoding that leaves more characters as they are than a URI component does, or anything derived from the value (a hash, a signature, a JWT made with it, a ciphertext, an archive, an image). `exec`'s answer and the command's log catch the value and its base64 only.
  - A **remote (`url`) connector's secret**, which the agent can read in `mcp.json` once the owner settled it as `plain` (above): rpi's own MCP client cannot use a decrypted host. And a **connector's secret in a header its own config does not name**: a `command` connector's program must send it in `Authorization`, or the connector is `plain`.
  - A bound host that answers **compressed although asked not to**: nothing leaks, but the request fails with `502`, so such an API cannot be used with a bound token (the token is `raw`, or the owner finds the API's uncompressed mode).
  - A bound host whose API needs a **websocket, a range request or a compressed reply** cannot be used with a bound token: those are refused rather than passed unread.
  - A value **shorter than 4 characters**, which is not looked for anywhere.
  - **Use.** The agent can still use a bound token on its hosts, through any program: the binding limits where a token goes, not what is done with it there (§4.16 still judges the command). So the owner binds a token only to the API it is for.
  - A `raw` token, a `plain` connector, a login and `[agent] env` are in the agent's hands as before; of those only what a command prints is scrubbed from its log.
- **Not done:** swaps in request bodies; proxy-side signing (AWS SigV4, HMAC webhooks, JWT service accounts: such a token is `raw`); an owner-supplied extra root for a host with a private CA, and plain `http://` to a bound host (`raw`); HTTP/2 and gRPC on a bound host; client certificates; a class on a token that would send each swapped request to `gate::decide` (an in-flight ask, which §4.20 ruled out; payments can revisit it); provider credentials.
- **No schema version.** Bindings live with the secrets they bind (`vault.toml`, `zephyr.toml`), surrogates are derived, leaves and the notice limiter are in memory, and the `audit`, `settings_log` and `meta` tables are used as they are.
- **Tested** in `broker.rs` (surrogates, bindings, the swap and scan tables, the map, `doctor`), `ca.rs` (the CA's files and renewal, leaves, the compiled-in roots, publishing), `egress.rs` `tests::decrypted` (a bound host through real TLS on both legs: the swap, keep-alive, streaming, a websocket, ALPN, the audit; an echo of the token in a header, a body with a length and a chunked body that cuts it in two, and a compressed reply refused; a Basic credential and other base64 sent back, the status line's text, a range, hop-by-hop headers both ways, an upgrade, a request framed two ways, a stand-in in a header that is no credential's, a server that closes, trailers; a stand-in on plain HTTP and in a host name; another token, another `Host`, another SNI; rebinding; a CA made here; an unbind and an unreadable vault on an open connection; no CA), `vault.rs`, `drafts.rs`, `settings.rs`, `agent.rs`, `supervise.rs`, `tests/router.rs` (an `exec` on a stand-in, the agent's `bind`, the upgrade notice), `tests/host.rs`, `tests/attach.rs`, `tests/tui.rs`, and against a real container by the ignored `tests/token_broker.rs`.

## 7. Open items

- The name collides with the Zephyr RTOS (a Linux Foundation project). That doesn't matter for a private repo, but check it before using Zephyr as a public brand.
- The agent runs as your uid, so it can read anything mounted that you can. Only the listed secret paths are masked.
- The agent can read the provider credentials rpi itself needs (`accounts/*/auth.json`, the Claude config) and the conversation (`sessions/`); the policy plugin's name check is the only thing in the way, and it can be bypassed.
- A connector the owner marked `secrets = "plain"` has its real secrets in `mcp.json` (§4.6), so the agent can read them, as it can a `raw` vault token and any variable `[agent] env` lets through (§4.21). A remote connector with a secret works no other way (rpi's own MCP client cannot reach a host the broker decrypts), which is why it is the owner's word, and the upgrade's for those that were there, never a default.
- Under the network floor (§4.20) the agent still reaches the host's own public address on a VPS: it is a public address like any other, and what the host serves there on `0.0.0.0` is already open to the internet, behind the host's own firewall. Services the host keeps on its loopback are out of reach.
- A plain GET can carry data out in its URL; outbound alerts list only commands that send a body or use another method (§4.4 item 3).
