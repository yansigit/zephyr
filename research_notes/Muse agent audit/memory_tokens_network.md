# Security techniques for always-on personal agents: memory poisoning, token brokering, network egress

## Memory poisoning: attacks, provenance/taint defences, whether scanners catch it, and how commercial agents expose view/edit/forget

### Takeaway
Writing to persistent memory from untrusted content works almost every time against current frontier models (injection 95–99.8%; retrieval later 60–98%; behaviour change 33–89%). Content scanners do not stop false-fact poisoning (0 of 360 caught by a pipeline that gets 0.83 recall on prompt injection). The defences that hold up bind trust to where a write came from, recorded at write time and not inferred from content or lineage, and then limit what memory of untrusted origin may authorise. Every commercial product (ChatGPT, Claude, Gemini, Meta's Muse) offers a human-readable view, in-place editing and a "forget" or delete path. None of them gives a strong guarantee that a forget is complete.

### Cited Findings

**Attacks and measured results**
- AgentPoison (NeurIPS 2024, arXiv:2407.12784, DOI 10.52202/079017-4136): backdoor triggers optimised so poisoned demonstrations are retrieved from memory/RAG. Average attack success ≥80% with ≤1% benign-performance drop at a poison rate <0.1%. The paper reports 82% retrieval success and 63% end-to-end ASR. Targets were an autonomous-driving agent, a QA agent and EHRAgent — [NeurIPS proceedings](https://proceedings.neurips.cc/paper_files/paper/2024/hash/eb113910e9c3f6242541c1652e30dfd6-Abstract-Conference.html); [paper PDF](https://proceedings.neurips.cc/paper_files/paper/2024/file/eb113910e9c3f6242541c1652e30dfd6-Paper-Conference.pdf)
- MINJA (arXiv:2503.03704, NeurIPS 2025 poster): the attacker never touches the memory bank. They only send queries, and use "bridging steps", an "indication prompt" and "progressive shortening" so the agent writes the malicious record itself. Injection success rate was 95.9–100% across EHR (GPT-4) and RAP/Webshop (GPT-4/4o) settings, with an average ASR of 76.8% (v2) — [arXiv abs](https://arxiv.org/abs/2503.03704); [v2 HTML](https://arxiv.org/html/2503.03704v2); [NeurIPS](https://neurips.cc/virtual/2025/poster/118152)
- A MINJA replication under realistic conditions (arXiv:2601.05504): pre-existing legitimate memories "dramatically reduce attack effectiveness". GPT-4o-mini fell from 62% ASR / 100% ISR to 6.67% ASR / 26.67% ISR. Llama-3.1-8B kept ~99.95% ISR but 0% ASR, meaning injections were stored but rarely changed answers. Memory-sanitisation defences needed careful trust-threshold calibration to avoid either blocking everything or missing subtle attacks — [arXiv:2601.05504](https://arxiv.org/abs/2601.05504); [HTML](https://arxiv.org/html/2601.05504v2)
- **Source of "fabricated preference saved up to 99.8%"**: "Hidden in Memory: Sleeper Memory Poisoning in LLM Agents" (arXiv:2605.15338). A black-box adversary controls an external document or webpage, and the assistant persists a fabricated user memory that is retrieved in a later session. Universal payloads reached an injection rate above 97% on GPT-5.4 and above 99% on GPT-5.5. Retrieval in later sessions was 60–89% in agentic settings. Goal-adjacent adversarial-usage rate ranged from 42% (GPT-5.4) to 85% (DeepSeek-v4), falling to 0–6% when the goal was unrelated to the query. On agent actions every model acted on the injected goal: 33% for Claude Sonnet 4.6 (lowest) up to 53% for Gemini 3.1 Pro. Claude Sonnet 4.6 had a much lower injection rate (6.5% on the Agent Action subset, against 97% for GPT-5.4). Preference-like goals ("Personal Attribute Fabrication", 35.4% IR on GPT-5.4; "fabricated personal attributes" 40% usage) got through more easily than explicit exfiltration, which safety training catches — [arXiv HTML](https://arxiv.org/html/2605.15338). The promptfoo DB summary gives "tool-based behavioral-memory injection rates up to 99.8% for GPT-5.5 and 95.0% for Kimi-K2.6" — [promptfoo LM Security DB](https://www.promptfoo.dev/lm-security-db/vuln/sleeper-memory-poisoning-in-llm-agents-9f001ee2). **Conflict:** the OpenReview version attributes the 99.8% to "GPT-5.6 Sol" rather than GPT-5.5, and gives "38–89%" for attacker-intended agentic actions — [OpenReview PDF](https://openreview.net/pdf?id=0imYw5ajm4). Cite this as "up to 99.8% on a frontier GPT model" unless the exact model matters.
- Sleeper-poisoning defences: prompt hardening (naive and GEPA-optimised) "can mitigate … but do not provide model-agnostic or adaptation-robust protection". An LLM document scanner placed ahead of ingestion was evaluated as a complementary direction. Benign memory saves stayed at ≥98.6% write rate under hardening — [arXiv:2605.15338](https://arxiv.org/html/2605.15338)
- GhostWriter (arXiv:2607.06595), aimed at tool-using personal agents (email, calendar, code): about 98% average injection (100% on most agents) and about 60% average activation. The proposed AM-Sentry combines (i) a write-time policy that scores vulnerability, sensitivity and **source trust**, with the scale "User 1.0, Internal contact 0.8, Client 0.3, External untrusted 0.0", plus contradiction, instruction-vs-informative, verifiability and justification, and a second LLM judge that checks whether the first was injected; and (ii) a retrieval screen. The utility-only baseline A-MAC admitted most attacks (minimum 54%, average 84%). The strictest AM-Sentry "almost completely blocks GhostWriter across most models" with minimal utility loss — [arXiv HTML](https://arxiv.org/html/2607.06595v1)
- MemoryGraft (arXiv:2512.16962): poisoned "experience" records give durable, trigger-free behavioural drift. The root assumption it exploits is "No Provenance or Sanitization". It proposes Cryptographic Provenance Attestation to tell self-generated records from injected ones — [arXiv HTML](https://arxiv.org/html/2512.16962)
- SpAIware (Rehberger; Herrador & Rehberger, *Future Generation Computer Systems* vol 174, 2026, DOI 10.1016/j.future.2025.107994): an untrusted website injected instructions into ChatGPT's long-term memory, which then exfiltrated user data across later sessions through rendered images and tools — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0167739X25002894). Gemini "delayed tool invocation" (Feb 2025): the untrusted content ties the memory write to a later user action ("if the user says yes, save…") to get around Gemini's restrictions — [Techzine](https://www.techzine.eu/news/security/128653/a-new-hack-corrupts-geminis-long-term-memory)
- OWASP Top 10 for Agentic Applications (Dec 2025) lists **ASI06 – Memory & Context Poisoning**, with the Gemini memory attack as its example incident — [OWASP GenAI](https://genai.owasp.org/2025/12/09/owasp-top-10-for-agentic-applications-the-benchmark-for-agentic-security-in-the-age-of-autonomous-ai)
- "Misattribution Gap" (arXiv:2605.22842): a policy-formatted document entered a shared vector store through normal uploads and returned as trusted system context once provenance was lost (a "Trust Laundering Chain"). Four safety classifiers, one of them trained on memory poisoning, made **zero detections across 510 checkpoints**. Agents cited the injected document as authority in 59 of 65 cases. The paper's "Memory-Persistent Information-Flow Control" blocked 97% at the cross-session boundary — [arXiv:2605.22842](https://arxiv.org/abs/2605.22842)

**Do scanners catch poisoned memories?**
- "Utility Under Attack" (arXiv:2608.21230): a four-stage write-time screening pipeline reached 0.832 recall on indirect injection (InjecAgent) and flagged only 1.5% of NotInject benign trigger-word text, against 42.8% for DeBERTa detectors. It **refused 0 of 360** fabricated-fact memories. Poisoning 1.2% of the corpus dropped LongMemEval accuracy from 0.850 to 0.300, leaving 35% of the memory's value. Provenance-weighted ranking recovered it only to 56%. With a stronger weight it became "a denial-of-service primitive" that made genuine but conservatively labelled content unretrievable (N-arm accuracy 0.858 → 0.042). The authors' conclusion: "Distinguishing a false assertion from a true one generally requires external grounding beyond the text being screened." The same paper's table: ProtectAI DeBERTa v2 recall 0.414/0.660, Llama Prompt Guard 2 0.228/0.000, LLM judge (Haiku 4.5) 0.757/0.932 on deepset/InjecAgent — [arXiv HTML](https://arxiv.org/html/2608.21230)
- Trajectory-based provenance detectors (arXiv:2606.30566): "retrieval-before-send" is a precondition for an attack, not a predictor of malice. False-positive rate was 24.7–57.6% across a 13-model factorial (N=4,160), PPV ≤3.85% at 1% prevalence, and a recipient-metadata gate flagged 129/129 legitimate external emails. The author withdrew their own earlier recommendation to use it as a standalone pre-filter — [arXiv:2606.30566](https://arxiv.org/abs/2606.30566)

**Provenance / taint / IFC defences**
- TMA-NM (arXiv:2606.24322): proves (with TLA+ models) that content-based and lineage-based authority can both be manipulated. An attacker can launder an untrusted origin through (1) the agent's own summarisation, (2) a trusted tool echoing it back, or (3) manufactured corroboration. Write-time origin binding is necessary, and non-malleable origin-bound authority with Sybil-resistant, corroboration-gated elevation is sufficient. Existing defences reached up to 68% laundering ASR; TMA-NM reached 0% on direct and laundering attacks across 8 frontier models "at full legitimate utility" — [arXiv:2606.24322](https://arxiv.org/abs/2606.24322)
- MemLineage (arXiv:2605.14421): attaches cryptographic provenance plus LLM-mediated derivation lineage to each entry. It refuses sensitive actions whose justifying context contains an entry whose chain of custody crosses an External ancestor. It notes that FIDES enforces labels at planning time "but do[es] not persist labels across the LLM derivation step that commits the laundered entry" — [arXiv HTML](https://arxiv.org/html/2605.14421v1)
- FIDES (Microsoft Research, arXiv:2505.23643): a planner that tracks confidentiality and integrity labels, enforces policy deterministically, and hides information selectively. Evaluated on AgentDojo — [MSR](https://www.microsoft.com/en-us/research/publication/securing-ai-agents-with-information-flow-control). NeuroTaint (arXiv:2604.23374) does offline semantic and causal taint auditing, including cross-session persistence through memory, and outperforms FIDES on its 400-scenario TaintBench — [arXiv:2604.23374](https://arxiv.org/abs/2604.23374)
- CaMeL and the design-patterns catalogue are cited as the system-level line: "detecting malice in content is the wrong place to stand" — [arXiv:2608.21230 §3](https://arxiv.org/html/2608.21230)
- The survey (arXiv:2604.16548, EMNLP 2026) frames the lifecycle as Write/Store/Retrieve/Execute/Share/**Forget & Rollback**. It recommends combining provenance, versioning and policy-aware retention ("Verifiable Memory Governance") — [arXiv:2604.16548](https://arxiv.org/abs/2604.16548)

**Commercial view/edit/forget**
- ChatGPT: Settings › Personalization › Memory, with "Reference saved memories", "Reference chat history", a "Memory summary" and "Saved memories". Users can edit the summary or a saved memory, and ask ChatGPT to forget. Saved memories are stored separately from chat history, so deleting a chat does not delete a memory, and deleting a memory "does not remove mentions … from past conversations". Logs of deleted memories are kept up to 30 days. The summary "may omit details". "Sources" below a response show which memory or chat was used — [OpenAI Help](https://help.openai.com/en/articles/8590148-what-is-chatgpt-s-memory)
- Claude: Settings › Your Claude › Manage memory shows "everything Claude remembers about you" as an editable summary, which can also be updated from chat. Sensitive topics (health, religion, and similar) are not stored by default. There is a per-chat memory-off toggle and memory import/export. Turning memory off at org level deletes all entries immediately. Chats that used Personal Finance linked accounts are never saved to memory — [Claude Help](https://support.claude.com/en/articles/11817273-using-claude-s-chat-search-and-memory-to-build-on-previous-context)
- Gemini: "Personal context"/saved info (gemini.google.com/saved-info) has per-item Edit/Delete. "Memory summary" is edited by prompt ("Remove my old phone number…") and comes with a chronological **Memory history** of changes. To delete something learned from past chats, you delete those chats from Gemini Apps Activity, and a connected app can reintroduce it — [Gemini saved info](https://support.google.com/gemini/answer/16413516); [memory summary](https://support.google.com/gemini/answer/18617127); [past chats](https://support.google.com/gemini/answer/16598469?hl=En)
- Meta Muse: runs in a per-user isolated cloud VM. Memories live in an editable `MEMORY.md`, and identity/personality ("Soul") in `Identity.md`. A **forget skill** asks Muse to find a person, topic or matter in its memories and supporting files and "remove it to the best of its ability". Meta warns that after you delete something "Muse may still remember information it learned from what you deleted". Reset wipes everything, and a data download is offered. Meta states "important permission and security checks operate separately from the AI model" — [Meta: manage Muse data](https://www.meta.com/help/artificial-intelligence/2225571704857152); [Meta: Muse privacy & security](https://www.meta.com/help/artificial-intelligence/1047255454427887); [muse.ai privacy](https://muse.ai/privacy)

### Inferences
- Auto-approving memory writes by provenance is the defence the research supports, if provenance is fixed by the daemon at write time from the channel the bytes came from (owner message vs. tool output, web page, email, task report). The agent must not supply it, and it must not be inferred from content. Writes the agent derives from untrusted context should inherit the untrusted label, because summarisation and tool echo are the documented laundering channels.
- Content scanners (including LLM judges) are worth running as a cheap second layer against instruction-shaped payloads. They should not gate false-fact poisoning, which is the "fabricated preference" case.
- The provenance-ranking DoS result argues for a quarantine/pending tier (owner digest, approve or drop) rather than silent down-weighting.
- Forget: every vendor admits forget is best-effort when memory is an LLM-maintained text file. A git-committed memory store (zephyr's `memory.rs`) can do better. It can delete the lines, show the diff, and optionally scrub history. Note that git history keeps a forgotten fact unless it is rewritten.
- A digest in the style of Gemini's "Memory history" or ChatGPT's "Sources" maps naturally onto periodic digests of git log entries, one line per write with its provenance.

### Gaps
- No public numbers on how ChatGPT/Claude/Gemini/Muse internally label provenance on memory writes. Vendor docs describe user controls only.
- The exact model behind the 99.8% figure conflicts between arXiv and OpenReview versions of arXiv:2605.15338.
- TMA-NM, MemLineage and AM-Sentry are 2026 preprints without independent replication. Their adversaries are mostly non-adaptive.

## Token brokering: agent holds surrogates, a proxy swaps in real credentials

### Takeaway
"Placeholder in the sandbox, real secret injected at an egress proxy, bound to an allowlist of hosts" is now the standard design. Fly.io Tokenizer, Cloudflare Sandbox outbound Workers, OpenAI hosted environments, Anthropic's Claude Code cloud and `sandbox-runtime`, Docker Sandboxes and E2B all ship it. Each binds a secret to specific destination hosts, since an unbound placeholder can be sent to an attacker's echo server. HTTPS injection needs TLS termination with a proxy CA trusted inside the sandbox. Request signing (SigV4, HMAC, JWT) has to be done by the proxy, because the sandbox cannot compute with a secret it never sees.

### Cited Findings
- **Fly.io Tokenizer**: a stateless HTTP proxy holding the private key of a Curve25519 keypair. Clients send ordinary HTTP/1.1 through it with `Proxy-Tokenizer` headers carrying a sealed secret plus rewrite instructions, usually "inject the plaintext into a header". The key threat it names: a compromised app could "proxy requests for a particular secret to a service you ran that collected the plaintext", so secrets are locked to allowed hosts or host regex patterns. The SSOkenizer runs the OAuth dance itself and hands the app only sealed tokens — [Fly blog "Tokenized Tokens"](https://fly.io/blog/tokenized-tokens)
- Tokenizer mechanics: the sealed JSON carries `inject_processor`, `allowed_hosts`/`allowed_host_pattern`, and client auth (`bearer_auth` as a sha256 digest, `fly_src_auth` tying the secret to an org/app/machine "so the token is not useful if exfiltrated"). Processors include `inject_hmac_processor`, `sigv4` (re-signs AWS requests, stripping proxy headers before signing), `jwt_processor` (Google SA → short-lived token, with response rewritten to a sealed token so "the caller never sees any plaintext credential"), and `client_credentials_processor`. Requests without sealed secrets are blocked unless `OPEN_PROXY`. The client must "speak plain HTTP to the proxy" for injection to work. It refuses circular requests to its own hostnames — [README](https://github.com/superfly/tokenizer/blob/main/README.md); [UserGuide](https://github.com/superfly/tokenizer/blob/main/docs/UserGuide.md); [processor.go](https://github.com/superfly/tokenizer/blob/main/processor.go); [tokenizer.go](https://github.com/superfly/tokenizer/blob/main/tokenizer.go)
- **Cloudflare Sandbox outbound Workers** (changelog 13 Apr 2026): `outboundByHost` handlers run outside the sandbox and set auth headers. They support TLS interception, `allowedHosts`/`deniedHosts` (evaluated before handlers), `enableInternet = false` by default, and per-instance credentials via `ctx.containerId`. Benefits listed: "No token is exposed to the sandbox", rotation without touching the sandbox — [changelog](https://developers.cloudflare.com/changelog/post/2026-04-13-sandbox-outbound-workers-tls-auth/); [guide](https://developers.cloudflare.com/sandbox/guides/outbound-traffic); [blog](https://blog.cloudflare.com/sandbox-auth). Dynamic Workers: `globalOutbound: null` blocks all fetch/connect, described as "the most secure way … block the Internet, then provide specific capabilities through bindings" — [Cloudflare egress control](https://developers.cloudflare.com/dynamic-workers/usage/egress-control)
- **OpenAI hosted agent environments**: "Sandbox code uses a placeholder; a network proxy supplies the real secret for approved hosts." Self-hosted users must provide their own trusted proxy. "Injecting a stored secret into the environment still exposes it to agent-generated code" — [OpenAI sandbox security](https://developers.openai.com/api/docs/guides/agents-api/environments/security.md). The vault API `environment_variable` credential works like this: the sandbox gets a placeholder env var, and the egress proxy replaces it "for allowed HTTPS destinations on ports 443 and 8443". "Sandbox code cannot read the real secret or use it for local computation, such as signing a request." Each secret carries a `networking` destination list, and the environment network policy must allow those too — [OpenAI API reference](https://developers.openai.com/api/reference/typescript/__sdk_schema?declaration=%28resource%29+beta.agents.vaults.credentials+%3E+%28method%29+create+%3E+%28params%29+default&selected=%28resource%29+beta.agents.vaults.credentials+%3E+%28method%29+create)
- **Anthropic Claude Code cloud**: "network secrets" are attached by Anthropic's agent proxy "after each request leaves the session's VM". Each secret binds to one exact host (no `*.` wildcard) and a header (`Authorization` or custom such as `X-Api-Key`), and can't be viewed after saving. The proxy never attaches secrets to GitHub (separate proxy), `api.anthropic.com`, public package registries (npm, PyPI, crates, Go proxy), setup-script requests, or telemetry. The GitHub proxy swaps a scoped in-VM credential for the real token, uses the literal placeholder `proxy-injected` for `GITHUB_TOKEN`/`GH_TOKEN`, scopes API calls to the attached repos (403 otherwise), rejects branch deletions, tag pushes and GraphQL. It "doesn't limit which branches a push can update" — [Claude Code cloud environments](https://code.claude.com/docs/en/cloud-environments)
- **Anthropic `sandbox-runtime` (local)**: credential `mode: "deny"` withholds a value. `mode: "mask"` puts a sentinel inside the sandbox and substitutes the real value on egress to that entry's `injectHosts` (default: the allowed domains). Masking requires `network.tlsTerminate` so the value "only leaves over a verified TLS connection" (opt-out `allowPlaintextInject`). `tlsTerminate.excludeDomains` tunnels opaquely, so injection does not apply there — [sandbox-runtime README](https://github.com/anthropics/sandbox-runtime). Without TLS termination, "masking fails without exposing anything": the sentinel reaches the server and auth fails. `claude doctor` warns about this — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- **Docker Sandboxes (`sbx`)**: a host-side HTTP/HTTPS proxy looks up the credential on the host and overwrites the header. "For proxy-managed credentials, the real value never enters the sandbox." Custom secrets give a placeholder for an env var keyed to a domain. The proxy "stops injecting credentials into install-only domains before the agent launches" — [Docker Sandboxes credentials](https://docs.docker.com/ai/sandboxes/configuration/credentials/)
- **E2B**: the egress proxy injects `transform.headers` on matching requests and can replace a placeholder "with a freshly minted token on each matching request". To modify HTTPS it "terminates TLS with its own CA" — [E2B internet access](https://docs.e2b.dev/network/internet-access)
- **AWS Bedrock AgentCore Identity**: a managed Token Vault stores outbound OAuth tokens keyed to (workload identity, user id). Client secrets live in Secrets Manager. The agent obtains tokens through `GetWorkloadAccessToken` rather than holding long-lived secrets — [AWS AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-oauth.html); [AWS sample architecture](https://aws-samples.github.io/sample-autonomous-cloud-coding-agents/architecture/identity-and-auth). Note that this hands the agent a real, short-lived token, which makes it a broker but not a surrogate-swap design.
- **TLS interception trade-off**: the Claude Code built-in proxy decides on the client-supplied hostname and by default does not inspect TLS, so "code running inside the sandbox can potentially use domain fronting" to reach hosts outside the allowlist. The recommended fix for stronger guarantees is a TLS-terminating proxy with its CA installed in the sandbox — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing). The sandbox-runtime README lists the cases TLS termination "fundamentally breaks" (handled with `excludeDomains`) — [sandbox-runtime](https://github.com/anthropics/sandbox-runtime). Allowing `github.com` "lets a process push to any repository" — [sandbox-runtime](https://github.com/anthropics/sandbox-runtime)

### Inferences
- For zephyr: the daemon (root) runs the proxy and keeps the real values (it already has `vault.toml`). The agent holds a surrogate such as `zephyr-surrogate-<name>-<random>`. The proxy swaps it only when the destination host is in that secret's bound host list, and only on the TLS-terminated leg. Replace inside headers only, or also in bodies? Header-only (Authorization, X-Api-Key, configurable `dst`) mirrors every vendor. Body substitution widens the echo-exfil surface.
- The surrogate must be useless elsewhere. Make it random per secret (and ideally per session/container, like Cloudflare `ctx.containerId` and Fly `fly_src_auth`). If it is sent to an unbound host, the proxy forwards it unchanged or blocks the request and audits it. It never substitutes.
- Signing secrets (AWS SigV4, HMAC webhooks, JWT service accounts) need proxy-side processors (Tokenizer's model). Otherwise the agent needs the real key, which OpenAI explicitly says the placeholder model cannot support.
- TLS interception means an agent-trusted CA. Its private key must be root-only and live outside the agent's home, consistent with zephyr's rule that root publishes only into root-owned 0755 folders. Certificate-pinned clients and non-HTTP protocols (SSH git, gRPC with pinning) will not work through it. Those hosts need an opaque-tunnel exclusion where no injection happens.
- Replace zephyr's current output scrubbing (`[vault:NAME]`) with substitution at the proxy, keeping scrubbing as defence in depth for response bodies that echo the real secret.

### Gaps
- No public measured evaluations (attack success numbers) of placeholder-swap proxies. The evidence is design documents and vendor docs only.
- Google Cloud agent-identity credential handling: no primary source found in this pass.
- OpenAI Codex Cloud's internal proxy implementation (TLS CA handling) is not documented beyond "placeholder; proxy supplies secret for approved hosts".

## Network egress for agent sandboxes: SSRF/metadata/loopback, DNS rebinding, and enforcement mechanisms

### Takeaway
The strongest shipped pattern removes direct network access from the agent and forces everything through a host-side proxy. Anthropic's sandbox-runtime deletes the network namespace and exposes the proxy over a bind-mounted Unix socket. Cloudflare, E2B and Modal intercept below the guest. The proxy then (a) allowlists hostnames, (b) resolves and rejects loopback, link-local (169.254.169.254), private, CGNAT, IPv4-mapped/NAT64 and own-host addresses, and (c) connects to the exact IP it validated. Hostname checks made before connecting only reduce DNS rebinding; they do not stop it (OpenAI says so explicitly). Per-uid packet rules (iptables `owner --uid-owner` / nftables `meta skuid`) are the documented lower layer for when the agent shares a network namespace with a root daemon.

### Cited Findings

**How the major sandboxes do it**
- Anthropic `sandbox-runtime` (Claude Code's sandbox): network is "allow-only"; an empty `allowedDomains` means no network. On Linux "the network namespace of the sandboxed process is removed entirely", so all traffic must go through HTTP and SOCKS5 proxies on the host, reached by Unix sockets bind-mounted into bubblewrap via `socat`. seccomp BPF blocks `socket(AF_UNIX)` and `io_uring_*` (since `IORING_OP_SOCKET` would bypass it), and refuses `unshare`/`clone` with user or mount namespace flags, `setns`, `mount`, `pivot_root`, and `clone3` (ENOSYS). It does not stop inherited or `SCM_RIGHTS`-passed fds. Allowed hostnames are checked against resolved addresses before dial (loopback, link-local, host's own addresses); "other private ranges are only covered if you list them in `deniedResolvedAddresses`". Allowing `/var/run/docker.sock` "effectively grant[s] access to the host system" — [sandbox-runtime README](https://github.com/anthropics/sandbox-runtime)
- Claude Code docs: the sandbox has "No direct route out". After the allowlist passes, the proxy resolves the name and "refuses the connection when the name resolves only to local addresses", including loopback, link-local `169.254.169.254`, and the machine's own addresses. Linux gives the sandbox its own loopback, so `localhost` doesn't reach host servers. A custom upstream proxy makes Claude Code's own checks "stop applying to that traffic". Managed settings can lock `allowedDomains`, `allowUnixSockets` and `allowLocalBinding` so a repository cannot widen them — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- OpenAI Codex: Linux uses `bwrap` + `seccomp`, macOS Seatbelt. `network_proxy` domain rules are allowlist-first, deny wins, and `*.x` does not match the apex while `**.x` does. `allow_local_binding = false` blocks loopback, link-local and private destinations; "hostnames that resolve to local/private IPs stay blocked even if they match the allowlist". DNS rebinding: lookups that fail or time out are blocked and non-public resolutions are blocked, but "it does not eliminate it. Preventing rebinding completely would require pinning resolved IPs through the transport layer. If hostile DNS is in scope, enforce egress controls at a lower layer too." Proxy listeners stay loopback-only. The proxy does not cover web search, MCP, browser or connectors, which "use separate service connections" — [Codex agent approvals & security](https://developers.openai.com/codex/agent-approvals-security)
- E2B: `allowInternetAccess:false` ≡ `denyOut:['0.0.0.0/0']`. Domain allowlists require denying all other traffic. Allow beats deny. Rules can be changed live (`updateNetwork`). Under BYOP, "UDP DNS to 8.8.8.8:53 leaves directly, outside BYOP", so the user's proxy policy doesn't apply to it. Proxy addresses resolving to internal ranges are rejected at creation — [E2B internet access](https://docs.e2b.dev/network/internet-access); [E2B BYOP](https://docs.e2b.dev/network/byop)
- Modal: `block_network=True` drops all outbound traffic. `outbound_cidr_allowlist` (any protocol) and `outbound_domain_allowlist` (TLS on 443 only to listed domains). Modal itself notes the domain allowlist doesn't protect against domain fronting and suggests "a Sidecar as a proxy" — [Modal networking](https://modal.com/docs/guide/sandbox-networking); [md](https://modal.com/docs/guide/sandbox-networking.md)
- gVisor: its own user-space netstack. `--network=none` leaves loopback only. An experimental `--network-proxy-path` attaches the NIC to a SOCK_SEQPACKET Unix socket owned by an external process that "is responsible for any egress filtering". Only the primary interface is proxied — [gVisor networking](https://gvisor.dev/docs/user_guide/networking/)
- Cloudflare Dynamic Workers `globalOutbound: null` (no fetch/connect at all, capabilities via bindings) — [Cloudflare](https://developers.cloudflare.com/dynamic-workers/usage/egress-control)

**SSRF ranges, metadata, rebinding**
- OWASP SSRF cheat sheet minimum deny list: `169.254.169.254`, `metadata.google.internal`, `127.0.0.0/8`, `0.0.0.0/8`, `::1/128`, RFC1918, `fc00::/7`, `fe80::/10`, multicast `224.0.0.0/4`/`ff00::/8`, IPv4-mapped `::ffff:0:0/96`. NAT64 `64:ff9b::a9fe:a9fe` also reaches metadata where NAT64 runs. "Bind the connection to a validated address …; checking DNS answers separately does not prevent DNS rebinding." "Deny-lists are bypass-prone. Prefer allow-lists." — [OWASP SSRF cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)
- MCP security best practices: block the same ranges and validate redirect targets (disable auto-redirect and validate each hop). Use egress proxies like Smokescreen. Watch for DNS TOCTOU and "consider pinning DNS resolution results between check and use". "Avoid implementing IP validation manually. Attackers exploit encoding tricks (octal, hex, IPv4-mapped IPv6)" — [MCP spec security](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- A real-world bypass (2026): a hand-written `isBlockedAddress` missed `::ffff:7f00:1` (hex-mapped 127.0.0.1), `::7f00:1` (v4-compatible), `fea0::1` (inside fe80::/10) and NAT64. The fix was full-CIDR matching plus extracting embedded IPv4 regardless of notation, with adversarial tests — [GitHub issue AZX-PBC-OSS/helix#2](https://github.com/AZX-PBC-OSS/helix/issues/2)
- Stripe Smokescreen: an egress proxy that by default denies non-global-unicast destinations ("Deny: Not Global Unicast" for 127.0.0.1) and RFC1918/fc00::/7. It has `--unsafe-allow-private-ranges` and ACLs with per-role `enforce`/`report`. Fly.io itself uses it for SSRF protection beside Tokenizer — [Fly docs Smokescreen](https://fly.io/docs/app-guides/smokescreen); [stripe/smokescreen](https://github.com/stripe/smokescreen); [Fly blog](https://fly.io/blog/tokenized-tokens)
- Validate-then-connect: resolve, validate every IP, connect only to a validated IP, keep the hostname for Host/SNI/cert checks, and apply the same rule on retries and fallbacks. Test rebinding with a short-TTL domain flipped to a private IP — [Safeguard guide citing OWASP](https://safeguard.sh/resources/blog/ssrf-dns-rebinding-validate-then-connect) (secondary source)
- AWS IMDS: IMDSv2 with hop limit 1 blocks containers behind an extra hop; AWS recommends 2 for container hosts. Per-user blocking on the host: `iptables -A OUTPUT -p tcp -d 169.254.169.254 -m owner --uid-owner apache -j REJECT`, or the allow-only inverse `! --uid-owner trustworthy-user`. The IPv6 IMDS endpoint is `[fd00:ec2::254]` — [AWS limit IMDS access](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-metadata-limiting-access.html); [IMDS options](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html); [new instances](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-IMDS-new-instances.html)

**Docker bridge / host loopback**
- Docker writes bridge rules in the host namespace. User rules go in `DOCKER-USER` (iptables), or under nftables a separate table with a `forward` base chain at priority `filter - 1` or lower. Packets reaching DOCKER-USER are already DNATed. Docker's NAT bypasses ufw's INPUT/OUTPUT — [Docker nftables](https://docs.docker.com/engine/network/firewall-nftables); [Docker iptables](https://docs.docker.com/engine/network/firewall-iptables); [packet filtering](https://docs.docker.com/engine/network/packet-filtering-firewalls)
- Hardening recipe (Palo Alto Cortex XSOAR): a dedicated bridge (`com.docker.network.bridge.name=docker-external`), `iptables -I INPUT -i docker-external -d <host private ip> -j DROP` to block the host, `iptables -I DOCKER-USER -i docker-external -d 169.254.169.254/32 -j DROP` for metadata, and blocks on internal ranges "so a rendered page … cannot perform a SSRF or DNS rebind attack" — [Cortex XSOAR Docker network hardening](https://docs-cortex.paloaltonetworks.com/r/Cortex-XSOAR/6.13/Cortex-XSOAR-Administrator-Guide/Docker-Network-Hardening)
- CVE-2020-8558: kube-proxy set `route_localnet=1`, which stops the kernel treating 127.0.0.0/8 as martian, so neighbours on the same L2 could reach a node's localhost-only services. Fixed in Kubernetes v1.18.4/1.17.7/1.16.11 — [Unit 42](https://unit42.paloaltonetworks.com/cve-2020-8558)

### Inferences
- **Mechanisms ranked for zephyr's shape** (root daemon and unprivileged agent in one container):
  1. *Separate network namespace for the agent* (the sandbox-runtime model: no netns route out, proxy over a Unix socket). This is the strongest, because it also removes the agent's view of the container's loopback, where the daemon's sockets and the gate live. It would mean spawning agent children under a netns, which conflicts with `rpi` needing model-API access unless that traffic also goes through the proxy.
  2. *nftables `meta skuid <agent-uid>` rules in the container's own netns*: allow only `tcp dport <proxy-port>` to the proxy's loopback address (and DNS to the proxy if it resolves), and drop everything else from that uid, including 127.0.0.0/8, ::1 and the docker bridge gateway (host). This is the documented `--uid-owner` pattern (AWS). Caveats: it needs `CAP_NET_ADMIN` at setup, root must own the ruleset, and the agent must not be able to setuid or reach the root daemon's other loopback listeners. uid matching works only on locally generated packets (OUTPUT), which is exactly this case.
  3. *Proxy-only egress via env vars* (HTTP_PROXY) alone is advisory. Any raw socket bypasses it, so it needs (1) or (2) under it.
- Host-side layer: run the container on a user-defined bridge, and in `DOCKER-USER` (or an nftables forward chain at priority < filter) drop traffic from that bridge to the host's IPs, RFC1918, 100.64.0.0/10, 169.254.0.0/16 and the IPv6 equivalents. Separately, the host's INPUT chain must drop traffic from the bridge to host loopback-bound and published services. Never enable `route_localnet`.
- The proxy itself (run by the daemon) should: resolve once, validate all A/AAAA records with a proper CIDR library (normalising IPv4-mapped, v4-compatible and NAT64), dial the validated IP, keep the hostname for SNI/Host, refuse redirects to internal addresses, and handle CONNECT by host:port with the same checks. Smokescreen's "deny non-global-unicast" default is a good baseline. DNS for the agent should go only through the proxy or a daemon resolver, to close the E2B-style direct UDP/53 leak and DNS-based exfiltration.
- Domain allowlists without TLS inspection can be bypassed with domain fronting (Claude Code and Modal both say so). If the token broker already terminates TLS, the same proxy can compare SNI with the Host header and refuse a mismatch.

### Gaps
- No measured studies (success rates) comparing uid-owner rules, netns isolation and proxy-only egress for agent sandboxes. The evidence is vendor design documents.
- No primary source found on how Modal, E2B or Cloudflare treat 169.254.169.254 and host loopback inside their guests, beyond E2B rejecting internal BYOP proxy addresses.
- "Muse" (Meta) network or credential architecture beyond "permission and security checks operate separately from the AI model" and per-user isolated VMs is not public.
