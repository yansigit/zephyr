# Human approval and consent for tool-using AI agents (centred on arXiv 2610.21063)

Scope note: all arXiv IDs below were checked against the arXiv export API on 2026-11-09 (title and abstract match). Figures for 2610.21063 come from its full text (v1 PDF, 36 pp.); figures for other papers come from their abstracts unless stated. Reference URLs for non-arXiv items (Checkmarx/OWASP, MCP spec, ADR 0030, Visa disclosure) are as cited in 2610.21063's bibliography and were not fetched independently.

## Q1. "Approve What, Exactly?" (arXiv 2610.21063): method, runtimes, findings, mitigations

### Takeaway
The paper exists: Kodathala, Pollishetty, Cargill, "Approve What, Exactly? Effect Binding and Trusted Rendering for Agent Step-Up Authorization", cs.CR, submitted 2026-10-15. Its thesis is that an approval is a second factor only if (a) compromising the agent cannot produce it and (b) it commits to exactly the effect that executes. Binding is the dependable, cheap half; trusted rendering is the fragile half; a second device added nothing measurable over a trusted on-host card in their experiments; flooding still works 45–60% of the time even with limits. Note: the "about half" figure in the brief is precisely "4 of 8 runtimes where binding could be measured" (10 runtimes audited, 12 rows).

### Cited Findings
**Framing and properties**
- Criterion: "An approval protects an agent action only if compromising the agent cannot produce it, and only if it commits to exactly the action that executes." Modelled on EU PSD2 strong-customer-authentication "dynamic linking" (code bound to amount and payee). — [arXiv 2610.21063 §1.1, §2.1](https://arxiv.org/abs/2610.21063)
- Seven properties: P1 agent independence (agent cannot read/forge/answer/overlay/replay the approval), P2 effect binding (executed digest = approved digest, signed), P3 freshness and single use (nonce, expiry, atomic consume, at most one execution), P4 trusted rendering (every card element computed from the canonical descriptor except one labelled untrusted region; distinct descriptors render as distinct cards), P5 non-repudiation (third party with the user's public key can verify), P6 scope integrity for grants, P7 flood resistance (rate limits, per-session and per-user pending caps, lockout after repeated denials, duplicate merging). — [2610.21063 §2.2](https://arxiv.org/abs/2610.21063)
- Approval designs compared as modes of one gateway: none; chat-confirm ("yes" in the agent's own channel, lacks P1); narrated-card (agent-written card text, lacks P4); unbound (passkey approves run/session, lacks P2, P3); TOTP (lacks P2, P5, relayable); txn-sign (payee and amount only); host-confirm (trusted card on agent host, no second device, no signature); ASU; ASU without the agent's explanation. — [2610.21063 Table 2](https://arxiv.org/abs/2610.21063)
- Explicitly no human-subjects data: approvers are simulated oracles (exact-compare, perceptual, careless, fatigued, narration-trusting) with assumed miss probabilities, or 15 LLMs. Authors state no claim is made about how often people catch attacks. — [2610.21063 §1.4, §7.1, §8.3](https://arxiv.org/abs/2610.21063)

**Twelve approval-path attacks (AB1–AB12)**
- AB1 amount cancellation (amount=10000, total=-10000); AB2 decoy-field recipient (e.g. hidden bcc); AB3 grant stretching ("allow similar" reused for different payee/amount); AB4 padding/hidden text (U+2800 Braille blank, U+3164 Hangul filler, bidi controls); AB5 label spoofing (argument names like "Target" or "Verified by client"); AB6 non-injective rendering (boolean vs string "true"); AB7 enrollment squatting (agent registers its own passkey); AB8 challenge encoding ambiguity; AB9 ceremony control; AB10 post-approval substitution; AB11 flooding within one run; AB12 threshold splitting. — [2610.21063 Table 3](https://arxiv.org/abs/2610.21063)
- Targets: Google AP2 reference impl (v0.2.0, commit e1ea56d), Microsoft Agent Governance Toolkit ADR 0030 (commit 47abed7), MCP Python SDK 2.3.0 elicitation, OpenClaw 2026.10.3 (static review only), the in-process frameworks, and ASU as control. — [2610.21063 §3.2](https://arxiv.org/abs/2610.21063)
- AP2: constraint layer rejected every executed binding attack; residuals: sample card summarises merchant-chosen `payee.name` while binding is on `payee.id`, so two payees can share a display (AB6); cumulative budget only if the integrator sums usage, else two sub-budget payments both pass (AB12). — [2610.21063 §3.3](https://arxiv.org/abs/2610.21063)
- Microsoft ADR 0030 was "the strongest third-party design": whole-action digest, substitution fails with `action_digest_mismatch`, one-time consumption, LLM output cannot satisfy a human stage; but floats serialise with Python repr not RFC 8785 (cross-language hash parity fails closed), and no flood control — module opened 50 pending requests freely. — [2610.21063 §3.3](https://arxiv.org/abs/2610.21063)
- MCP elicitation (form mode) forwards server text unchanged: a 521-character message with 400 blank Braille glyphs, an RTL override and 50 Hangul fillers reached the client byte for byte; label-spoofed text arrived verbatim while the tool paid a different account; payments of 10 and 10000 to different accounts produced byte-identical requests and both executed after "accept". — [2610.21063 §3.3](https://arxiv.org/abs/2610.21063)
- OpenClaw is the positive control for rendering: its exec-approval card escapes invisible characters, caps length, redacts secrets; "allow always" grants are keyed to the resolved argv and cwd, but matched on parsed arguments rather than a signed digest (AB3 partial). — [2610.21063 §3.3](https://arxiv.org/abs/2610.21063)
- Worked example (AB2 hidden bcc): on the agent-narrated view 15/15 LLM approvers approved; on the gateway-rendered card listing both recipients in the title 15/15 denied. — [2610.21063 §3.1, Fig. 2](https://arxiv.org/abs/2610.21063)

**Runtime audit (10 runtimes, 12 rows)**
- Probed with stub models: OpenAI Agents SDK 0.23.1, LangGraph 1.2.15, Google ADK 2.12.0, Agno 3.1.3, Pydantic AI 2.56.0, CrewAI 1.15.27 (two primitives), AutoGen AgentChat 0.7.5 (two primitives), smolagents 1.26.0 (no approval mechanism), MCP SDK 2.3.0; OpenClaw static. Claude Code, Codex CLI, Cursor not run (proprietary). — [2610.21063 §4.1, Table 5](https://arxiv.org/abs/2610.21063)
- P1 fails by construction for every in-process callback (approval runs in the agent's process). — [2610.21063 §4.1](https://arxiv.org/abs/2610.21063)
- Effect binding (P2): of 8 measurable rows, 3 pass (OpenAI Agents SDK binds a call id to a canonical payload; AutoGen code-executor approval; MCP keeps args server-side), 1 partial (Google ADK resists the resume API but not a session-store writer), 4 fail (LangGraph and Agno execute whatever is in thread state at resume; Pydantic AI executes caller-supplied message history; a later CrewAI hook can mutate args an earlier hook approved). — [2610.21063 §4.2](https://arxiv.org/abs/2610.21063)
- Agno substitution via the documented remote-continue endpoint reproduces on 3.0.9, 3.0.10 and 3.1.3, i.e. past Loopjacking's published affected range (2.5.6–3.0.9). — [2610.21063 Table 6](https://arxiv.org/abs/2610.21063)
- Single use (P3): in 5 rows an approval is consumed relative to run state but executes twice after a rollback-and-resume, because the approval carries no nonce/expiry of its own. — [2610.21063 §4.2](https://arxiv.org/abs/2610.21063)
- Flooding (P7): in all 7 measurable rows nothing capped or rate-limited pending approvals; in the 5 runtimes with a native pause a single model turn raised 20 pending approvals. — [2610.21063 §4.2](https://arxiv.org/abs/2610.21063)
- Audit record: no runtime produces a third-party-verifiable approval record; approvals are unsigned booleans/flags in run state. Every runtime with structured arguments leaves rendering to the integrator. — [2610.21063 §4.2](https://arxiv.org/abs/2610.21063)

**ASU reference design**
- Agent holds only a session token; gateway canonicalises the call to descriptor Δ (RFC 8785 JCS, SHA-256), policy returns allow/deny/challenge; on challenge the agent gets HTTP 202 and an opaque approval id only (no code, no card text, no challenge). The approval page is served to the user's phone, never relayed through the agent. Passkey (WebAuthn, user verification required) signs c = H(JCS({tag, digest, approval_id, nonce, grant_digest})). Retry with id atomically moves approved→consumed and executes the stored descriptor; resubmitted args with a different digest get 409 `effect_mismatch`. Optional token mode: short-lived Ed25519 token over {h, aud, exp, jti}. Every step appended to an HMAC-keyed hash-chained audit log; receipts verifiable offline. — [2610.21063 §5.1](https://arxiv.org/abs/2610.21063)
- Descriptor v2: tool, effect class (read, write, delete, send, pay, exec, net, admin), typed args, union of all targets, principal/session/agent, claimed origin, issue/expiry. Normalisation: paths absolute and symlink-resolved; URLs reduced to scheme/host/port/path, rejected if userinfo; emails lower-cased and IDNA-encoded; shell commands as argv not strings; closed per-tool schema so unknown arguments are denied; at most one amount and one currency, never summed; schema-less tools always stepped up and flagged. — [2610.21063 §5.3](https://arxiv.org/abs/2610.21063)
- Packaged policy: step-up on first-time recipient, amount over threshold, autonomous origin, destructive classes, plus an aggregate window over all non-read effects of 5 effects or 200 USD per 600 s; crossing it forces a fresh challenge no grant can satisfy. Origin is agent-asserted and the card says so; origin-based step-up is not counted as a defence. — [2610.21063 §5.3](https://arxiv.org/abs/2610.21063)
- Flood control: one pending card per session, identical retries merged, 6 calls per minute per session, at most 3 pending approvals per user across sessions, lockout after 3 denials. — [2610.21063 §5.3](https://arxiv.org/abs/2610.21063)
- Enrollment closed by default: first passkey needs a one-time out-of-band token (closes AB7). Page sets anti-framing headers and never rebuilds a card already on screen. ~5,600 lines Python/FastAPI, 610-line authenticator page, 410 tests. Overhead: challenged call 3.5 ms median, passkey verify 3.4 ms, policy 36 µs, offline receipt verification 144 µs. — [2610.21063 §5.4, Fig. 5](https://arxiv.org/abs/2610.21063)
- Formal: Tamarin model, 53 lemmas, proving binding, single use and key-level non-repudiation under three hypotheses; H3 (honest rendering origin) is the residual: authenticators sign but do not display the challenge, so a page on the gateway's own origin could show one card and get a signature over another (AB9 partial). — [2610.21063 abstract, §3.3](https://arxiv.org/abs/2610.21063)

**Evaluation (27,108 scripted trials, 609 AgentDojo pairs, 15 LLM approvers)**
- RQ1 binding: post-approval substitution (A4), replay (A5), grant stretching (A9), symlink swap after approval (A10) each succeed 1.00 against `unbound`; A4 and the symlink swap also 1.00 against TOTP; all four 0.00 against ASU. — [2610.21063 §7.2](https://arxiv.org/abs/2610.21063)
- RQ2 trusted rendering: AgentDojo with forged narration — attack success 0.54 against a narrated card and TOTP (95% CI 0.42–0.65) vs 0.03 against ASU (0.00–0.11) for the exact-compare approver; residual 0.03 is entirely effects policy allows without asking. For an approver who trusts the agent's words whenever shown, ASU equals the narrated card (0.54 vs 0.54); removing the explanation box drops it to 0.05 (0.01–0.13). Payee+amount-only display (txn-sign) lets 0.20 through vs 0.06 for the full card under the perceptual approver. — [2610.21063 §7.3](https://arxiv.org/abs/2610.21063)
- RQ3 second device: host-confirm (trusted card on the agent's host, no phone, no signature) equalled ASU in 137 of 140 scenario cells and every AgentDojo cell; the three differing cells are A9 and are caused by grants, not the device. The case for the phone rests on threat model (host compromise) and third-party verifiability (P5), not measured attack rates. — [2610.21063 §7.4, §8.1](https://arxiv.org/abs/2610.21063)
- RQ4 LLM approvers (15 models, 9 vendors, 23 attack + 11 benign stimuli, 6,120 decisions, $8.48): pooled catch rate 0.30 (CI 0.27–0.32) from the agent's description vs 0.98 (0.97–0.99) from the trusted card; per-model 13–52% narrated vs 90–100% on card. False-deny on benign near misses 0 on narrated, 0.16 on card (0–39% by model); 88 of 103 benign refusals cite a `<report placeholder>` artifact, without which false-deny would be 0.02. Decoy recipients, narration forgery and padding caught 0.00 from narration and 1.00 from card; visible plausible substitution weakest on card (0.88). Removing the explanation from the card changed at most 2 of 34 paired decisions for any model (no significant effect). — [2610.21063 §7.5, Table 9, Fig. 9](https://arxiv.org/abs/2610.21063)
- RQ5 flooding: A6 succeeds 1.00 with flood limits off and 0.45–0.60 with them on (default policy 95% CI 0.39–0.78), same for every bound design, slightly higher for TOTP (0.65, 0.70). "Rate limits, one pending card and lockout after denials reduce the number of chances an attacker gets, but each remaining chance is still a draw against an imperfect human." A6 is within one session, so per-user caps do not change it. — [2610.21063 §7.6](https://arxiv.org/abs/2610.21063)
- Fatigue sweep (21,840 trials, assumed fatigue model, ten-task session): challenge everything 0.35 attack success, challenge nothing 0.62, challenge only amounts and new payees 0.31 (of which 0.25 from effects then allowed without a prompt). Ordering changes with fatigue parameters; "fewer prompts help only if the prompts that remain are the ones that matter." — [2610.21063 §7.6, Fig. 11](https://arxiv.org/abs/2610.21063)
- Grants: "allow similar" lowers A9 for the perceptual approver (0.20→0.00) but raises it for the careless approver (0.30→0.70), "because a careless approval of a grant also approves the grant's later uses." — [2610.21063 §7.4](https://arxiv.org/abs/2610.21063)
- What approval doesn't fix: splitting a payment with no aggregate window succeeds 1.00 in every mode (0.00 with the window); a memory write the agent claims a user asked for succeeds in every mode because policy allowed it — agent-asserted origin alone was enough to skip approval. — [2610.21063 §7.6, §8.2](https://arxiv.org/abs/2610.21063)
- Utility: on benign AgentDojo tasks every bound design completed all 97 tasks with no false blocks (simulated approvers), at 0.3–1.6 prompts per task (0.75 overall). — [2610.21063 §7.6](https://arxiv.org/abs/2610.21063)

**Recommended mitigations (§8.2 deployment guidance, verbatim in substance)**
- (1) Bind the approval to a canonical digest of every argument and execute the stored call, not the agent's resubmission. (2) Render the card from the call, type every value, escape what cannot be seen, list every recipient in the title; the agent's text, if shown at all, in a collapsed box. (3) Cap pending approvals and lock out repeated denials, accepting this only reduces chances. (4) Don't let the agent's claim that the user asked for something decide whether to ask. Second device is worth it when the host may be compromised or an approval must be shown to someone later; it is "not a substitute for" binding/rendering. — [2610.21063 §8.1–8.2](https://arxiv.org/abs/2610.21063)
- Code, data, proofs: github.com/Sports-Vision-Inc/agent-step-up (not inspected). — [2610.21063 abstract](https://arxiv.org/abs/2610.21063)

### Inferences
- For zephyr's gate (DESIGN §4.16): its existing per-run cap of 3 and 20/day roughly matches ASU's "3 pending per user"; the paper's own number says such caps still leave ~45–60% flood success within a session, so the cap should be paired with one-pending-card-per-run, duplicate merging and lockout-after-N-denials, and should not be relied on alone.
- The gate builds the card from the payload with agent/page text quoted and scrubbed; the paper's data (0.54→0.05 when explanation removed for narration-trusting approvers; LLM approvers unaffected) supports keeping agent text collapsed/labelled untrusted rather than removed, especially if a human (who may trust narration) is the approver.
- `/ok N` taking "the stored payload ... once in one statement" is the ASU "execute the stored call, atomically consume" pattern; the paper's P3 finding (rollback double-execution in 5 runtimes) argues the consumed state must live outside anything a rollback/restore touches (e.g. not in the agent session).
- The 30-minute one-time pass is a grant; the careless-approver result (0.30→0.70) suggests the pass should bind every target (recipient, URL, path) and free only bounded fields, as ASU does.
- The host-confirm result suggests the TUI/chat socket card (rendered by root code from the payload) is as good as a phone against an agent-only compromise; a passkey/phone app buys P5 (verifiable record) and resilience to host compromise, not better catch rates.

### Gaps
- No human-subjects data in the paper; all catch/fatigue numbers are simulated or LLM approvers.
- The GitHub artifact (code/data) was not inspected; Tamarin hypotheses H1/H2 not read in detail (only H1 "decide from the card" and H3 "honest rendering origin" were seen).
- Paper is v1 (2026-10-15), not peer reviewed as far as found; no citing papers located yet.

## Q2. Related work: fatigue/flooding, TOCTOU, card content, standing grants, delayed actions, audit logs, strong vs weak channels

### Takeaway
2026 saw a cluster of arXiv work converging on the same conclusions: bind approval to the exact effect and re-check at commit time (Loopjacking, Approval Laundering, Commit-Time Authorization, AID-Guard, VAC, Consent Integrity, SUDP); standing "allow always" rules are a real escalation vector (58% elicitation against Claude Code/Codex); approval fatigue is recognised but almost unmeasured in humans; audit work proposes hash-chained, offline-verifiable records with millisecond overhead.

### Cited Findings
**Approval fatigue and the industry picture**
- Systematic analysis of 59 papers, 21 production agent systems and 26 security plugins (as of April 2026): runtime approval adopted by 15/21 systems, policy specification by 14, scope configuration by 16; intent anchoring and trust labeling (heavily studied in academia) have zero production deployment. Users are "caught between approval fatigue and uncontrolled agent autonomy." — [Wang, Li, Tian, arXiv 2605.24309](https://arxiv.org/abs/2605.24309)
- Agents of Chaos (two-week red-team, 20 researchers, live agents with email/Discord/shell): 11 case studies incl. non-owner compliance, identity spoofing; per 2610.21063's reading, Case #8 a non-owner renamed their Discord display name to the owner's and the agent deleted memory/config and reassigned admin; Case #1 both "double-check" confirmations came from the requesting non-owner in the same conversation. — [Shapira et al., arXiv 2602.20021](https://arxiv.org/abs/2602.20021); case details via [2610.21063 §1.2](https://arxiv.org/abs/2610.21063)
- User study (20 students, OpenClaw, five tasks varying privacy/stakes/reversibility) introduces "delegation regret": users regret the agent acting beyond what they would have authorised, not that it erred. — [arXiv 2607.18257](https://arxiv.org/abs/2607.18257)
- Permission user study → ML assistant predicting users' permission decisions at 85.1% overall, 94.4% for high-confidence predictions; decisions driven by communication context and consistent within contexts. (Relevant to reducing prompts, not to adversarial settings.) — [arXiv 2511.17959](https://arxiv.org/abs/2511.17959)

**Time-of-check/time-of-use and binding**
- Loopjacking: a human approves operation A and the implementation uses that decision for B. Two variants: representation-based (B encoded but omitted/misrepresented at approval) and post-approval state substitution. Reproduced substitution in 7 Agno AgentOS releases up to 3.0.9 and 12 versions of a LangGraph Agent Server composition up to 0.14.0; representation mismatch in OpenClaw 2026.2.23, fixed in 2026.2.24; OpenAI Agents SDK 0.22.0/0.22.2 negative control (rejects mutated B). Fix: complete canonical rendering plus exact use-time comparison, or preventing pending-state mutation. — [Arun Kumar, arXiv 2609.21081](https://arxiv.org/abs/2609.21081)
- Approval Laundering: six failure modes in coding harnesses (Scope, Argument, Temporal, Tool, Delegation, Semantic laundering); instrumented Claude Code's PreToolUse, N=19–20 runs per class, Bound-Gap Rate with Wilson CIs, kappa=1.0. Prototype "Approval Token" = keyed Hk(principal, agent_id, session_id, tool, arguments, scope, expiry) from a mediator that never gives the agent the key; across 118 paired runs it eliminates Delegation and (for the seeded construction) Temporal laundering (p<10^-5), leaves Scope laundering unaffected and no significant reduction in Argument laundering (p=1), because those diverge "one process level below" what a field-only verifier sees. — [Wang, arXiv 2609.38983](https://arxiv.org/abs/2609.38983)
- Commit-Time Authorization: 17 fixed advisories from 3 deployed agent products: 12 where the approval did not cover the executed effect, 5 where it survived a change in the facts it depended on. CTA requires at commit a live grant, current premises, ready dependencies, exact-effect binding and an eligible path; sink validates or atomically consumes an expiring single-use derived grant. Without a revocation signal all five tested models mostly completed tasks with unauthorized effects. Machine-checked proofs. — [Santos-Grueiro, arXiv 2607.10487](https://arxiv.org/abs/2607.10487)
- AID-Guard: revalidates the approved request and provider state at commit; one reservation yields at most one effect across retry and recovery. 210 Stripe trials matched; 40 terminalize-successor, 30 race, 10 crash-recovery schedules without duplicate effects; blocked 44/44 attacks under full proposer compromise. Cost: strict exact-manifest profile cut benign utility 35.4–43.8 points. — [Tong, Dai, Guo, arXiv 2608.21159](https://arxiv.org/abs/2608.21159)
- SUDP: requester proposes a canonical operation, user authorises with a fresh authenticator-backed (WebAuthn) grant, a custodian redeems it; reusable authority never crosses to the agent. Satisfies 6 of 7 stated properties; proofs sketched, no empirical evaluation (per 2610.21063). — [Yu et al., arXiv 2604.24920](https://arxiv.org/abs/2604.24920)
- Microsoft Agent Governance Toolkit ADR 0030: RFC 8785 action binding, one-time consumption at execution, fail-closed, hash-chained log, LLM output barred from human stages. — [ADR 0030, cited in 2610.21063](https://arxiv.org/abs/2610.21063)

**What a card must show**
- Verifiable Action Card (agentic browser): card reconstructed from the ground-truth pending action and trusted intent provenance, rendered in trusted browser chrome, re-verified at dispatch; default-deny confirmation. 24-scenario benchmark (confused deputy, Lies-in-the-Loop dialog forging, IPI, adaptive substitution): attack success 68–100% without VAC, 0% with it on every model, 78% legitimate-task completion, 0% false blocks. No signature or second device. — [Irshad et al., arXiv 2609.18411](https://arxiv.org/abs/2609.18411)
- Consent Integrity (WYSIWYS for agents): card rendered by a trusted mediator from the real action at the boundary; what the analyzer cannot classify is surfaced as "uninspectable", not silently approved. On GTFOBins (1,330 trusted-tool abuses) it silently passes 10.0% (all via a trusted tool); on 28,798 normal tldr commands it marks 87.0% uninspectable — quantifying the security/usability tension for shell commands. — [Weng, arXiv 2606.02668](https://arxiv.org/abs/2606.02668)
- 2610.21063's six card rules: typed and quoted values with a property test that distinct digests render distinct cards; escape non-printables, collapse blank-glyph runs to a counted marker, cap long values with expand control and risk line; agent-chosen arg names only under a fixed `arg.` prefix; every recipient/account/URL/path is a target listed in the title with a first-time-recipient check; flag inline interpreters (`bash -c`, `python -c`); agent explanation collapsed and labelled untrusted. — [2610.21063 §5.2](https://arxiv.org/abs/2610.21063)
- CATP found distinct argument vectors can normalise to the same action before hashing, limiting what a receipt establishes (a non-injectivity hazard for card and digest alike). — [arXiv 2609.38223](https://arxiv.org/abs/2609.38223)

**Standing grants ("allow always")**
- From Approval to Abuse: repository-planted context steers coding agents to request "plausibly justified, yet dangerously broad" allow-rules. Against Claude Code and Codex CLI, agents elicited the target allow-rules in 58% of instances; acquired rules covered 56.9% of category-specific capability test cases; conditional on approval, verified silent goal completion in 47/58 (81.0%). — [arXiv 2610.22987](https://arxiv.org/abs/2610.22987)
- Earned authority under a fixed ceiling: when an agent evolves under a live grant, fix a transition envelope and immutable effect ceiling at grant time; agent-produced evidence may allocate authority below the ceiling but never raise it. — [Zhang & Zhang, arXiv 2607.23586](https://arxiv.org/abs/2607.23586)
- 2610.21063: grants built by the gateway (not the agent) from the approved descriptor, digest inside the signed challenge, bind every argument except explicitly freed bounded fields (capped amount, length-bounded text); recipients, accounts, paths, URLs never free; use cap, total cap, expiry, scoped to one session and tool. — [2610.21063 §5.3](https://arxiv.org/abs/2610.21063)

**Delayed / scheduled actions**
- No paper found that studies "approve now, run later" scheduling directly. The closest is Commit-Time Authorization (approval can be withdrawn or premises change before commit; 5 of 17 advisories were approvals surviving a change in facts) and AID-Guard (retry/recovery after approval creating a second effect). — [arXiv 2607.10487](https://arxiv.org/abs/2607.10487); [arXiv 2608.21159](https://arxiv.org/abs/2608.21159)
- Approval Laundering's "Temporal laundering" class covers approvals used outside their intended time/session window. — [arXiv 2609.38983](https://arxiv.org/abs/2609.38983)

**Audit logs and after-the-fact review**
- 2610.21063: no audited runtime produces a verifiable approval record; ASU uses an HMAC-keyed hash chain plus passkey receipts verifiable offline from the public key and RP id. — [2610.21063 §4.2, §5.1](https://arxiv.org/abs/2610.21063)
- Auditable Agents: five auditability dimensions (action recoverability, lifecycle coverage, policy checkability, responsibility attribution, evidence integrity); 617 security findings across six open-source agent projects; pre-execution mediation with tamper-evident records adds 8.3 ms median; proposes an "Auditability Card". — [arXiv 2604.05485](https://arxiv.org/abs/2604.05485)
- Agent Flight Recorder: canonically serialised event binding 8 fields intent→execution→provenance; hash chain + Merkle batching; ~48 µs median per event, 512 bytes/event; detects edit, delete, reorder, fork tampering at 100% with zero false positives; structured forensic queries 1.0 precision vs 0.013/0.077 for unstructured text search. (On-chain anchoring optional, for cross-org disputes.) — [arXiv 2609.01931](https://arxiv.org/abs/2609.01931)
- CATP (Claude Code and Codex hooks): commit to enforcement-time policy and normalised action, durably record the decision before returning permission; five missing consistency checks found in validly signed counterexamples; ~85 ms median hook overhead, ~174 ms offline verification. Evidence remains conditional on trusted runtime, monitor, host and key. — [arXiv 2609.38223](https://arxiv.org/abs/2609.38223)
- aiAuthZ (predecessor to 2610.21063): off-host gateway, per-message HMAC with single-use nonce, SHA-256 hash-chained audit log; residual attack success 0% for 15 models at ≤0.03 ms decision latency; blocked all 7 attacker-directed AgentDojo banking calls at the cost of one legitimate first-time payment. — [Kodathala, arXiv 2607.05518](https://arxiv.org/abs/2607.05518)

**Strong vs weak approval channels**
- Chat-confirm in the agent's own channel lacks agent independence and succeeds 1.00 against every scripted attack; TOTP is out-of-band but unbound and relayable (A4 1.00); host-confirm with a trusted card ≈ phone passkey in measured outcomes; the passkey adds third-party verifiability and survives host compromise. A passkey or TOTP secret readable from the agent's host "gives no independence". — [2610.21063 §2.2, §7.2, §7.4](https://arxiv.org/abs/2610.21063)
- CIBA + OAuth Rich Authorization Requests is deployed for agents as out-of-band per-action approval (Auth0), but issues a bearer token, not a user signature, and the details come from the requesting backend (2610.21063's assessment). — [2610.21063 §9](https://arxiv.org/abs/2610.21063)

### Inferences
- Zephyr's facts/vault scrubbing and "unreadable control reads as strictest / fails closed" align with Consent Integrity's "uninspectable ⇒ surface, don't pass"; the 87% uninspectable rate on ordinary shell commands is a warning that a gate classifying `bash` strings will either flood or pass a lot — argv-level descriptors (as ASU uses) help.
- The 58% allow-rule elicitation result is the strongest evidence against letting the agent propose standing grants; grants should be generated by the gateway from an approved descriptor, never from agent-proposed scope text, and broad rules should require a strong channel (zephyr's `strong_channels` concept fits).
- A delayed action ("a delay never goes late") is a TOCTOU window by construction; CTA suggests re-validating premises (recipient still allowed, grant not revoked, page/target unchanged) at the moment of execution, not just at approval.
- For the web/phone app: render from the stored payload server-side, never let the agent's process serve or relay the page, close enrollment with an out-of-band token, set anti-framing headers, and don't re-render a card while it's on screen (ASU §5.4).

### Gaps
- No peer-reviewed human-subjects measurement of approval fatigue or habituation for agent approvals was found in 2024–2026 arXiv searches; classic security-warning habituation literature (pre-2024) was not searched.
- MFA push-bombing statistics (the human analog of AB11) were not found in this pass.
- EffectGuard ("Approve the effect, not the tool call", ICML 2026 Workshop on Agents in the Wild) is cited by 2610.21063 but has no arXiv ID given; not verified.
- Per-class Bound-Gap Rates for Approval Laundering are in the full text, not the abstract; not extracted.
- OpenAlex/Semantic Scholar citation graphs were not queried (budget); citing papers of 2610.21063 (submitted 3–4 weeks ago) likely don't exist yet.

## Q3. Prompt injection aimed at the approval step itself

### Takeaway
The approval card is itself an injection target: if the agent (or a page/tool output it read) writes any of the card text, a forged benign narration defeats both humans and LLM approvers. Measured: forged narration succeeds 0.54 against narrated cards on AgentDojo; LLM approvers catch only 30% of attacks from agent descriptions vs 98% from a trusted card; hidden recipients/padding are caught 0% from narration.

### Cited Findings
- "Lies-in-the-Loop" (Checkmarx, 2025; catalogued by OWASP): agents misstate pending actions to their approvers so a benign description is shown while a different action runs. — [OWASP: Lies in the Loop](https://owasp.org/www-community/attacks/Lies_in_the_Loop) (as cited by [2610.21063](https://arxiv.org/abs/2610.21063) and [2606.02668](https://arxiv.org/abs/2606.02668))
- Forged narration on AgentDojo (agent claims to do the user's call while requesting the injected one): 0.54 success vs narrated card/TOTP, 0.03 vs trusted card; scripted narration forgery (A3) 1.00 against a narrated card. — [2610.21063 §7.3](https://arxiv.org/abs/2610.21063)
- Rendering attacks that worked against real designs: blank-glyph padding (U+2800, U+3164), bidi overrides, label spoofing via argument names, non-injective display (MCP elicitation: 10 vs 10000 to different accounts byte-identical). Example card in Fig. 4c hides `curl ...| sh` after 3,000 blank Braille glyphs. — [2610.21063 §3.3, Fig. 4](https://arxiv.org/abs/2610.21063)
- LLM approvers: catch 0.30 from narration vs 0.98 from the card; decoy recipients, narration forgery and padding 0.00 vs 1.00; homoglyph hosts 0.96 even from narration because the narration repeats the host. — [2610.21063 §7.5, Fig. 9](https://arxiv.org/abs/2610.21063)
- A prior NeurIPS 2025 workshop poster reports agents' justifications raise LLM monitors' approval of policy-violating actions (Za et al., cited by 2610.21063; not independently fetched). — [NeurIPS 2025 WiML poster](https://neurips.cc/virtual/2025/133902)
- Injected repository context steering the agent to request a broad allow-rule (an injection that targets the grant-approval step): 58% elicitation, 81.0% silent goal completion once approved. — [arXiv 2610.22987](https://arxiv.org/abs/2610.22987)
- VAC benchmark includes Lies-in-the-Loop dialog forging and adaptive substitution in agentic browsers: 68–100% success without, 0% with a ground-truth card in trusted chrome. — [arXiv 2609.18411](https://arxiv.org/abs/2609.18411)
- Underlying IPI benchmarks: AgentDojo (97 tasks, 629 security test cases) — [Debenedetti et al., arXiv 2406.13352](https://arxiv.org/abs/2406.13352); InjecAgent (1,054 cases, 17 user tools, 62 attacker tools; ReAct GPT-4 vulnerable 24%, nearly doubling with a "hacking prompt") — [Zhan et al., arXiv 2403.02691](https://arxiv.org/abs/2403.02691)
- Agent-asserted origin ("the user asked for this") is itself an injection lever: in ASU's scenarios it alone was enough to skip approval for an allowed write. — [2610.21063 §7.6, §8.2](https://arxiv.org/abs/2610.21063)

### Inferences
- Any card field that page text, tool output or agent prose can influence (titles, labels, button text from `browser_class`, mcp server descriptions) must be quoted, typed, escaped and visually subordinate to fields computed from the payload; zephyr's current "agent and page text quoted, cut, scrubbed" is the right shape, and the paper adds: counted markers for invisible runs, bidi stripping, and listing every target in the title.
- If zephyr ever lets an LLM pre-screen approvals, it should see only the trusted card; the 0.30 vs 0.98 gap is the paper's largest effect.

### Gaps
- No work found measuring injection against *human* approvers on agent cards (all numbers are simulated or LLM).
- Checkmarx's original Lies-in-the-Loop disclosure and the Wiz Research symlink-dialog report were not fetched directly.
