# Virtual cards (D2-cards) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Main's agent can ask for a virtual card for one checkout; zephyr checks the cap, the checkout origin and a payment window over all money, the owner approves (zephyr's strong `/ok` with `Manual`, Link's biometric with `Link`), the daemon fills the number only on the bound origin, and the number never reaches the agent's text.

**Architecture:** `cards.rs` holds the `Issuer` trait, `AnyIssuer` (`Manual`, `Fake`, `Link`), the in-memory numbers (`Live`) that every daemon-side scrub reads through `broker::secrets`, and the card's life (ask, issue, fill, poll, close). The gate reads tool `card` as a money action of kind `Card`, adds the payment window after the mode for every money effect, and lets a Pay click through on an open card's origin within its cap. `cards_link.rs` is Link's HTTP client (device login, spend requests) against `api.link.com`, tested with a local fake server.

**Tech Stack:** Rust, no new crates (`reqwest` with rustls, `hyper` for the fake server, `rusqlite`, `toml_edit`, all present). Python only in `tests/fake-rpi.py`.

**Spec:** `docs/superpowers/specs/2026-11-12-calls-cards-design.md`, the cards parts (§4.1–4.7, §4.14, §4.15). Its closing "Decided with the owner (2026-11-12)" section wins. Calls are another lane's.

**Decisions this plan adds** (the spec is silent, wrong about the code, or the brief overrides it):

1. The spec's `spend` table name is taken (the LLM budget, schema v2): money effects go in **`payments`**.
2. `proposals.strong` exists since v15 (setting proposals); the window reuses it. v20 adds no column to `proposals`.
3. Cards have their own id space (`cards.id`): an `auto` card has no proposal. The scrub label is `[card:#<card id>]`; a held card's proposal is `#P` and its card says so when issued.
4. `cards::Live` is a process-wide static keyed by the state folder, because every scrub path has only a `Config` (`broker::secrets(cfg, vault)` appends its values). Tests in one process use distinct fake numbers.
5. The owner's number reaches the daemon over the chat socket in a `card` field of the line, which `ChatChannel` moves into `cards::enter` (memory) and never into the inbox row; the row's text is `/card put N KIND`. The host's `zephyr card put N` is the one way in. **No TUI form** in this lane.
6. The code (3–4 digits) is scrubbed only where it stands as a whole run of digits; a 3-digit value replaced everywhere would garble unrelated output.
7. Command logs (`.procs/*.log`) are scrubbed by a separate process that reads `vault.toml`; it cannot see the in-memory number, and handing it a descriptor risks leaking that descriptor to the agent's commands. So a number the agent reads back from the page into a command's output is scrubbed in the answer the daemon gives, not in the log file. The spec's threat model already accepts the read-back (§4.4).
8. A request's currency must be `approvals.currency`: `cards.max` and the window are in it.
9. With an issuer that asks the owner itself (`Caps::asks_owner`, Link), the gate's mode step is skipped for kind `Card`: facts, `cards.max`, the origin and the window run, then the spend request is created. A window-crossing card is held `strong` and created only after the strong `/ok`. It is cancelled with `/card close N`.
10. Link, from its published docs and `stripe/link-cli`'s source: `POST /spend_requests`, `GET /spend_requests/:id?include=card`, `POST /spend_requests/:id/cancel` on `https://api.link.com`; the device login `POST /device/code`, `/device/token`, `/device/revoke` on `https://login.link.com`. A cancel call exists (the spec found none), so `close` cancels an unused request. Link's `expires_at` is at least 3 hours, so zephyr's own expiry is the bound. The OAuth client id is the service's `account`; nothing is hard-coded.
11. `Manual` instructions go in the reply to the `/ok` (a strong channel by `Config::check`); under `auto N` they go to the run's channel. They hold no secret.
12. A `Manual` card's `expires_at` restarts at `put`, so making the card does not eat the fill time.

## Review Focus

1. **A card number in the agent's text, audit, notices or replies.** After a full run (issue, put, fill, a read-back echoed by `exec`, close): no outbox row, audit row, inbox row or session file holds the number; the echo reads `[card:#1]`. Tests in C-4 (unit) and C-8 (`no_number_anywhere_after_a_card_run`).
2. **A fill on a look-alike origin** (`https://www.amazon.ca.evil.example`, `http://` for `https://`, another port): `not filled`, `reveal` never called, no `fill` in the browser's log. Test in C-8.
3. **A purchase split across cards**: under `auto 100`, a 99 card issues and the second within 600 s is held with `strong = 1`; its `/ok` from `discord` is refused even with `strong_only = ["loosen"]`. Tests in C-5 and C-7.
4. **A card with no checks**: `Issuer::issue` is reached only from `cards::issue`, which takes a `Checked` token only `gate` code can make; an amount of 0, over `cards.max`, another currency or `http://` never reaches `Fake` (its log stays empty). Tests in C-5 and C-6.
5. **The payee by id beside the name**: the card's `pays:` line is the origin from `vault::origin`; the agent's merchant is on its own quoted line; a merchant text of `https://www.amazon.ca` with site `https://evil.example` shows `pays: https://evil.example`. The charge notice puts the issuer's merchant id first. Tests in C-5 and C-9.
6. **A Link token or key in the agent's reach**: the agent's `exec` environment, `mcp.json` and `/vault` list hold neither `[[service]]`'s key nor `cards-link.json`'s tokens, and that file is 0600. Tests in C-3 and C-10.
